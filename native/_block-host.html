First layer: Human → UI → Host (here) → Daemon{Orchestration → System of Process} → SoR / External World

Internal flow

The operator request enters from the UI into the Host's agent runtime; runtime and model are one fused unit (single block, no internal edge to a separate LLM box — the doc explicitly collapses them: “Claude CLI — agent runtime + model in one”). The Host then carries the request downward into the Daemon on the edge labeled “runs”, where Orchestration translates it and selects the process. Daemon lifecycle (session-boot start or explicit sutra native start, §4.0) is attributed by §4.0 to the Sutra plugin (“managed by plugin”), now placed Host-resident per ADR-021 (gap #4 closed) — the lifecycle edge is drawn from the Host only on the partial support of §1.0's “runs” label. A return edge comes back up from System of Process: when a process runs, it invokes a host LLM selected per workflow among claude/codex/deepseek (ADR-005) — so the Host slot is entered from below as well as above. Everything sits inside the Authority + Tenancy gate wrap and stands on the Compute base layer.

Open / gaps — questions for the founder

  • Working assumption carried from founder session (also echoed in sibling drafts _matrix.html / _block-orchestration.html, which are not source of truth): only System of Process calls the LLM/Host. This exclusivity appears nowhere in index.html — §1.0 states no such rule, and ADR-005 only says host-LLM selection is per-workflow. Confirm and write it down (§1.0 or an ADR), or drop it.
  • ADR-005 allows codex/deepseek as host-LLMs, yet §1.0 labels the Host box “Claude CLI” singular — is Claude CLI the fixed operator-facing host while per-workflow LLM calls may route to a different host, or can the top-of-stack Host itself be swapped? Cited ranges do not reconcile this.
  • §1.0's Host → Daemon edge label “runs” conflates lifecycle (Host runs the Daemon) with request flow (request reaches Orchestration) — which transport carries the request (CLI invocation, IPC, file)? Not specified in cited ranges.
  • Where does the Sutra plugin live in the block diagram? §4.0 says the daemon is “Started by Sutra plugin at session boot” / “managed by plugin”, but the plugin is not placed inside Host, Daemon, or any §1.0 block.
    DECIDED 2026-06-12 — Sutra plugin is HOST-RESIDENT: hooks = Host lifecycle interceptors · skills = Host-invokable bundles · per-turn blocks = Host-emitted discipline; daemon-side analogs live in Orchestration/SoP. sutra/os/decisions/ADR-021-sutra-plugin-host-residency.md (Accepted) + index.html §4.12.4.
  • Host is per-session while Daemon is “always-on” — what happens to an in-flight operator request if the Host (Claude CLI session) exits while the Daemon is still RUNNING? Cited ranges cover daemon restart but not Host-absence semantics.
  • No internal decomposition of the Host beyond “agent runtime + model in one” exists anywhere in the cited ranges — is second-order detail for the Host block (session state, tool loop, context window) intentionally deferred to the UI/_consumer-product detailing pass?
