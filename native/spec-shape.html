SHAPE — functional spec SPEC · Lens (decomposition)

STATUS: WORKING DRAFT (2026-06-16). Functional spec for the SHAPE family (worked axis: Lens (decomposition)). Product altitude (the WHAT, not the HOW). Produced by the A→B bootstrap path as bounded Work-Atoms (write → critique → fix), rendered deterministically. Spine: D62 P1 (directional/bounded/structured) + P2 (placement).

At the front of every run, SHAPE reads the fresh input and decides the run's form — what kind of ask it is, how certain the ground is, and where to cut the work into children — so RUN executes a deliberately-shaped plan instead of a default one.

1. Abstract

SHAPE is the family of axes that read the incoming work fresh, every single run, and decide the form that run will take before any of it executes. The one thing every SHAPE axis shares — its answer to the sorting test — is that it reads the INPUT, fresh, on each pass: nothing is carried over as a standing decision, the shaping is re-derived from this ask, this goal, and the patterns available now. SHAPE fires at the front of the loop, between INTENT and RUN, and GOVERN wraps the shaping transition like every other. What the operator gets is a run that is deliberately formed to its own situation — a one-line ask gets one atom, a multi-part build gets a partitioned plan — instead of every piece of work being forced through the same default mold. Read SHAPE as the front door: where an intent stops being a wish and becomes a plan with a shape.

2. What it does

When a new intent arrives, SHAPE looks at it and forms the run around what it actually is, so the operator never has to hand-build the plan or watch a trivial ask get over-processed. It reads the ask and names its kind, it reads how certain the ground is and chooses a posture to match, and it reads where the natural seams are and cuts the work into children along them — and only then does the work begin. The operator feels this as a system that meets each piece of work on its own terms: a summarize-this-doc request runs as a single shot, a ship-the-redesign request fans into a coordinated set of pieces, and a why-is-retention-falling request is treated as an exploration rather than a march to a wrong answer. The plan is shaped to the work, freshly, every time.

3. Why this is its own family

SHAPE exists because the very first decision about a piece of work — what form it should take — is otherwise an unexamined constant, and a wrong default here taxes every later stage. It solves the front-of-loop framing problem for whoever sets work in motion: the same partition, the same posture, the same assumed kind of ask applied to everything regardless of fit. It is its own closed family, and not folded into a neighbor, because its members are the only ones defined by reading the input afresh on each run rather than by accumulating on the unit, gating a transition, or spending a stock — that single read-the-input-fresh property is the boundary. The six-family count is principled on the system's own native rule, not on any external numeric precedent: the families are a closed skeleton while the axes inside each are open, minted flesh (faceted classification in the Ranganathan sense, where a fixed set of facet families holds an open set of values). SHAPE is the front-reading facet of that closed skeleton, with the axis set inside it deliberately left open to mint.

4. Place in the loop

On the shared loop — INTENT, SHAPE, RUN, RECORD, EVIDENCE, GROW, with GOVERN wrapping every transition — the highlight sits on SHAPE, the stage right after INTENT, and the map is otherwise unchanged. SHAPE reads the input fresh and fires at the front, before each run, exactly as its row in the master family table states; it consumes the just-arrived intent and emits the shaped plan that RUN will execute. It is also the stage that reads back from the loop's learning: the form it picks this run can be informed by what GROW has codified from prior runs — the record becomes evidence the moment it is read across runs, which is the EVIDENCE seam — so the front of the loop is where past improvement re-enters the present. GOVERN sits over the shaping transition the same as over every other, deciding whether the chosen shape proceeds, asks, or is denied.

5. The axes

The catalog of SHAPE is small and each member is a categorical dimension you sort the work into — these are read-and-decide axes, not numbers you aggregate. TYPE reads the ask and decides its kind (a task versus a question versus a direction), and it runs first because the kind colors everything after it. CERTAINTY reads how known the ground is and decides the posture — do, analyze, probe, or stabilize — and it sits upstream of the cut because the posture decides which cut even fits. LENS reads where the natural seams are and decides where to cut the work into children, and how those children are wired relative to one another. Alongside these the family also carries the finer shaping dimensions — the control-flow pattern (parallel versus sequence), the depth of effort, and the run's pace — each likewise read fresh from this input. Every row answers the same sorting question with YES: it reads the input, fresh, every run, and fires at the front before RUN.

6. One axis, walked

Take LENS, the most load-bearing SHAPE axis, and watch its value change across two runs. The takeaway first: the same system produces a completely different plan for two different asks because LENS re-reads the input each time and the seams it finds differ. For a ship-the-onboarding-redesign intent, LENS reads a multi-deliverable build, finds the seams between deliverables, and cuts by deliverable into roughly three children wired to coordinate — its value resolves to a parallel, multi-actor shape. For a fix-this-one-bug intent arriving moments later, LENS reads a single-thread change, finds no seam worth cutting, and resolves to a sequential, single-actor shape — effectively one piece. Nothing about the first run's cut is carried into the second; the value is derived fresh from the input each time, which is precisely what makes it a SHAPE axis rather than a standing setting. The cut LENS chooses is then handed to RUN as the plan to execute.

7. Boundaries

SHAPE owns the fresh, front-of-run framing and nothing downstream of it. It looks like SHAPE should own learning which shape worked best, but that reads the accumulated record across runs, not this input fresh — flip it to GROW, whose Codify axis writes a proven practice into the FOLLOW catalog that SHAPE then reads. It looks like SHAPE should own whether the chosen shape is allowed to proceed, but that gates a transition with an auto-ask-deny verdict — flip it to GOVERN. It looks like SHAPE should own how the children it cut talk to each other, but that reads the relationship between two atoms — flip it to EDGE (handoff, shared-resource, must-cohere). It looks like SHAPE should own the budget a parallel cut will burn, but that is a finite stock the work spends — flip it to RESOURCE. And it looks like SHAPE should own when the run must happen, but that is about over-time scheduling and dynamics — flip it to TIME. In each case the sorting test is the referee: only read-the-input-fresh stays in SHAPE.

8. Why this grouping

These axes group under one family because they all answer the same question — what should this run look like, read fresh from this input — and splitting them would scatter a single front-of-loop decision across several places while merging them into a neighbor would hide the framing step inside learning or gating where it does not belong. The grouping rule is the closed-skeleton, open-flesh principle plus the sorting test: the family slot is fixed, the axes inside it are minted and open, and membership is decided solely by the read-the-input-fresh answer. The rejected alternative was a single mega-shaping axis, which collapses genuinely distinct reads (kind, posture, cut) into one undifferentiated decision and loses the stagger between them.

9. Path to productization

A new SHAPE axis grows along the same reusable path every axis follows — name and define it against the sorting test, show its need-advantage-how-example, thread it onto its owning page, cross-link it into the loop and its neighbors, then ratify it — specialized here so that SHAPE axes thread onto the workflow/flow page and attach at the front of the loop, and are ratified as front-reading members of the closed family. The honest math note belongs here too: SHAPE's natural fit is partial-order and topological ordering over the children it cuts, with acyclicity as the soundness check — detection-grade ordering ships early, while optimizer-grade scheduling is the at-scale horizon and properly belongs to TIME, not SHAPE. For the generic method see axis-productization; for where SHAPE axes live and run, see the platform workflow/flow page. This section points at those; it does not re-explain them.

Acceptance criteria (black-box tests)

  • A reader can quote section 1 alone and know what SHAPE is, the one thing every SHAPE axis shares (it reads the input fresh, every run), where it fires on the loop (the front, before RUN), and what they get — with zero other context.
  • Every SHAPE axis in the section-5 catalog answers the sorting-test question 'does it read the INPUT, fresh every run?' with YES, and each carries its own reads-WHAT / fires-WHEN / value-ladder coordinates matching the master family table verbatim (reads = the input fresh; fires = front, before each run).
  • Section 7 names the exact sibling family that owns each adjacent concern (GROW for accumulated learning, GOVERN for the gate verdict, EDGE for the link between children, RESOURCE for the finite stock, TIME for the when) via convert->flip->flag, with no 'see other families' hand-waving.
  • The worked micro-trace (section 6) walks ONE load-bearing axis (Lens) across two runs of the same workflow, showing its value change with named states (e.g. ship-redesign -> parallel/3-actors vs bugfix -> sequential/1), takeaway sentence first.
  • The doc states SHAPE's math fit (partial order / topological sort + acyclicity) AND its over-engineering boundary (detection-grade ordering ships early; optimizer-grade scheduling is the at-scale horizon, and belongs to TIME) in one honest clause rather than over-claiming.
  • The whole doc stays at product altitude: WHAT and WHY only, no schema/code/field-level implementation, with section 9 pointing OUT to axis-productization and DOWN to platform/flow rather than re-explaining the HOW.
  • EVIDENCE appears as a co-equal stage in the shared loop INTENT->SHAPE->RUN->RECORD->EVIDENCE->GROW, consistent with the sibling specs and the canon loop diagram.
  • Section 3's family-count justification rests on the canon's own native argument (families = closed skeleton, axes = open minted flesh, with Ranganathan cited only as generic faceted classification) and cites no de-canonized external authority.
