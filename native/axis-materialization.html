Materializing the axes — the six family workflows OVERVIEW · sub-page

STATUS: WORKING DRAFT (2026-06-16). The concrete companion to axis-productization. That page gave the generic five-step method; this page runs it — one worked example axis for each of the six families — and draws the system diagram tying every materialized axis to the loop. This is the L2 rung of the build ladder (workflows), the step before L3 (code). Productization, not implementation.

The one move — recap

Every axis — built-in or user-minted — is made the same way: one primitive (value ↔ axis, ADR-027) is minted, sorted by a read-test into one of six families, then walked through P1 NAME → P2 SHOW → P3 THREAD → P4 CROSS-LINK → P5 RATIFY. Families are a closed skeleton; axes are open, minted flesh. Materializing an axis = running that pipeline until the axis is live on the loop and backed by a real primitive field.

The system is not six separate machines. It is one factory (mint → sort → P1–P5) feeding one loop. The six families differ only in where they thread (which page), where they attach (which loop stage), and which field(s) on one or more of the 10 canon primitives store the value (several families compose more than one).

System diagram — the axis factory

Mint is cheap and open. The pick test retains (keep / merge / rename) or drops (reject) the axis, or — if it passes but fits no family — escalates to the core author, the only actor who reworks the closed family skeleton.

System diagram — the shared pipeline

Identical for all six families. The only thing that changes per family is the content of P3 (which page) and P4 (which loop stage + which primitive). Detail: axis-productization.

System diagram — the loop the axes attach to

The materialized axes are not new boxes on this loop — they are behaviors that fire at these stages. The attach matrix below says which family fires where.

The six workflows

One worked example axis per family. Each carries its five-step materialization workflow (every step with a runnable check) and a wiring table (runtime · backing primitive · loop attach · mint/escalate · failure mode).

Minting on the fly — and when the families change

Five of the six worked examples above were minted — they were never in a built-in list. That is the point: users mint axes freely; the family skeleton stays closed. The retention gate decides each minted axis’s fate:

OutcomeWhenWhat happens
keeppasses the pick test, no overlapproductize via P1–P5 (on the fly)
merge / renameoverlaps an existing axis / clearer labelfold in; keep the better name
rejectchanges neither what’s built nor who-readsdropped — logged, not silent
escalate (family-gap)passes but fits NO familysurfaced to the core author → may trigger a family rework
Only escalate changes the families, and only the core author does it — deliberately, off-the-fly. This is the single guard that keeps the skeleton closed while the axis set stays open. These family reworks (a new family, a split, a merge) are rare — the common path is keep / merge / rename. Pending: ratify this open-axis / core-author-rework rule as a numbered D-direction.

What this unlocks — the next rung

Every workflow above ends at a backing primitive field — WorkflowStep.goal.constraint, DecisionProvenance.codification_status, ExecutionResult.results['TOKEN_BUDGET'], Workflow.outbound_edges, cron_spec, cadence_metadata. That is the seam to L3 (code): each field becomes a real schema field on one of the 10 canon primitives, and each runtime behavior becomes engine logic at its loop stage.

Order to build (maps to the roadmap): the fields land in S1 runtime core (WorkflowStep, ExecutionResult, DecisionProvenance) → the gates in S4 governance (Compliance, Delegation grant-check) → the detectors in S5 validation + emergence (Codify’s EMERGE, Cadence’s miss-detector). Materialize the axes (this page, L2) → then code the fields (L3, by stage).
