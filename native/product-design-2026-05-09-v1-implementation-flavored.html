Native — operating system for multi-strand operators

Native runs alongside founders + manager-ICs operating judgment-driven, multi-stranded work. Every decision becomes a typed artifact. Every consequential moment routes through a named, gated, audited workflow. Native learns the operator over time, carries picked work through analysis → decide → build → operationalize → auto-run, and stays out of the way until your judgment is needed.

1.The user need

1.1 The operator's reality

Multi-strand operators — founders running 1-N companies, manager-ICs leading teams while also taking on judgment-driven initiatives and IC work — have a workload that is variable, cross-cutting, and accumulating. They cannot just "do their job," because the job IS the variability. Three types of work happen simultaneously:

StrandExample (founder running 3 companies)
Named scopeCEO of holding co; leads orgs, hires
Judgment workCross-company initiatives picked because they matter, not because assigned
IC workHands-on code, writing, selling, deciding

1.2 Founder voice (verbatim, 2026-05-09)

"It can help me execute projects over time. It can help me do one-off tasks. It can surface relevant decisions it needs to take. It can understand my taste and the way I take decisions, the way I communicate. It can personalize communication for me and personalize the way I think about things and help me grow, and as I'm growing it can change things accordingly. It can help me have interactions between me and the Native. It can help me create and pick some work so it can run through the entire lifecycle of doing analysis, taking decisions, maybe building out and then operationalizing it, and once it is operationalized it can just automatically run so... so founder graduates to next problem." Captured verbatim in NATIVE-ENGINE.md §12.1

2.The solution Native delivers

2.1 Mission (one sentence)

Native is the operating system that runs alongside a manager-IC day-to-day — executing projects over time, picking up one-off tasks, surfacing decisions the operator needs to take, learning taste + decision-style + communication voice, personalizing how it thinks with the operator as the operator grows, and carrying picked work through its full lifecycle from analysis → decision → build → operationalize → auto-run. Mission — NATIVE-ENGINE.md §12.2, RATIFIED v1 2026-05-09

2.2 The 5 outcome promises (v1 top-5 blocks)

Five capability blocks deliver the v1 outcome experience. Other 13 blocks ship as stubs in v1 (per pillar P3) and fill incrementally.

BlockWhat operator saysMechanism

B7"Every LLM call shows me what it expected + what it got."Pre/post validation gates per Workflow step. Testing-framework discipline applied to LLM execution.
7d"I pick the work; Native carries it through analysis → auto-run."Lifecycle orchestrator: ANALYZE → DECIDE → BUILD → OPERATIONALIZE → AUTO-RUN.

B18"Native sounds more like me over time."Person formation: taste / voice / decision-style / risk tolerance / cadence modeled passively + (opt-in) sparse explicit ratings.

2.3 The 6 surfaces the operator interacts with

ROUTE

Classify every operator utterance. Match a Workflow OR log + consider pattern emergence.

RUN

Fire matched Workflow. Host-LLM executes each step. Pre/post-validation gates fire per step.

GATE

Pause on steps requiring approval. Surface structured approval card. Resume on explicit utterance.

EMERGE

When a pattern repeats ≥4 times, Native proposes a named Workflow. Operator approves once → registered.

AUDIT

Every transition emits a typed EngineEvent (26 types) + DecisionProvenance row. 3-channel JSONL durability.

TENANT

Each company is an isolated Tenant. Cross-tenant ops require explicit delegation. Default-deny.

2.4 What Native is NOT (explicit non-goals)

  • NOT a UI / visual designer. Terminal + audit log + slash commands only.
  • NOT autonomous execution. Daemon proposes; operator approves; host-LLM executes.
  • NOT a memory product. The artifact catalog is reuse, not memory.
  • NOT browser automation. Consume the commodity; don't build it.
  • NOT capability-additive over vanilla Claude Code. Native adds content + integration + curation + distribution + governance + multi-tenant.

4.Evolution stages

Native evolves across THREE timelines simultaneously: per-operator (how Native learns ONE operator over time), per-product-version (v1 → v2 → v3), and per-migration-phase (the 127-part canon decomp shipping now).

4.1 Per-operator evolution (the person-formation arc)

Per pillar P7 falsification test: "If Native behaves identically at day-1 vs day-180 → P7 broken; personalization static not dynamic."

Day 1 — first install

Time-to-first-Execution ≤ 30 min · 0 OHS/wk baseline

Native is generic. Operator types an utterance; Native classifies, no Workflow matches yet, signal logged. Operator may run an ad-hoc one-off via sutra run. Audit log starts capturing voice + decision-style + cadence patterns.

Day 14 — early signal (v1 target window)

≥3 OHS/wk · 4+ repetitions trigger first proposal

Native has logged enough operator activity to detect a pattern (k=4 emergence). Surfaces first Workflow proposal — "you've done this 4 times in 3 weeks; should I register it?" Operator approves → first auto-run candidate exists.

Day 30 — operating cadence

Multiple registered Workflows · weekly Pulse view

Native uses operator's verbs in proposals. Multi-Workflow cadence schedule runs (Pulse, weekly portfolio review, etc.). Operator's weekly Pulse shows decisions queued + cycles auto-running + hours-saved. Approval gates fire on risky steps only.

Day 90 — sustained automation

≥10 registered Workflows · founder predicts gate decisions

Person-model predicts operator's gate decisions ≥75% accurately. Operator can watch Native operate the work-week and intervenes only on novel decisions. Cross-tenant ops gated cleanly. Decision-replay works for every past Execution.

Day 180 — adapted operator

Native runs work the operator's way

Native sounds like the operator. Workflow proposals come pre-shaped to operator's style. Cycle approval becomes implicit (trust signal ≥30d clean → fully autonomous on per-Workflow basis). Operator graduates to the next problem; prior Workflows keep running.
