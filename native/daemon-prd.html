The Daemon PRD · PROPOSED

The clerk that never sleeps: one background process per operator that runs the six-verb loop the v1 tools already implement by hand. It adds no new powers — it adds continuity.

s0 · The founder's model, and where it already lives

Founder (2026-08-19): one input gate · hard-constrained step spine — inside the daemon it is always deterministic where things go · each step, when reached, decides its own way of doing it · the last unit is a workflow, programmatic or LLM-driven · systems inside systems.

The model is a restatement of ruled canon — nothing here invents architecture. This PRD only binds the daemon to it and names the decisions the daemon newly forces.

s1 · Promise

"Decisions are waiting on you; everything else is handled." Work advances while no chat window is open: schedules fire, events route, asks queue — and every outcome lands in the same auditable records the tools write today. The daemon is invisible when healthy; its only operator-visible surfaces are the app's stores and one health row.

s1b · v0 already runs: the chat harness (founder recognition, 2026-08-19)

The simplest daemon is not a thing to build — it is the thing you type into. Every message to Sutra already flows through a deterministic per-turn pipeline that understands the input, resolves it to the right architecture, and forces declared work before any mutation. Honest name (dual-lane fold): v0 is a daemon-shaped harness with a human clock — not yet a daemon. The loop exists; only the clock and the machine-readable rows are missing.

s2 · The loop contract (deterministic spine, free interiors)

        +--> 1. LISTEN   utterance | schedule tick | event
        |    2. ROUTE    registered way? FOLLOW : (low confidence -> ASK)
        |    3. OPEN     record goal + pinned check BEFORE any work
        |    4. WORK     steps run; interiors free; permission -> outbox, WAIT
        |    5. CHECK    run the pre-declared check; measured, never claimed
        +--- 6. CLOSE    one ledger row: outcome, attempts, duration

Failure is part of the spine, not an exception (deepseek fold): reject, timeout, cancel, fail-retry, fail-escalate are first-class CLOSE outcomes with their own deterministic next hops. A tick firing mid-WORK on restart must find the OPEN record and resume or close it honestly (crash consistency); OPEN and WORK are idempotent on retry — same input never yields two ledger rows (join keys: run_id, outbox_id).

s4 · Effectuation boundary (what the daemon may and may not do)

Codex fold: without this section, "daemon schedules work" quietly becomes ambient authority.
  • The daemon only ever emits proposed workflow invocations — it never mutates target state itself (ADR-004: registry + audit layer).
  • Every mutation executes in an identified host session (claude | codex), and the record row carries the chain: input id → workflow id → host session id → operator decision → output ref. That chain IS the observability answer: one causal trace across daemon, host, and mutation.
  • Approve/reject from any surface (app, terminal) is UI over the same process-layer gate — not an app-specific write path. The app never writes the record (B18-7 twin rule).
  • Approve is never automatic. No flag, retry policy, or schedule can synthesize one (F8 stands).
  • Slow or wedged LLM work must not block the gate: the queue is visible, bounded, and shed-able — "3 waiting, 1 stuck 40min" is a rendered state, not a hidden one.

s7 · Non-goals (v-first daemon)

  • No cross-device ordering, no cloud, no multi-operator — one daemon per operator per machine (A3 single-user stands).
  • No new authority: every gate that binds a session binds the daemon.
  • No retry policy beyond the ruled outcome enum — retry budgets arrive with A8, not here.
  • Not a general job runner: it runs registered workflows only; unregistered asks become CONSTRUCT proposals for a human.

s10 · Interaction patterns — how v1 behaves, drawn out

Seven flows, same five lanes every time. These are product-level interaction contracts, not implementation sequences: each shows the trigger, the ownership handoffs, what the human sees, where state persists, and the terminal outcome. Together they exercise every ruled close outcome: pass · fail-retry · fail-escalate · reject · timeout · cancel.

Reading key: solid = action · dashed amber = durable wait · red = failure (still spine) · green = recovery. The DAEMON lane is deterministic code; the HOST lane is where the LLM lives.

Pattern 1 — Happy path: speak once, see the result

Pattern 2 — Approval wait: the durable pause

Pattern 3 — No registered way: the honest ask

Pattern 4 — Schedule tick: work while you sleep (gate G1)

Pattern 5 — Failure escalation: evidence, then a decision

Pattern 6 — Crash recovery: the files are the state

Pattern 7 — Change of mind: cancel and supersede
