The system, grown in this order A READING · PROPOSED

The system itself, drawn plainly: ARTIFACT → WORK → ARTIFACT. Then one capability is added per picture, in the order ruled on what comes first. Every label is the system's own word first, with the lending example in italics under it. Whatever a step adds is outlined in yellow, and a box at the top right says what it is and gives the example.

Founder's direction, 2026-09-26: write the system diagram itself (artifact, work, artifact), take the example out of it, and show one by one which element is added to grow the system, in the order of the priorities. Each capability either adds structure (boxes and arrows) or one line to a kit card: what the department carries, what every piece of work carries, what every artifact carries.

This section, in order: what comes first (the order) → the system, grown (this page) → the product (its screens, same steps) · to a company (the plumbing, and growth now, next, later) · the model (artifacts, work, where decisions are made) → to a running system (every capability carried down to records and one run loop).

0 · The system, bare

An artifact, a piece of work, an artifact, inside a department that has its identity from birth. Nothing else yet: the three kit cards are empty.

1 · Now: 15 steps, one at a time

Step 1 · + Named reads and writes EDGE

Named reads and writes (a line on every artifact's kit): work touches only named artifacts, through one contract: read, add a version. e.g. Intake reads Loan book, writes Due list.

Step 2 · + Goal SHAPE

Goal (a line on every piece of work's kit): says what this piece of work is for. e.g. list every loan due within 7 days.

Step 3 · + Versions GROW

Versions (a line on every artifact's kit): an artifact is never edited; each change adds a version. e.g. Due list v31 after v30.

Step 4 · + Run log GROW

Run log (a line on every piece of work's kit): every run recorded, naming the recipe it used. e.g. Intake ran 09:02 on recipe v1.

Step 5 · + Run on request TIME

Run on request (a line on every piece of work's kit): anyone can start a run: a person, an AI, a rule, another piece of work. e.g. the collections lead or an engine asks Intake to run.

Step 6 · + Check SHAPE

Check (a line on every piece of work's kit): the output must be verifiable; the shape of the work picks which kind of check. e.g. a count that must match the loan book; for a judgment, a sample a reviewer passes.

Step 7 · + Auto inside the record GOVERN

Auto inside the record (a line on every piece of work's kit): work that only reads and writes the company's own record runs without asking. e.g. Intake rebuilds the due list on its own.

Step 8 · + Ask and stamp GOVERN

Ask and stamp (a line on every piece of work's kit): an action the rules do not cover waits for an answer (approve, change, decline) from whoever is asked: a person, an AI, a rule or another department. e.g. publish a due list 40% longer than yesterday's? asked of the collections lead.

Step 9 · + Cap per run RESOURCE

Cap per run (a line on every piece of work's kit): a limit on what one run may spend, per resource dimension: tokens, money, calls, time. e.g. 50k tokens and 60 calls a run.

Step 10 · + Deny GOVERN

Deny (a line on every piece of work's kit): some actions are refused outright by a rule. e.g. never call before 09:00.

Step 11 · + Lineage GROW

Lineage (a line on every artifact's kit): each version records which input versions and which run made it, and whether its check passed. e.g. Due list v31 made from Loan book v412, check passed.

Step 12 · + Schedule TIME

Schedule (a line on every piece of work's kit): work runs on a clock: daily, weekly. e.g. Intake daily at 09:00.

Step 13 · + Wake on a new version TIME

Wake on a new version (a line on every piece of work's kit): work runs when an artifact it reads gets a new version. e.g. Score risk wakes on a new due list.

Step 14 · + Chain brake RESOURCE

Chain brake (a line on every piece of work's kit): a new version can wake work that writes a version that wakes more work; the brake gives each chain one id and a step count, so no piece runs twice in one chain and a chain stops at its limit and asks. e.g. a loan book change wakes Intake once, not again when Intake's own output lands.

Step 15 · + Undo, with severity GOVERN

Undo, with severity (a line on every piece of work's kit): every action inside the ecosystem names how it is undone, and a severity that sets who must approve the undo. e.g. a wrong due list: revert to v31, low severity, automatic.
