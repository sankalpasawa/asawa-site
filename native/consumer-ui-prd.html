Work-order header

idband / parentstatusversionowner
consumer-ui-prdPLATFORM / consumer-uiPROPOSEDv1claude (founder to reverse-engineer screens)
How to use this PRD. It is reverse-engineered FROM the locked design surfaces — design-system.html (skin authority), consumer-ui.html (cockpit doc), preview/app.html (DS UI v2.0 built prototype), preview/tokens.css (token core). Two disciplines guard against reverse-engineering traps (dual-consult folds): (1) the locked visual is a sample, not the requirement set — every section separates LOCKED VISUAL LANGUAGE (aesthetic constraint) from REQUIRED PRODUCT BEHAVIOR (semantic requirement); (2) nothing here may exist only in the UI — every card maps to a persisted record (§P4), and consequential actions always cause a persisted state transition, never a UI-only one.
Reverse-engineering the shipping app: Desktop App — the live terminal vs panel states read off the code, the governance behavior/visibility mode design, and the design-system import delta.

P2 · Users + jobs

Primary user: the operator-founder (single-user v1 — RULED B18-4; collaborator-awareness arrives v2+). Jobs, in priority order: decide what only they can decide (approvals) · direct new work in plain words · watch that promised work ran honestly · trust-check ("show me what you did and why") · tune autonomy over time. The desktop app's promise, carried from the cockpit doc: "decisions are waiting on you; everything else is handled."

Governance contract — two switches (RULED B18-2)

Governance is two independent switches, never one:

SwitchValuesWhere it livesRule
BehaviorON / OFFserver-persisted (per instance)consequential actions confirm before executing while ON; flipping is itself a consequential action
VisibilityFULL / QUIET / RAWper-browser (local)changes what the operator sees, never what the system does

Hard label rule: while behavior is ON, the word “off” is forbidden on every UI surface — quiet visibility is labeled QUIET, honestly scoped (terminal quiet = T1, panel-only). Mixing the switches into one control is a design defect, not a simplification.

Field-map rule (deepseek fold): when a screen adds a field to any card, the field must name its source column in the persisted record, its type, whether it is required, and whether it is read-only or derived. A field with no source column is forbidden — that is UI inventing state.

P5 · Component inventory + state matrix

13 locked components (skin authority; class names ds-* are STABLE for import): decision card, chip, quiet line, composer, WorkBlock, atom card, work line, tray, held, clock, dot, banner, table, rail. LOCKED VISUAL LANGUAGE: warm-light single theme (bg #FAFAF7, ink #1A1714, gold accent #B8945F); 4 semantic colors carry meaning ONLY — clay=decide, steel=review, forest=done, rose=alert; Playfair display max 19px in-app (30px greeting), Inter body 14px, mono for blueprints/commands; spacing steps 4/8/12/16/24/32/64 only; shadows on cards only; max 3 chips per row.

State-matrix rule (dual-consult convergent): no component ships without ALL of: default · hover · active · empty · loading/skeleton · error · blocked/permission-denied · retry · offline-queued · audit (post-action receipt). The preview covers happy states; no true zero-states exist anywhere yet — first-run, no-sessions, no-decisions screens are unspecified and are the first screens the founder should design.

P7 · Pattern extrapolation — what generalizes, what must not be inferred

  • Generalizes: the card grammar (dot + title + meta + primary/quiet actions) to any new decision type; the chip grammar to any new status; the two-pane session shape to any new record-bound conversation; the quiet-line to any new queue.
  • Must NOT be inferred: new semantic colors (4 is the set); dark mode (single warm-light theme is a commitment); new rail tabs without a founder gate (L1 open); any card without a persisted entity (P4 rule); density beyond max-3-chips; shadows beyond cards.

P8 · Acceptance criteria (screen-design definition of done)

  1. Every screen names its cards, and every card names its P4 record + truth-class tag.
  2. Every component instance has the full P5 state matrix designed (incl. zero-states).
  3. Every consequential action traces to a persisted state transition (no UI-only state).
  4. Semantic colors used for meaning only; tokens from tokens.css exclusively.
  5. Escalation/approval cards carry: why, risk, reversibility, safe default, once-vs-rule.
  6. Version gating respected: a screen may not render capabilities its version has not earned (chapter below).
Authority note. This ladder is the rendering layer: what each version looks and feels like. The capability contract — what ships, the entry and exit evidence gates, the success numbers — lives once in Versions (v1–v5) and is normative there. If the two ever disagree, versions.html wins. Nothing on this page restates a gate or a success number; it only shows the surface.

Zero-state doctrine for every future screen: an empty surface states what is empty, what that means, and offers exactly one primary next step. A degraded surface additionally states what still works, what does not, and — only where a record actually guarantees it — where in-flight work is safe. With the v1 durable outbox (RULED B18-5), the degraded screen may now promise exactly this much: “queued work is safe on this Mac” — and no more (the outbox is not a scheduler). Never a spinner without a sentence; never a blank panel; never a safety claim without the record to back it.
