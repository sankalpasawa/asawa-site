Axis-productization — the methodology OVERVIEW · sub-page

STATUS: WORKING DRAFT (2026-06-15). The repeatable method that turns any axis — one of the built-in ones or a new one a user mints on the fly — into product. Sub-page of the system, simply. Productization, not implementation.

What this is

Axes are an open set — minted on demand from one primitive (value ↔ axis). That raises a question the product must answer: when a new axis appears, how does it become part of the product? This page is that answer — one repeatable, five-step path, the same path the built-in axes (Substance, Scale, Codify, …) already took, and the same path a user-minted axis takes.

Self-similar: productizing one axis is the same shape as productizing the whole product (lock → thread → validate → wire → ratify). The method is the product process, run at axis scale.

The five steps

StepWhat happensOutput
P1 · NAME + DEFINEanchor the axis as a value via value↔axis; run the sorting test to assign it ONE family (SHAPE / GROW / GOVERN / EDGE / RESOURCE / TIME)one row in the family table (axis · what it reads · what it fires on) + the family verdict
P2 · SHOWwrite the product quartet: need (what breaks without it) · advantage (what reading work against it buys) · how (its ladder/state-machine + triggers from the record) · one examplea product-altitude section (no schemas/code)
P3 · THREADplace it on the surface its family points to — SHAPE→flow, GROW→evolution (+ own page if load-bearing), GOVERN→authority, EDGE/RESOURCE→company-decomposed, TIME→its homea row on the owning page, or a new child page if it earns one
P4 · CROSS-LINKwire it into the loop — which record-evidence it reads, which joint it writes back to, which neighbors it toucheslinks both ways (overview ↔ page)
P5 · RATIFYonce it's earning its keep, promote the decision to canon (a numbered D-direction or ADR)ratified axis

A NEW axis, walked end to end — "compliance"

A user runs a regulated workflow and keeps hitting an unnamed dimension: does this action satisfy a binding external rule? They mint it. Here is that brand-new axis going through the same five steps:

"Compliance" was never in the built-in list. It enters the product the same way every axis does — minted, sorted (GOVERN: it gates whether an action is allowed), shown (need/advantage/how), threaded onto the authority page as a new gate dimension, cross-linked into the loop, and ratified. No re-architecting; the open-set machinery absorbed it.

The retention gate — what happens to a minted axis

Minting is cheap, so the gate must do more than pass/fail. The pick test (“does it change what-you-build or who-reads?”) produces one of five outcomes:

OutcomeWhenWhat happens
keeppasses the test, no overlapproductize via P1–P5
mergeoverlaps an existing axisfold into it; keep the better name
renamesame axis, clearer labelalias → canonical name
rejectchanges neither what's built nor who-readsdropped (noise) — logged, not silent
escalate (family-gap)passes but fits NO familysurfaced to the core author — may trigger a family rework (governed, not on the fly)
Only escalate can change the families — and only the core author does that, deliberately. Users mint axes freely; the family skeleton stays closed until real usage forces a rework. See the open-axis rule on the system, simply §5.
