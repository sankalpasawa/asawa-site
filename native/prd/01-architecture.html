§1.4.1 Module eligibility — strict 4-test rule

A capability becomes a Module only if it satisfies ALL four:

#TestWhat it means
1Independent lifecycleCan be added / updated / retired without touching the host Product's release cycle
2Explicit configuration surfaceHas per-Deployment binding config (not hardcoded into Product code)
3Own runtime state / observabilityProduces its own audit rows, metrics, replay artifacts (not just inherits Product's)
4Possible reuseDesigned so a future second Product could compose it (cross-product reuse designed for, not guaranteed in v1)

If a capability fails any test → it's a feature of Product, not a Module. Avoid Module-bloat (every feature inflated into a Module). Daily Pulse + Feedback Engine pass; small UI panels don't.

§1.4.2 Capability vs Module — distinct concepts

ConceptDefinitionExamples
Capability (cap-NNN)Atomic platform/product primitive · single technical service · tracked in CSM (§4.8)cap-001 Input Routing · cap-002 Depth Estimation · cap-003 Blueprint · cap-007 SBOM
ModulePackaged composition of multiple Capabilities + UX + policy + per-Deployment config + own runtime stateDaily Pulse (composes cap-Telemetry + cap-Audit + cap-CrossPortfolio-Priority) · Feedback Engine (composes cap-Connector-Slack + cap-Privacy-Sanitize + cap-Audit)

Capabilities are building blocks. Modules are deployable units. CSM tracks both: capabilities flat-indexed; modules referenced as compositions.

§1.4.4 Layer-B products on Native (current + planned)

Native (§1.4 Layer A) is a multi-product platform. CoS is one Layer-B product on it; future products sit at the same layer. Each Layer-B product specifies its own pillars + capability surface; all share the same Native Platform substrate + canon.

§1.5 Tech-parts cross-cut overlay

Four technical contract categories cut across every Layer-B product + every CoS pillar. PRD body surfaces what the operator observes (capability contract). Engine architecture — type signatures, state machines, invariants, lifecycle, storage — lives in canon (sutra/os/native/** + ADRs at sutra/os/decisions/). This overlay is the bridge: names what each category MEANS for the operator + where the deep spec lives.

The full design ↔ product ↔ tech traceability table lives in sutra/os/decisions/ADR-019-design-product-tech-bridge.md (engineering audience; not gating reading material).
