§3 HOW Methodology — Native's epistemic core #

PurposeNative's IP: not "do the work" — "do the work via the right HOW for this task." The methodology engine that the platform operationalizes.
OwnsHOW selection per task tier · approach · mindset · structure · detailing · decomposition · cascading recursion · before-doing thinking.
Depends on§2 task tier (T0-T3); §4 Native runtime (executes HOW choices); §7 Observability (measures HOW accuracy).
Does NOT ownExecution (§4 runtime); operator surface (§2); transport (§5).

Native exists to operationalize HOW, not as a platform with a HOW feature. Every operator turn — every Charter, every agent materialization, every Method route — embeds a HOW choice. §3 is the doctrine; §4 Native Platform is the runtime that enforces it.

DecompositionBreak into 3 / 7 / by-stakeholder / by-deliverable / by-risk?3-factor: forced parsimony · 7-factor: completeness · by-stakeholder: comms-heavy tasks · by-risk: high-stakes
CascadingWhen a sub-task gets stuck, recurse the HOW engine on the sub-task?Sub-T3 spawns child T3 with own HOW choices; depth bounded by complexity budget

§3.4 Acceptance criteria (HOW engine v1)

Forward-looking note: HOW Methodology has open questions documented at §C.6 FQ1 — which approach for which situation, when cascading stops, when HOW is learned vs operator-overridden. v1 ships the doctrine + operationalization shape; v2+ refines based on dogfood signal.

  • Every Native turn carries an explicit HOW manifest in state envelope (operator can request "show me your HOW").
  • HOW choices learned from B5.d learned patterns improve future selections (drift signal triggers re-learning).
  • Cascade depth bounded by complexity budget (Charter-set); depth-exhaustion escalates to operator (Authority gate).
  • Operator can override any HOW choice; override learned + applied to future similar tasks.
