§4 Native Platform — workforce-deployment substrate #

PurposeThe substrate that scopes, deploys, and supervises a workforce of agents. CoS (and future products) ride on it.
OwnsCharters (fixed/flex) · Agents (on-demand materialization) · Method routing per task tier · Authority gates · State envelope between pillars · Audit substrate (DecisionProvenance).
Depends on§4 Connector layer (for any out-of-process tool call); §6 Observability (instruments platform health).
Does NOT ownOperator surface; pillar UX; pricing; channels.

Native is the engine room. Operators don't see Native directly — they see CoS (§2). Native shows up only when CoS asks Native for a Charter scope, an agent, a method route, or an authority decision. Detailed primitive definitions live in §9 D.10 (Charter Model) and §9 D.11 (Method Selection); §3 surfaces the runtime behavior + state.

§4.0 Runtime daemon — where Native lives + runs

Native runs as a per-operator local daemon. The operator doesn't see it (per §A.2.2 post-onboarding zero-terminal); the daemon manages workforce deployment, audit-log writes, hook firing, and cadence scheduling silently in the background.

§4.4 Acceptance criteria (Native platform v1)

  • Charter create/update/retire is operator-only; agent materialization is Native-internal.
  • Authority gate fires at every external-effect call (send · write · delete · pay).
  • State envelope round-trips with zero data loss across pillar handoffs (HS-4 fires if it doesn't).
  • Audit substrate writes 100% of decisions to triple-channel (gate-log + provenance + artifact); cross-tenant queries default-deny.

§4.5 Test-before-conclude gate (accuracy primitive)

Native does NOT mark a task done before testing the output. Accuracy is a per-workflow KPI. Test happens BEFORE concluding, not after. Output is rejected back to B3 retry if test fails.

StepWhat happens
1 · Pre-declare testFor each task tier, Native pre-declares the verification criteria BEFORE running. For T0 (atomic): grep / file-exists / contract-match. For T1 (multi-action): step-by-step verify + final integration check. For T2 (iterative): operator-visible 1-min iteration verification. For T3 (Charter): milestone-gate verification at goal-transition points.
2 · Generate outputB3 produces output (auto-execute path).
3 · Run testNative runs the pre-declared test against produced output. Determinism: same input + same Charter → same expected output shape.
4 · Conditional concludeIf test passes → conclude + write audit row + present to operator. If test fails → loop to B3 retry (max N retries per Charter); after N failures → escalate to operator (Authority gate).
5 · Post-concludeOperator's feedback (drop / accept / refine) becomes test signal for B5.d learned patterns. Test thresholds adapt over time per workflow.

Why before-conclude, not after — testing AFTER means the operator sees a failure and has to ask CoS to redo. Testing BEFORE means CoS catches its own failures and retries silently. Accuracy KPI in §7 Observability measures: % of CoS outputs that passed first-time-test vs needed retry.

§4.6 HOW Methodology bridge (cross-reference)

Every Native primitive (§4.1) embeds a HOW choice from §3 HOW Methodology. Charters declare HOW preferences at creation; agents materialize with HOW context inherited; method routing (D.11) implements HOW-tier mapping; authority gate (D.6) defers to HOW's escalation logic. Native runtime is the executor; §3 HOW is the doctrine.

§4.10 Resilience contract — operator-visible failure behavior

Native's hardstop catalog (HS-1..HS-8) defines what the system does when it cannot continue safely. The full engine spec lives at sutra/os/native/hardstops/HS-*.md; this section is the OPERATOR-VISIBLE summary — what each hardstop looks like in operator surface terms. The operator never debugs the system; the system tells the operator what happened, what's safe to do next, and what needs operator decision.

§4.10.1 Hardstop catalog (operator-visible behavior)

HardstopTrigger (engineering, full spec in canon)Operator-visible behavior
HS-1 reflexive-checkWorkflow attempted to modify Sutra core primitives without reflexive_check Constraint clearedSystem REFUSES to self-modify; surfaces "this change touches Sutra's own rules — please ratify directly" — operator can authorize or cancel
HS-2 governance-overheadPer-turn governance overhead exceeds 25% of token budgetSystem aborts the current turn; operator sees "turn aborted (governance overhead exceeded budget)"; next turn proceeds normally per canon
HS-3 tenant-boundaryExecution attempts cross-tenant access without explicit delegates_to edgeCross-company action DENIED per canon; operator gets a "this action would touch ; explicit delegates_to authorization required" prompt
HS-4 audit-unwritableDecisionProvenance log unwritable across all 3 fallback channelsSystem STOPS per canon; surfaces "cannot record this decision; halting until audit recovers" — no silent unaudited execution
HS-5 cutover-rollback-failsCutover rollback path itself fails to restore prior stateCutover PAUSED per canon; operator + Tenant owner brought into HITL (human-in-the-loop) for the decision; no automated retry
HS-6 governance-hooks-fail3+ distinct governance hooks fail within the same turnSESSION SUSPENDED per canon; resume requires manual investigation of the failing hooks before re-engagement
HS-7 codex-queue-staleCodex review queue exceeds 20 items OR any item more than 7 days staleShipment broadly BLOCKED per canon until queue drains; operator sees "review queue saturated — shipments paused"

Hardstop UX contract: every hardstop produces (a) a 1-2 sentence operator-facing message stating WHAT happened, (b) a recommended NEXT ACTION (decide / authorize / wait / investigate), (c) a link to the audit row for the event. Operator never has to read engineer-level stack traces; the system translates.
