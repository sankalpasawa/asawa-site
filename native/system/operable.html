From capabilities to departments, functions and work items A READING · TESTED AT RUNG 0

In plain words first: a department, its functions and its work are four kinds of record, like four sheets. Each capability becomes a column or a rule in one of them. Today's app keeps all four in part; the documents sheet lacks versions, made-from and the check, and that is the gap.

The capability list says what the system must be able to do. It does not say where each thing lives or what runs it. The site already has the layers for that: the vocabulary's objects (L2), the platform's blocks (L3) and the ten canon primitives (L4). Carrying each of the 15 capabilities ruled now down those layers shows the gap exactly: 6 are in canon today, 6 need one new field on an existing primitive, and 3 need a primitive the canon does not have: the Artifact. Departments, functions and work items are not designed separately; they fall out as compositions.

Founder's question, 2026-09-26: we have written down capabilities; how do we design an ecosystem that is operable, shaped like what we have today (departments, functions, work items)? Where are we, what is the gap, what is the process, and teach that skill. Routed through core:native (stage: idea), core:native-coach and core:native-method; the test is rung 0, a think-through on paper.

Which solution to build is chosen first, on from capabilities to a solution; this page elaborates the one chosen.

In plain words: four sheets

A department, its functions and its work are records, like four sheets in a spreadsheet. Every capability becomes a column, or a rule, in one of them. The only step between the capability list and a working department is one question asked of each capability: is it about the department's rules, a standing job, one run of work, or one document? The answer is its sheet. The tags under each column name the capability it holds.

Partly built today. The app already keeps file records: the Workspace files each document into a department and a charter (a placement record), and the agents keep each run's files and name the run that made them. What is not there yet: versions across runs, what each version was made from, and whether its check passed. The one-room apartment: the seed is one department row, one kind of work (Intake), two documents, and only Identity awake. Growing never adds a new kind of sheet; it adds rows, columns ruled next, and functions that wake.

For the builders: the same thing in engineering terms

The sections below say where each sheet and column lives in the platform: the vocabulary's objects, the platform's blocks, and the ten canon primitives.

1 · Where we are

The design ladder is the site's own layers, walked downward. The model and the capabilities are ruled. The rungs below them already exist as pages, but no capability had been carried down into them. That carrying is the gap, and this page does it for the now tier.

2 · The records: the ten primitives, and the missing one

Every capability ruled now lands on exactly one primitive. Green is already in canon, amber needs one new field, red needs the Artifact, the ruled node of the model, which has no primitive: today an output is only a data reference inside a run.

3 · The one run loop

Every capability is a step of one loop. A trigger opens a run, the brake checks its chain, inputs are read by name, the step does the work, the check runs, the gate decides (deny, else auto, else ask), the new version is written with what it was made from, and the run is logged while its readers wake. The state on the right of each box is the run's state in canon.

4 · Departments, functions and work items

What we have today maps onto the same records: a department is a System with a Domain, a Charter and a Tenant; its five functions are glue workflows over its own records (Identity and Audit are needed now; Priority, Coordination and Adaptation arrive with the next tier); a work item is one run, an ExecutionResult.

6 · One case, walked on paper

A new loan book version, walked through the loop across the blocks. Every one of the fifteen now capabilities is touched. The walk needed exactly one record type the canon does not have: the Artifact, for the loan book, the due list, their versions and what each was made from.

7 · The founder's corrections, and where each landed

CapabilityThe correctionWhere it lands

The worlda use case built on the product, like a tool; latermoved from now to later
Wake on a new versionvery importantkept in now; it needs the Artifact primitive
Undoinside the ecosystem, not the outside world, with a severityWorkflow: an undo per action; severity picks who approves it

The chain brake, simply. Wake-on-a-new-version means one change can set off a chain: the loan book changes, Intake writes a new due list, the new due list wakes whatever reads it, and so on. The brake gives the whole chain one id (its root: the loan book version that started it) and counts its steps. A piece of work never runs twice for the same root, so nothing loops, and a chain that grows past its limit stops and asks.

9 · The process, as a skill: the descent

The method this page used, written so it can be taught and run again on the next tier:

#StepWhereDone when
1List the capabilities with their tierwhat comes firstevery capability has a definition and an example
2For each, name the object that carries itL2 vocabulary; a thing the model has no word for goes through the new-thing protocolno capability without an object
3Name the block that owns its mechanismL3 platformone owner each
4Name the primitive and the field that hold itL4 data model; mark it in canon, a new field, or a missing primitiveno empty cell; at most 1 in 5 unplaced
5Put it on the run loopcontrol flow: which step acts on itevery step has a capability; every capability has a step
6Walk one real case on paperone department, one day, through the loopthe walk touches every capability; every missing record is written down
7Cut the smallest slice that runsthe gap list becomes the walking skeleton; hand it to the builderthe slice's walk runs on a throwaway registry

The fields behind it: systems engineering's allocation of each requirement to one element, kept in a traceability matrix; event storming (Alberto Brandolini), which finds a domain's commands, events, records and actors by walking what happens; and axiomatic design (Nam Suh), which maps each functional requirement to one design parameter and flags a requirement that needs two. Confidence: high that each field works this way; moderate on the fit.

Capabilities become a running system by being carried down, not by being designed again. Each one lands on a record the canon already has, as one new field, or on the one record it lacks: the Artifact.
