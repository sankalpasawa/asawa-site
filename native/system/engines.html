How a unit runs: one engine shape BUILT BEHIND A SWITCH · NOT RELEASED · DECISIONS PROPOSED · v3

Every unit that runs in a department is an engine: the four that make the work, and the five functions that keep the department true to its charter. An engine is a skeleton of code around steps, and each step runs on the rung its record has earned, from a person, to a model, to code. This page is the engineering design that makes three ruled pages real in Core. Nothing on it is built.

The documents: holding/plans/engine-runtime/PRD.md (what the owner observes), HLD.md (the architecture, its twenty-one decisions, and the component that makes every engine the same), LLD.md (schemas, algorithms, twenty edge cases, and section 13, as built), ADHERENCE.md (every founder message with a check that can fail), RESEARCH-agent-communication.md (published practice, with sources). What runs today is on the first build.

2 · One engine shape

The skeleton is the same for every engine and is always code: it starts the run in its slot, reads what the engine names, writes a new version, keeps a row per step, resumes at the first unfinished step, and stays inside the envelope. What differs from engine to engine is the list of steps.

Three forms a step can take. The difference is who owns the loop. No engine is an agent: the skeleton is code and owns the loop; a step inside may use a model call, or an agent where it must look things up.

2b · How an engine starts

The founder, 2026-09-28: “start is just a button”; an engine “needs a trigger to start. Either the trigger is external or internal”, and starts “unless it has a blocker”; once started each has “their own internal agency to do things. That's the definition of autonomous systems.” The rule by which one engine starts is its activation. It is the same for the four work engines and the five internal systems. A word on words, ruled the same day: inside, in documents and code, the five are internal systems; on the screen, for users, they are functions. Published practice has the same shape under other names: an event-condition-action rule; in BPMN, a start event of kind timer, message, signal or condition.

What engines share is Coordination's

3a · The box: a covering of code, an inside of AI RULED 2026-09-30 (S-22, S-23)

The founder's shape for crystallization, ruled 2026-09-30: every engine, and every function (a function is an engine), is a black box. The covering is code and does the bookkeeping; the inside is AI and does the thinking. The same shape holds at two levels: an engine is a box whose inside is a row of step boxes. At the start every inside is AI only; a box climbs the ladder to code one step at a time, as its rows earn it. Sections 3 and 4 below are read through this: a rung is the inside of one step box; a gate is covering, never an inside.

The box at two levels. Green is code, the covering; amber is AI, the inside. The four step boxes show the ladder: F (AI with a prompt, where every step is born), A (AI holding the box's code, later), C (code, the top).

Engine boxStep box
inputwhat it reads (an artifact version, a post), its trigger and blockerswhat the step before handed it, typed
insidethe row of step boxes: the workflowone of F (AI with a prompt), A (AI with the code), C (code)
outputthe version it files, with the checkthe value handed to the next step

The five rules

#RuleWhy
1The covering never changes hands: input typing, the check and the row are code, whoever runs the inside.the record's invariants hold whatever the inside does
2Each step box has a setting: its inside (F / A / C) and who may move it. The setting is data on the skeleton, not code.the setting is the crystallization
3Born AI only: every step box starts F. Nothing deterministic lives in an inside; the gates, the spend count, the sample pick, the checks, the filing and the triggers are covering.S-09, S-22
4The ladder goes F to A to C, never skipping: F runs repeat and pass, Adaptation drafts the code, A trials it (the model may still deviate and says why), when deviations stop the box goes C; a failed check moves it back one.crystallization is earned by rows, not declared

Against sections 3 and 4 below: the rung C1 (checklist) folds into F, a prompt is a prompt (founder 2026-09-30); the "code from birth" expectations in section 4's table are coverings under this design, not insides; the three inputs of section 4 (determinism, frequency, stringency) stay the test for a move up the ladder. The component in six parts: type = a step with a covering and an inside; contract = rule 1; growth law = rule 4; record = the row and the setting; surface = the step on the function's first tab with its F / A / C mark; proof = a box whose inside is swapped F to C gives the same output on the same input, and a malformed inside is refused by the covering.

4 · When a step becomes code

Never the function; a step of it. Three things must hold, which are canon's three inputs. When all three hold, the next rung runs beside the current one as a trial, Adaptation proposes the move with the numbers, and the owner stamps it. When variance rises again, the step moves down one rung with no stamp.

InputHolds whenRead from
Determinism, the gatethe answer is one of a closed set, and the same input gave the same answerstep rows: outputs that differ, per input
Frequency, the triggerit runs often enough that a call each time costs more than hardening itstep rows: count, cost
Stringency, the carethe proof the charter asks for at that step's risk is in handthe charter; the trial's agreement

The five functions, read by the nature of their steps. These are expectations; canon says where a step lands is read off the record.

FunctionIts gate stepsIts slot stepsExpected
Coordinationin progress, lock, chain, who may post to whomcarry an alarmcode from birth
Prioritythe enveloperank the due slots; answer a proposalcode, except ranking and the bargain, which harden into a table
Identitythe rules: go, ask, refusejudge a request against the goal; close an exchange sent to itthe gate is code; judging starts soft and hardens as the same asks return
Adaptationnonecount from the rows; keep the ladder; write one proposalcounting and the ladder are code; writing a proposal stays soft
Auditnonepick what to sample; mechanical checks; judge a page against the briefpicking and mechanical checks are code; judgment stays soft

A gate is asked on every admission, inside the motor's tick, so it must be on the code rung. A gate that is not answers “wait” and runs in a slot of its own. A model call never sits inside a tick.

5 · How two functions speak

The founder's open question, and his answer to it: a message board. One board per department, kept as a record. It is the shared thread recorded on 2026-09-20 (NAT-THREAD-1), not a group chat: a post names who it is for and wakes only them; nothing is broadcast. Each engine has its own agent, its soft side, and agents never speak to each other directly.

QuestionAnswer
Where do engines speak?on the department's one board, an append-only record; an inbox is the posts addressed to one engine
Does each engine have its own agent?yes, one each: a card that says who it is, its skills, the department's rules and, for a function, the template it runs; a code step does not use it
Do agents talk to each other directly?never: an engine posts, the post names who it is for, only that engine is woken
What does the woken engine do?runs one step: code if it has a rule for that kind of post, its agent if not; then posts its answer in the same thread
What stops a runaway?four hops, a time limit, a spend limit, one decider per thread, and the outcome that holds when a limit is hit
Where is the owner?reads the whole board; speaks through the one box; stamps and refuses; the owner's posts always pass. Pause and mute are not built

An edge hardens like a step. An exchange that ends the same way each time becomes a default, then a row in a table with no exchange at all. Canon names the four kinds of edge (observed, suggested, default, hardwired); that sheet is proposed, not ruled.

5b · How a person speaks to a department

One box. The owner never sorts his own words: Identity's first soft step recognises which of the five journeys they are, and each journey has its own steps after that. A new goal is a directive on the goal line. Words that are none of the five go back to the owner as one question. Besides the box, a person has four more acts, all on the department's screen: stamp or refuse an ask, hold a step on its rung, stop or resume the department, and read the Board.

Why a directive and lasting feedback are always put back: a wrong recognition would send words down the wrong path. What would change how the department works from now on is restated in the department's own words and kept only on a stamp.

Purpose

Workflow and Engine are one rung of the ruled ladder seen from its two columns. A Workflow is the WRITTEN blueprint — an authored, stateless artifact composing 1..n Work-Atoms with a pattern and a failure policy. An Engine is the GROWN form of that same workflow — the workflow plus everything it has accumulated by living: state envelope, record slice, learned patterns, and charter binding. The distinction exists because of two axioms ruled by the founder (2026-08-05/06): X1 no naked work — whatever is worked on always has a workflow, a single atom being a workflow of one — and X2 no stateless execution — every run executes inside an engine, born at its workflow's first run with an empty record slice. You author the written half; only the grown half runs. See the hub diagram for this rung in the full ladder.

How it works

One object, two columns — never conflate them:

HalfColumnDefinition (RULED, A1 family)StateStorage
WorkflowWRITTENStateless blueprint: 1..n atoms composed; steps, pattern, failure policynoneWorkflow primitive — unchanged

The written half: authoring and FOLLOW

  • A workflow composes 1..n Work-Atoms. Canonical owner of the atomicity rule (one goal, ONE verify): Work-Atom — this page depends on it for the split test.
  • Workflows are reached through the loop's resolution edge: a matching workflow type is FOLLOWed; none found means CONSTRUCT builds the skeleton. Resolution is child-custody-wins (ADR-026).
  • A workflow becomes FOLLOW-able through the reuse_tag C0→C1 promotion — the only crystallization step that is canon today. Paths earn the workflow-type noun by repetition.
  • Per X1 the FOLLOW/CONSTRUCT spine is total: nothing dispatches outside a workflow.

The grown half: engine birth and the four state stores

An engine is born at its workflow's first run, with an empty record slice (X2). From run 1, every run writes to some engine's record slice. The engine's statefulness is exactly four stores — a name over things that already exist, never new storage:

StoreScopeHolds
State envelopewithin-runthe live run's working state
Record slicedurable, cross-runthis workflow's slice of the record — history of runs, artifacts, corrections
Learned patternsbehavioral (B5.d)lessons that change how future runs behave
Charter bindingpolicywhich charter's constraints and authority bind this engine's runs
Engine-Library rule (RULED, A1): an engine's statefulness must be EXPLICIT inputs from the record — never hidden internal state — or crystallization to C2 code breaks. State you cannot point at in the record is not engine state.

Run 50 differs from run 1

The real proof is W-md-authoring (decision sheet §8c). On 2026-08-05 the founder ruled that diagrams in md files use mermaid, not ASCII art. That correction landed once — in the Md-Authoring Engine's learned patterns — and changed every future doc. The engine is the workflow (outline → author → audit) plus its record slice (docs + founder corrections) plus learned patterns (mermaid-not-ASCII, tables-over-prose, hub-and-spoke) plus its charter binding. Run 50 ≠ run 1, provably — and the written workflow file never changed.

Attempts are not objects at this level — canonical owner: Work-Atom s5 (attempt log = data field on the HOW particle); the retry budget reads that field.

Invariants

  • X1 no naked work — nothing dispatches outside a workflow; a single atom is a workflow of one.
  • X2 no stateless execution — every run executes inside an engine; the engine is born at the workflow's first run with an empty record slice; every run writes to some engine's record slice from run 1.
  • Engine-Library rule — engine state = explicit inputs from the record, never hidden internal state; violation breaks C2 crystallization.
  • No new storage — Engine is a name over the four existing stores.
  • The written half never mutates at run time — all accumulation lands on the engine; the workflow file stays a stateless template (A1-ext grid).
  • Distribution ships templates only — instances and state never leave the tenant (A1-ext consequence; D33 in one sentence).
  • One goal, ONE verify per atom — canonical owner: Work-Atom (A1-ext).
