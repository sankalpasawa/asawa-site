Block — Authority + Tenancy — the GOVERN wrap PLATFORM · zoom 3

This page is one view of the single loop (overview: the system, simply). The loop is INTENT → SHAPE → RUN → RECORD → EVIDENCE → GROW → write state back → next INTENT. This block OWNS GOVERN — authority over every transition in that loop. Not a stage; the wrap drawn around all of it. GOVERN decides auto | ask | deny at every gate, and crucially it gates the four write-backs that Evolution makes when GROW reads the record — harden the dispatch, scale the shapes, codify the catalog, delegate cross-unit. Authority also owns the "accept" half of verify: the executor asserts done; a counter-party accepts (a human via Approval, another tenant, or a parent workflow), gated here. The boundary this page sits on is RECORD → EVIDENCE → GROW — the record becomes evidence the moment it is read across runs, and GOVERN is what authorizes the write-backs that evidence triggers.

1 · What GOVERN owns in the loop

Need. A feedback loop for work spends real things and touches the real world — money, messages, other companies' data, its own core rules. Left ungoverned, an autonomous loop will at some point send the wrong thing, spend past a threshold, leak across a tenant boundary, or rewrite the rules it runs under. Advantage. Native does not bolt approval on as an afterthought hook — authority is a wrap the whole runtime runs inside, and Approval is a first-class primitive (ADR-009), so the same gate logic covers a Slack message, a $-spend, a cross-tenant read, and a self-modification attempt, with one audit trail behind all of them.

GOVERN is not a stage; it is the wrap. The loop's doing-stages are SHAPE → RUN → RECORD → EVIDENCE → GROW. GOVERN sits around all of them and fires at every transition between them — auto (let it pass), ask (hold for a counter-party), or deny (a hardstop). The page diagram below draws this as a border, not a pipeline box, on purpose.

2 · Authority over the four write-backs (the GROW → loop arrow)

The most important transition this block governs is the one that closes the loop: when GROW reads the evidence and writes an improvement back into the running system. Evolution makes exactly four such write-backs (one per GROW axis). Authority is the wrap that forces auto | ask | deny on each one — not just on the per-action gates further down. A change to how the system runs itself is a higher-stakes act than a single send; the four columns below are where this page's authority does its heaviest, most distinctively-Native work.

How it flows internally

Every access entering the wrap is classified by the D.6 six-dimension Authority Model (domain · tool · stakeholder · dollar · reversibility · confidence), then run through the F.5 ask-vs-act cascade (irreversible → high-risk → new-authority → first-time-channel → else ACT-and-report); any ASK outcome is realized by the approval-gate primitive (ADR-009), which surfaces the prompt up through UI carrying its F.2 reversibility tag so a counter-party can accept, while the gated workflow inside System of Process holds in PAUSED or ESCALATED until the decision flows back down. In parallel, the tenancy half checks every System-of-Record touch against the ADR-006 Domain field, with HS-3 default-denying cross-tenant access lacking an explicit delegates_to edge; denials surface via the hardstop UX contract (WHAT + next action + audit-row link). Operator responses ("grant always", dial up/down) feed the F.4 trust ladder, which shifts future cascade outcomes from ask toward auto over rungs 1-4. The same machine governs the four GROW write-backs (§2): a HARDEN, SCALE, CODIFY, or DELEGATE proposal is just another access through the cascade, with HS-1 denying any CODIFY-to-doctrine that would self-modify core rules. Every decision through the gate writes a DecisionProvenance row onto the RECORD; the F.3 replay surface reads that trail back as EVIDENCE on demand, and the §1.5.1 guard tooling enforces the same contract at action-time as HARD/SOFT blocks.

Operator-facing governance UI — the Platform UI Kit (ADR-023)

The wrap is not only enforcement — the operator needs to see it: which domains and subdomains are running, what each charter promises, and what is waiting on their approval. Per ADR-023 this is solved without a new §1.0 block, by two additions: (1) an Exposure Contract — a cross-cutting facet each block declares (what of it is operator-visible, as read-only projections); (2) a Platform UI Kit — a Layer-A render library whose components render those projections inside the UI block’s Receive part, read-only, gated by this very wrap. Components are not Modules; Modules compose them (Charter Console = Charter+Domain Browser + Approval Inbox). The Approval Inbox is where the human counter-party sees what is waiting on the "accept" half.
