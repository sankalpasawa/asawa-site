0 · This page IS one stage of the loop

Native is one feedback loop for work: an intent is shaped, the atoms run, every run is recorded, the record is read as evidence, and that evidence grows the work — which writes state back so the next run starts better. This page is that GROW stage. Everything below details the back half of the loop: the record→evidence boundary it begins at, the growths it runs, and the four write-backs it closes through.

The same loop as the system, simply — here the GROW box is opened up. The record→evidence boundary is the moment a written run is read across runs; that evidence drives the growths; each growth writes state back. Authority wraps every step, including each write-back.

1 · The record → evidence boundary (where GROW starts)

The record is raw; evidence is the record read across runs. RECORD just writes down what happened (every atom, run, and resource-debit). GROW begins the moment that record is read as evidence — counts, variance, outcomes over many runs — the read-model form that tells you a step is stable, a practice is repeating, a system is straining. Nothing grows off a single run; it grows off the evidence the record becomes. This is the upstream boundary of this page; System of Record owns the raw write, Observability exposes the reads.
Why a boundary at all: it is the Good-Regulator hinge — the record is the system's model of itself, but only once it is read back does that model regulate the next run. Reading a single run is not evidence; reading the accumulation is. (Refinement from the codex two-deep review: the loop is RECORD → EVIDENCE → GROW, not RECORD → GROW directly.)

2 · The four write-backs (where GROW closes the loop)

GROW is not advice — each growth writes state back into a specific place, so the next run is materially different. These four write-backs are how this stage closes the loop.

Two of these grow in different directions at once. SCALE (Maturation): does a pile of work become a self-governing System? SUBSTANCE (Crystallization): does one unit harden from soft thinking into frozen code? Orthogonal — big-but-soft or small-but-hard are both possible; a mature B2B product is high on both. Two separate ladders, not one. Up the left = bigger + self-governing (writes back to the shapes); up the right = harder material / code (writes back to the dispatch). You can climb either without the other.

The logical flow — how one piece of work evolves

A unit runs soft, the record (read as evidence) proves whether it's stable, then it can harden (substance → dispatch) and/or the system around it can scale (scale → shapes). The two write-backs are independent and can both happen. This is the same RUNS-SOFT→PROVES-OUT→HARDENS arc as the medium walkthrough in the system, simply.

Codify — the codification ladder (its home is here)

Need: a good practice silently hardens from a one-off into fleet-wide doctrine that nobody may re-decide; Native has no way to name, measure, or govern that hardening. What it buys: you can read, at a glance, how binding any practice is — and there's a path to demote one that stops earning its keep. Each rung up costs more evidence + higher sign-off; the codification is the practice itself, not whether it's run by an LLM or by code (that's the separate Substance axis). As a write-back: a climb commits to the FOLLOW catalog — the next run finds the practice as a workflow-type it can follow, not reinvent.

Forward: a practice climbs only as evidence + authority justify it, committing to the FOLLOW catalog. Counter-flow: when a rule stops holding (rising variance, failing outcomes, a stale date), it's demoted one rung and re-opened — the thermostat runs both ways. This is the axis the word "Evolution" was hiding.

The mechanism underneath — and a warning

Composition is the mechanism, not an axis or a family. "atom → workflow → workflow-of-workflows" is the composition / recursion mechanism every family rides on — it lives in the Workflow section as "composed." Cross-unit is its sibling seen sideways: same-owner depth = composition; different-owner width = cross-unit (the tenancy boundary separates them), which is why cross-unit reads as a slice of Scale and writes back to who-may-call-whom. Honoring canon: Native does not lack composition — it carries 5 composition laws + the VSM metasystem (see corrections below); the website pages just under-surface it.
OPEN founder decision — do NOT canonize "3 orthogonal axes." An 8-agent grounding (run ws8dp6s5r) found the frame is 2 real axes + 1 mechanism + 2 hidden axes, not three — which is exactly why this page reframes them into the loop's families instead of a flat list. Canonizing three would be the "5-dials trap" again. This is applied known science, confirmed — not discovered.

Honest scope — what this stage does and does not promise

  • Productization, not implementation. Schemas, thresholds, solvers, and simulators are the implementation layer — deferred.
  • GROW models the work graph + its evolution — NOT on-time or stability guarantees. A fully-verified, fully-grown atom set can still miss a deadline (schedule) or oscillate (dynamics); the docs must not imply otherwise. TIME is carried as an axis (the critical-path idea + the oscillation warning), not as an engine in v1.
  • Every write-back is proposed, never auto-built. What exists today: Maturation's S1 auto-grows; Crystallization's C0→C1 reuse; the auto/ask/deny approval gate. Everything else is design-forward.

Output looks like

The persisted artifact of one GROW turn is a write-back record: a proposed change, its gate decision, and the state it committed — landing in the target each row of the write-back table names (the dispatch, the shapes, who-may-call-whom, the FOLLOW catalog). Under ruling #2 the evidence it reads is the Engine's record slice.
