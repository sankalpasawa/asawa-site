The whole stack in one picture

Each level is made of the level above it, plus one new thing. The atom is the smallest doer; the chain is the biggest whole. Same idea all the way up.

1. Workflow = a recipe

A workflow is one job written as ordered steps. Each step is a Work-Atom (one action). The workflow is the sequence, plus what starts it and what to do if a step fails.

Each box is one Work-Atom. The dashed box around them — the recipe — is the Workflow.

2. System = jobs + the glue that holds them together

A pile of jobs is not a system. A system = the jobs (workflows) plus the glue that makes them act as one: coordination, priority, checks, and a sense of what the whole is for.

The jobs (workflows) sit inside; the glue band on top is what turns a pile of recipes into a kitchen. Remove the glue and you just have loose recipes — not a system.

3. Recursive system = the same shape nested inside itself

Recursive means a system made of smaller systems, made of smaller systems — the same shape at every zoom level. Like nesting dolls.

Every box has the same shape (a system = jobs + glue) — just bigger or smaller. You design the shape ONCE and it nests. That's "recursive."

4. How workflows and systems connect

A workflow does one job. A system is many workflows + the glue — and one of its slots can itself be a smaller system. Nobody inherits; each level simply contains the level below and adds its own glue.

The system's work-layer is its workflows (and/or sub-systems); the glue sits on top. A workflow holds atoms; a system holds workflows + sub-systems. Pure containment — each thing has the smaller things, none is a kind of another.

5. Closed taxonomy = a fixed menu of kinds

A taxonomy sorts things into named kinds. Closed means the list is fixed — you can't add a kind without deliberately changing the system. The win: the system can be sure it handles every option, and adding one is a visible decision. Open = anyone can invent new kinds anytime — surprises the system can't pre-handle.

Native's closed menus: failure_policy = 5 · stringency = 3 (process/directive/principle) · EngineEvent types = 26. Each is a fixed panel: the system handles every kind, and adding one is deliberate. That's why these are modelled as fixed sets, not open class trees.

6. The frame: Domain + Charter wrap the work

SUPERSEDED by A1-FINAL-2 (RULED 2026-08-06). The "frame wraps the work" language below is the earlier model. The ruling: only SYSTEMS exist — the charter is a PROPERTY of a system (one-directional: only systems have charters), Domain names the standing-system tree, and tenancy design is deferred. Cross-cutting rules are the charter of a shadow system. Current model: The Model. Kept below for trace.
Domain and Charter are not rungs on the ladder — they are the frame the work runs inside. Domain = the scope (which company / function / project, + that area's principles). Charter = the rules/authority (what's allowed, how strictly, what happens on override; fixed or flexible). Every workflow/system runs within a Domain, under a Charter.

The work is WHAT gets done; Domain is the scope it's done within; Charter is the rules it's done under. This is the §1.0 Authority + Tenancy wrap — Domain ≈ tenancy/scope, Charter ≈ authority/rules. Both nest in parallel with the work: a company-Domain contains department-Domains; a broad Charter is narrowed by stricter sub-Charters.
