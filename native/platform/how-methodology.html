One sentence (theory). Every piece of design knowledge is a "way of looking" (a Lens). There are many possible lenses (axes), not capped to any number; the two recommended ones for building anything are Realization (abstract idea → running thing) and Reflection (instance → axis → meta-axis → … → grammar). You don't have to use all axes — you pick the lenses a destination actually needs. This section is THEORY work; productization is the next step.

§3.1 The atom — a value is just an axis

The smallest move is classification: a value is an item; an axis is a set of values. The role is RELATIVE to level — same thing is a value seen from above, an axis seen from below:

  a thing is a VALUE   seen from the axis above it
  the same thing is an AXIS    seen from the values below it

"Value" and "axis" are the same kind of object viewed from one level up or down. This is the only primitive; everything else is this move repeated. (Formal grounding: type-universe relativity; Tarski's object-language / meta-language stratification.)

§3.2 Axes — many possible, two recommended

An axis is a particular Lens — one way of looking at the thing being built. There can be MANY axes (viewpoint · concern · time · ownership · scale · certainty · …). You are not capped to any number. You pick the lenses that change a decision for this idea and ignore the rest. The two recommended for every idea:

AxisNameMeansExample values
Axis 1Realizationabstract idea → concrete running thingworldview · vision · strategy · capability · architecture · feature · contract · implementation
Axis 2Reflectioninstance → axis → meta-axis → method → framework → paradigm → grammar (the recursion, uncapped)M0 instance · M1 axis · M2 meta-axis · M3 method · M4 framework · M5 paradigm · M6 grammar

Other available lenses (add any per idea, only if it changes a decision): viewpoint (user / system / governance) · concern (security / cost / accuracy) · time (past / now / next / later · v1 / v2 / v3) · ownership (human / AI / human-in-loop) · scale (fleet / cohort / instance).

Coupling (how the two recommended axes interact): as you ascend Reflection to mint a structure (an axis, a schema), the forward Realization journey then consumes that structure instead of re-deriving it. Climb to write a schema once; descend and every instance conforms. The abstraction is carried forward as an input, not copied.

§3.3 Dynamic — nothing is capped

The number of Realization levels and Reflection heights is not fixed. It is decided per idea.

  • Dimensions are generated, not listed. Each dimension = (interrogative × mechanism) — a finite generator mints an open set on demand.
  • Realization stops by atomicity (downward): you stop decomposing at the smallest buildable unit.
  • Reflection stops by reflexivity (upward): you stop climbing at the level that describes itself.
  • Both stop by the decision test (the practical cap): add a level or a dimension only while it still changes what you build or who reads it.
Possibility is not obligation. The space is astronomic; you instantiate only the corner a destination needs.

§3.5 Making decisions with Lenses

A decision is choosing which lens to apply; a good decision is one that changes the path to your destination. The framework's biggest gift is telling you which decisions you do not have to make yet.

 DECISION PROCEDURE
 1. ANCHOR    name the destination. No destination -> no decision.
 2. ON-PATH?  if the decision isn't in the destination's required
              sub-graph -> DEFER. (Most "decisions" die here.)
 3. LEVEL     find the decision's level/dimension -> pick the matching
              LENS. Decide architecture with the architecture lens,
              not the implementation lens.
 4. REAL?     do the options lead to DIFFERENT downstream sub-graphs?
              If not -> not a real decision. Pick either, move on.
 5. WEIGH     reversible -> decide fast, revise later. Irreversible ->
              apply MULTIPLE lenses (viewpoint/concern/time); where the
              lenses DISAGREE is the actual tradeoff to resolve.
 6. RECORD    node + provenance: destination, lenses used, choice, why.

Worked decision — "B1 classifier: single LLM call vs fine-tuned model?":

StepApplied
1 Anchordestination = ship B1 intake (v1)
2 On-path?yes — the classifier is in B1's closure
3 Level / lenscomponent decision-level (master labels this "L3-component" — a change-cascade decision-level per holding/HIERARCHY.md, NOT a zoom band) + AI lens — not a strategy decision
4 Real?yes — fine-tune pulls in a whole data+training sub-graph; single-call doesn't. Different paths.
5 Weighreversible-ish (the intent{} contract is unchanged either way) → lean decide-fast. Lenses: cost (fine-tune expensive), time (single-call ships now), accuracy (eval lens: spike hit 17/20 ≥ threshold). Lenses agree → single-call for v1.
6 Recordprovenance: chose single-call; lenses [cost, time, accuracy, reversibility]; revisit if eval pass-rate drops below 90%.
Eliminates: off-path agonizing (step 2), false decisions (step 4), wrong-level thrash (step 3). Adds: effort calibrated to reversibility (step 5), multi-lens only for the genuinely hard ones (step 5), replayable rationale (step 6).

The science underneath — unit → work → record is a real discipline

The method this page describes is not an invention; it is a convergence. Five fields built independently over ~70 years — process science (van der Aalst), transaction processing (Gray–Reuter), event sourcing/DDD, operations science (Toyota/Goldratt/queueing), and cybernetics (Ashby/Beer) — land on the SAME falsifiable structure. That independent derivation of isomorphic results is the signature of a science, not a bundle of methodologies.

Every field derives the same invariant triple: (1) a Unit = bounded work with an explicit contract (= Native’s Step: pre-declared output + post-check); (2) Composition operators safe only when contracts are explicit — nesting is safe by theorem, message-interaction is not; (3) a Record the system can be rebuilt from (replay) or rediscovered from (mining). The founder’s three questions answer cleanly:

QuestionAnswerNamed result
system out of a record?close a loop on it — replay, mine, or regulate itα-algorithm (2004)
system of work?contracted units + named patterns + soundness check + loop foreverworkflow-net soundness (1998)
system out of a unit?units become S1 of the next level + a metasystem no unit containsBeer Recursive System Theorem (1979)

The loop — design → execute → record → compare → redesign — has a theorem at each edge. That is what makes Native’s methodology a discipline, not a style. Canon (linked, never copied — D54): research holding/research/2026-06-12-unit-work-record-science.md · the loop’s mechanisms at ADR-022.
