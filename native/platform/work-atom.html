The Work-Atom — the generative unit + adaptive workflow PLATFORM · zoom 4

ARCHIVED (v2) — this page predates the ruled model (WRITTEN Work-Atom→Workflow→Assembly / GROWN Engine→System; 4th particle = HOW). Kept for history; the ruled account lives at The Model.
SUPERSEDED (2026-08-07) — this page is an archive. Its content now lives in The Model and its PRD cluster (Workflow + Engine · Work-Atom · Particles · Assembly + System · Internal System). Remaining pieces (coffee-era diagrams, Method §3 detail, stringency cascade) migrate at the S5 pass per the decision sheet §9b — read there, not here.
STATUS: PLANNED · v2 · NOT BUILT. This page defines the generative unit (the smallest atomic dispatch — though recursively expandable: a step can call a sub-workflow, so "smallest" = atomic, not size-bounded), plus the adaptive workflow nuances. Most of this maps to canon — but it is not all derivative (peer review corrected an earlier "no new invention" overclaim; see the review block). Design-forward; runtime build follows the canon route (D54) when ratified.
Dual-lane peer review — 2026-06-14 (codex + deepseek): CHANGES-REQUIRED, corrections applied. Both lanes flagged "no new invention" as false. Genuinely new: System primitive · 6-detector EMERGE extension · S4 second-order loop · outbound comprehension · universal deepen-UI · comprehension-memory. Must be solved before any build: (1) the adaptive router is a taxonomy, not a runtime algorithm (no decision procedure: inputs/thresholds/confidence/tie-breaks/override; Cynefin auto-classification is unreliable); (2) determinism — the constructed step must be content-addressed (snapshot) or replay+audit break; deterministic prompt assembly does not make the stochastic LLM core deterministic; (3) the miner/maturation has no rollback model, verification, or impact-analysis safety envelope; (4) no halting/resource bound on recursive multi-instance workflows; (5) comprehension-memory needs privacy/tenant-isolation/consent + a transactional link to the execution trace. A · The Work-Atom (the 5 blocks)

RULED 2026-08-05 — particles, atomicity, Attempt (supersedes this section's naming). The canonical ladder is Particles → Work-Atom / Attempt → Workflow / Engine → Assembly / System — full ladder + axioms on Work structure. On THIS page: the atom's inner blocks are the four particles (read the diagrams' "WORK / dispatch" as means; the 5th block, Workflow, is the recursion edge, not a particle). ParticleQuestion it answersDefinitionThe test
goalWhat does done look like?a target state of the world PLUS the check that detects it; terminates the Attempt on verify pass; ONE goal per atomif you can't write the verify, you have a wish, not a goal

Atomicity rule (RULED): an atom is atomic in ACCOUNTABILITY, not size — one goal, ONE verify. It may hold 1..n internal steps (one bare LLM call, one call + a skill, or several moves), but they share the atom's single goal, context and verify. The moment an internal step needs its OWN verify, it is not a step anymore — split it: two atoms in a workflow. A live run of an atom is an Attempt (attempt 1..N against the Charter's retry budget). An Engine is NOT a run: it is the workflow plus its record slice + learned patterns + Charter binding — it behaves differently on run 50 than on run 1.

B · The adaptive router — different problem types go different ways PROPOSED

PROPOSED — not a prior conclusion (verified 2026-06-14). The "adaptive router" + "5 workflow dials" framing below was introduced in the June 2026 render, not concluded with the founder (absent from all ADRs / charters / directions). The individual knobs are real canon (see mapping table); the router-with-5-dials packaging is design-forward, needs an ADR. Now defined above this router (ADR-026): a Stage-0 classifies input TYPE (task / question / direction / feedback / concept) and resolves a workflow type (child custody → platform); this router's axes are then the inner engine that shapes each step, run whether the steps were followed or constructed. See Flow §0.

Native's IP (HOW §3): not "do the work" — "do the work via the right way of looking at it." The three axes classify the problem; the classification sets the five dials; the dials shape the workflow the atoms run in.

The Cynefin method-shapes — the certainty axis, drawn

The certainty axis routes to a shape: Clear → fixed sequence (the part you can harden to code); Complex → declarative (stays LLM-led). Patterns from the workflow-patterns catalog (research §3) build the step_graph.

Fires & feeds — what starts a workflow + what feeds its context

FIRES: a Trigger (utterance · cadence/cron · event) starts a workflow. FEEDS: context is assembled from 7a + B6 + SoR + Domain/Charter into the deterministic prompt (B11) the atom runs on. Both sit upstream of every atom — this is group 2 of the workflow nuances.

C · Two lifecycles, not one — the task clock vs the workflow ledger

These are TWO orthogonal machines. C1 (task lifecycle) is the execution clock — the phases the work passes through as it runs. C2 (workflow state machine) is the governance ledger — the approval state the workflow object sits in. A task walks all 8 phases of C1 while its workflow record sits in a single state of C2 (usually ACTIVE). Earlier this page stacked them in one box, which read as one machine — split below.

C1 · Task lifecycle — the execution clock (8 phases, D30a / 7d)

SHAPE = frame → decompose (ADR-025): pick the lens/POV, then B2 splits along it. 8 phases is canonical (D30a / 7d). The 9th ORIENT once shown in master §10.1 is not a separate phase — it is the FRAME sub-move now folded into SHAPE (ADR-025). One clock, eight stations, looping.

C2 · Workflow state machine — the governance ledger (§4.2)

The workflow object's approval state — orthogonal to C1. The whole 8-phase task clock (C1) turns inside the ACTIVE state here. ACTIVE = approved + runnable; the agent materializes per run; PERSISTED once it has run and been kept; RETIRED on revoke. (runtime §4.2.) Full end-to-end thread of both: Flow.

D · Composition + recursion (how one atom composes outward)

A Work-Atom composes into a Workflow; a Workflow can tag itself reusable (→ a Skill); workflows nest (Workflow-of-Workflows) and reference each other (interfaces_with). Seed one atom with goal="build Native" + this design doc as context → in principle it decomposes recursively toward the whole system — but full self-construction is unproven and gated on the open problems above (router, determinism, safety, halting). This is the maturation loop seen from the bottom.

Proposed resolutions to the open problems (design-forward — proposed, not built)

Per the dual-lane review: four of the five problems bind to mechanisms we already have; only a few small new pieces remain. None of this is built or canon — these are proposed design answers.

Determinism / replayAdopt ADR-022 #1 (SoR-truth-upgrade): content-address the constructed step (snapshot prompt+inputs → hash); persist the LLM output AS an event; replay reads the recorded output, never re-calls the model.already on the maturation roadmap (ADR-022 #1)

Bottom line: bind each problem to its mechanism, spec the four small new pieces (router confidence+fallback · recursion budget caps · shadow-run+compensator · explain-from-trace), and let the bootstrap prove out on L1 (regenerate the docs/website) before any canon is written.
