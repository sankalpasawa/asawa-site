This page is the FRONT half (SHAPE · RUN · RECORD). The back half — reading the record across runs to improve the work and the system — is the Evolution view. They meet at one named boundary: the record becomes evidence the moment it is read across runs, and evidence is what GROW consumes.

The Workflow section — what a workflow consists of

A workflow is the whole; running it is the Flow (this page) — i.e. one turn of the loop's FRONT. Top-down, a workflow consists of:
  • Work-Atom — the unit at each node (a 5-block step). The thing that RUNs.
  • Method §3 — how it's shaped (the lens). The thing that SHAPEs.
  • Work structure — how steps compose (atom → workflow → system). Native has real composition — 5 composition laws + the VSM metasystem (see the overview §8); this is where it shows.
  • Company decomposed — a whole workflow taken apart (worked example).
The sibling Evolution section covers the BACK of the loop — how a workflow grows + hardens over time by reading its own record (the RECORD→EVIDENCE→GROW hand-off).

0 · The complete spine — classify, resolve a workflow type, then run (inner engine always on)

An input arrives → it is classified by TYPE → the system looks for a workflow type (a reusable Workflow / registered high-level guidance) for this work → if one matches it follows its steps, if none it constructs the steps — but either way, within every step it runs the inner engine (factors + lens + Cynefin + dials). Guidance constrains the outer steps; it never replaces the inner engine. This whole spine is the SHAPE → RUN → RECORD front of the loop — CLOSE feeds the back half (Evolution).

The fork (green FOLLOW vs orange CONSTRUCT) decides only whether the outer steps are given or built. Both drop into the purple INNER ENGINE band — factors + lens + Cynefin shape every step regardless. That is the founder correction (2026-06-14): a workflow type adds a mandatory outer skeleton, it does not switch the inner engine off. The dashed CLOSE step is where this front-of-loop view hands the record across to Evolution as evidence. Sections A–F zoom into the task path.

A · The master flow — start to end (the task path, zoomed)

Read top to bottom: one intent enters; method frames + decomposes it; the chosen workflow is the resulting step_graph; each atom owns one slice of the intent and runs the same construct→dispatch→verify pipeline; outputs become artifacts (the RECORD); artifacts close the loop — reading them across runs is what turns the record into evidence for Evolution. The atom is constant; only the shape varies by problem.

B · The keystone — intent is the whole, atom-goal is the part

This is why the pieces felt unconnectable — they sit at different scales of one object. Intent and atom-goal are the same thing (a goal); the atom-goal is intent narrowed. Method is the function that does the narrowing. The frame decides how it narrows (history → by-epoch · product → by-deliverable · technical → by-component).

C · The two clocks — the task lifecycle turns inside the ACTIVE state

"The lifecycle of a workflow of a task" is two machines, not one. The task lifecycle (8 phases) is the execution clock. The workflow state machine is the governance ledger of the workflow object. The clock turns inside one state of the ledger. Drawn as one nesting below.

One picture, two axes: the green ACTIVE state is the ledger; the 8 white boxes are the clock turning inside it. A task can walk all 8 phases (and loop) while the object never leaves ACTIVE. PROPOSED before approval; PERSISTED/RETIRED after. The MEASURE→OPERATIONALIZE→LEARN tail is where this front-of-loop view hands evidence to Evolution. (Split source: Work-Atom §C.)

The shape is not invented freely. G · Recursion — a step is a smaller problem (Mode 1 / 2 / 3 · the how-of-how)

The spine is fractal. When you reach any step and ask "how do I do this?", you run the same spine on it. The step resolves three ways — and the inner engine runs at every block, every level. This is the DOING-lens view of the loop: work-atoms shaping work-atoms (a step becomes a smaller workflow of atoms), the dual of the THINKING-lens (value⇆axis, §H) which shapes how each step is cut.

Mode 2 sub-workflow does the work (steps that produce the output); Mode 3 how-of-how designs the work (steps that produce a workflow). Mode 1 (atom) is the base case that stops the descent. Modes 2–3 are exactly "work-atoms shaping work-atoms" — the doing-lens at work.

The meta-ladder — how far the "how-of-how" can climb, and why it stops

The "how-of-how-of-how…" is not open-ended. It maps onto Method's Reflection recursion (HOW §3) — a fixed 7-rung ladder with a halting rule: stop at the rung that describes itself (reflexivity).

The killer that defeats infinite meta: you climb once for a novel problem, mint a method, tag it reusable — it becomes a workflow type, and every future instance hits the FOLLOW branch (ADR-026) with no re-climb. The how-of-how is how a platform workflow type gets born — which is itself a write-back into the FOLLOW catalog (a GROW move; see Evolution).

Meta levelThe "how" questionReflection rungResolves by

1how to do XM1 axisMode 1 atom, or Mode 2 decompose — most work stops here

Your "recursive risk" = the halting problem — bounded three ways: (1) reflexivity — you cannot climb past the rung that describes itself (HOW §3); (2) height-per-idea — you climb only as far as novelty forces; (3) climb-once-amortize — the meta-cost is paid once per problem class, then the minted workflow type is FOLLOWed forever. Every recursion must bottom out at an atom (Mode 1) or an escalation to a human (Authority gate).
Honest status. The ladder + reflexivity halt are canon-as-THEORY (HOW §3, FQ1 PROPOSED, zero-runtime-enforcement). The operational stop rule — how the runtime detects reflexivity / when it escalates — is unspecified. That detector is the same open "halting" problem the Work-Atom page flags. Mode 3 (how-of-how) is design-forward, not built.

H · The lens engine’s one primitive (value ⇆ axis) — nothing hard-coded inside the lens

Scope. "One primitive" here is scoped to the lens / thinking engine — the machine that decides how to cut a problem. It is the one thinking primitive, not a single total primitive for all of Native. Canon carries 10 typed primitives (Domain, Charter, Workflow, Step, Trigger, ExecutionResult, EngineEvent, Tenant, DecisionProvenance, Approval) — see the overview §8. This section is about the lens engine specifically.

Inside the lens engine, the axes (Realization, Reflection, the lens family) and the cross are not baked in — that would cap an open set. The lens engine hard-codes one primitive; everything else is minted as data. Per HOW §3.1: "a value is just an axis … this is the only primitive [of the lens engine]; everything else is this move repeated."

One move, three directions — the THINKING lens. The names are labels on instances; the cross is computed, not enumerated. (This is dual to the DOING lens in §G — work-atoms shaping work-atoms.)

Two lenses, one loop — the duality (per the spine). The system shapes work two ways: the THINKING lens (value⇆axis, this section) decides how to cut a problem — UP / DOWN / ACROSS on axes; the DOING lens (§G recursion) decides how to build it — work-atoms shaping work-atoms (a step becomes a smaller workflow). They are the same recursion seen from the two sides of an atom: the THINKING lens cuts the goal, the DOING lens runs the cut. Both run inside every step of the FRONT of the loop.

The generic data model — no names, no fixed cross (the lens engine)

Axis  = { values: Value[] }          // NO 'name' in the type — a name is just a label on an instance
Value = Scalar | Axis                // a value can be an axis  → the recursion IS the type

mint(interrogative × mechanism) → Axis     // axes are GENERATED on demand, never enumerated
pick(axes, test = "changes what-you-build or who-reads")   // the decision test
cross = product(picked_axes)         // computed at runtime — never a fixed grid

stops:  atomicity (down)  ·  reflexivity (up)  ·  decision-test (across)

The axes are open — minted, not enumerated

The lens engine’s axes are an open set: any operator can mint a new axis on the fly (interrogative × mechanism), kept only if it passes the decision test ("changes what-you-build or who-reads?"). Only the core author reworks the closed family skeleton, and only after the system surfaces that real usage outgrew it. Families = closed skeleton; axes = open, minted flesh. Full rule on the open-axis page; the family catalog + sorting test on axes + families; how any minted axis becomes product on axis-productization.

The record → evidence → grow boundary — where this view ends

This page’s edge of the loop. The FRONT (SHAPE · RUN · RECORD) ends at the RECORD. The record becomes EVIDENCE the instant it is read across runs (the read-model form), and evidence is the input to GROW. Two refinements (from the codex two-deep review): (1) the loop is RECORD → EVIDENCE → GROW, not RECORD → EVIDENCE → GROW directly — evidence is the read-across-runs form; (2) verify’s "accept" half is owned by a counter-party — a human (Approval), another tenant, or a parent workflow — gated by Authority; it is not the executor grading its own homework. GROW — and the write-backs it makes (harden a step to code, codify a path into the FOLLOW catalog, grow coordination into a System) — is the Evolution view, not this one. The two write-backs this FRONT view participates in: (a) artifact → next atom’s context (within a run), and (b) record → evidence → next intent’s shaping (across runs, via GROW).

The named seam of the single loop. This Flow view writes the RECORD; the Evolution view reads it as EVIDENCE and runs GROW. Authority (GOVERN) wraps the hand-off — the "accept" half of every verify is a counter-party decision, gated auto / ask / deny.
