Maturation — how the daemon grows a System PLATFORM · zoom 4

This page is ONE VIEW of the one loop — the SCALE axis of the GROW stage. The loop is INTENT → SHAPE → RUN → RECORD → EVIDENCE → GROW → write-back → LOOP, wrapped by GOVERN. GROW is where the system reads its own record to do better next time. SCALE is the one GROW axis that grows the shape of the operation: it READS recurring pains from the RECORD and WRITES BACK the SHAPES available — the same write-back the overview names ("a pile of workflows grows coordination → a System"). Everything below details that one read → write.

The 2026-08-05/06 sitting ruled the model this page is built on: System = engines + glue engines (glue functions — coordination, priority, audit, adaptation, identity — ARE engine types, WHAT-WE-DECIDED.md #3) and only systems exist (frame collapse, #15). Definitions live at The Model (ruled) · Assembly + System · Workflow + Engine.

Where SCALE sits in the loop — the read-write this page owns

The record→evidence boundary: SCALE does not read the live run — it reads the accumulated record across runs, the moment of which turns the record into evidence (the read-model form before GROW). The write-back this page participates in is to the shapes available — it grows what SHAPE can reach for next time, never the live atom. Sibling GROW axes write back elsewhere: SUBSTANCE → the atom's dispatch; CROSS-UNIT → who-may-call-whom; CODIFY → the FOLLOW catalog.

The READ side — detectors are NAMED PAINS in the record

SCALE does not invent shapes; it names a pain, watches for it in the record, and only proposes a shape when that pain is sustained. A detector is a named pain plus the signal that betrays it — nothing more. This is the record→evidence read of the GROW stage made concrete: each detector reads the accumulated record across runs (never the live atom) and, on sustained pain, emits a proposal.

S2 (coordination) and S3 (resource) ARE the shared-resource / contention edges — seen as named pains over time. The overview puts it plainly: "shared-resource edges and scheduling contention are the same thing seen two ways — and they are the S2 (coordination) / S3 (resource) rungs of the maturation ladder." An edge is the wired-at-SHAPE view of two atoms competing for one finite thing; the same fact, accumulated in the record, is the S2/S3 pain SCALE reads here. The finite stock itself — tokens, $, the daemon's concurrency, the human — and its allocation rule live on Resource. So: read Resource for the stock, Edges for the per-run link, and this page for the over-time maturation that crystallizes a coordination/resource rule into Orchestration.

The S3*/S4/S5 signatures inherit that — each likely needs its own signature-definition sub-ADR, exactly as ADR-022 deferred mechanisms #3/#5. S2/S3 are defensible today; S3*/S4/S5 are research-open.

The WRITE-BACK side — the shapes available grow one rung

An approved proposal does not edit a running atom — it crystallizes a new shape into the operation and fills a slot on the recursive System. That is the write-back this page participates in: SCALE writes back the shapes available, so the next SHAPE stage has a richer set to plan against. (Compare the sibling GROW write-backs: SUBSTANCE writes back the atom's dispatch; CODIFY writes back the FOLLOW catalog — see Axes + families.)

The thesis — aggregation is not a system

Native today can mint many Workflows. But a pile of workflows is not a system — that is a theorem, not a preference. Beer's Recursive System Theorem (1979): units become the operational layer (S1) of the next level, and viability requires metasystem functions that exist in no individual unit. So a system never appears by piling units up; it appears when the metasystem (coordination, regulation, identity) crystallizes on top. Maturation is the process of growing that metasystem — organically, as the operation produces the pain that demands each piece. This is why SCALE reads pains, not preferences: the metasystem is earned from the record, never declared up front.

Naming, to avoid collision (L-number ban): S1–S5 here are Beer's Viable System Model recursion levels (cybernetics). They are NOT the PRD's §-section numbers (§4 runtime, §7 observability), NOT the L0–L5 change-cascade in holding/HIERARCHY.md, and NOT the L0–L2 D38 build layers. Three numbering namespaces already exist; this VSM ladder is a fourth, kept in words wherever possible.
Native is NOT short of composition. Canonical owner: the system, simply — corrections (the 5 composition laws + 10 typed primitives roster) — this page depends on it for that roster; SCALE is one growth mechanism among them, not Native's only structure.

The scaffold — present day-one, mostly empty

The founder constraint: the rungs up to identity must exist in the schema on day one, so the ladder is reachable without re-architecting — but they need not be built out. Two pieces deliver that:

1. A recursive System object (would sit beside Workflow in canon): it holds the domain it serves, its S1 units (each itself a Workflow or a System — recursive), one slot each for s2-coordination / s3-resource / s3*-audit / s4-adaptation (the "missing 2nd-order loop") / s5-identity (a Charter, always set — even a bare System has identity), and a maturity readout per slot (filled vs empty) so a System is never overclaimed. (Productization note: the field-level schema is the implementation layer — deferred; this page states what the object must carry, not its types.)

2. A dormant-but-present detector REGISTRY in EMERGE. The six detector slots are declared day-one — but a slot is not a working detector. Only the utterance detector (S1) is active; S2-S5 are dormant placeholders pending signature-definition (their event schema, thresholds, and false-positive handling are undefined — see gaps). "Ships day-one" means the slots exist so the ladder is reachable without re-architecting, NOT that the detectors work. (Peer review 2026-06-14 corrected the earlier "all six ship day-one" overstatement; the miner also needs a rollback model + verification/impact-analysis safety envelope before any rung crystallizes or retires — currently undefined.)

How it flows — one turn of the SCALE read → write

  1. Human INTENT → the daemon RUNs S1 units in the System of Process; events land in the System of Record (RECORD).
  2. EMERGE reads the record (the record→evidence boundary). A named-pain detector crosses its sustained-pain threshold.
  3. EMERGE proposes the matching rung (a new event, mirroring today's pattern_proposed).
  4. The human decides at Gate + Approval — GOVERN over the transition; nothing auto-builds.
  5. Approved → the rung crystallizes into its block (S2/S3→Orchestration, S3*→SoR/Observability, S4→new loop, S5→Charter) and fills the System's slot — the write-back to the shapes available.
  6. The matured System changes what the record shows next → LOOP, climbing toward S5.

Safety — why this is not premature over-engineering

GuardWhat it prevents
Sustained-pain thresholdA rung is proposed only on repeated, windowed pain (reuse the production graduation constants from canon). No crystallizing a one-off.
Reversibility (re-warm)If a crystallized rung is not reducing its pain, the same detector proposes its retirement. The thermostat runs both ways — this is what stops brittle ossification (Cynefin: only Clear/Complicated work earns hardening; Complex/Chaotic stays declarative).
No-overclaimThe maturity readout means a System with empty S2–S5 is reported as an S1 aggregate, honestly labeled — never as "viable."
ReflexiveA System editing its own metasystem trips the self-modify reflexive hardstop (HS-1) — existing hardstop, no new mechanism.

What runs today (no overclaim)

Per ADR-022 and the unit-science research, Native today runs design → execute → record. The record fails both litmus tests — nothing replays it, nothing reads it in-loop — so the SoR is telemetry, not yet a system of record (the record→evidence read this page depends on is not yet closed). EMERGE grows only S1 units (utterance ≥4 → propose a Workflow template; the lived unit it becomes is an Engine — ruled #1/#2). The entire S2–S5 ladder on this page is design-forward and unbuilt. The role the daemon would play (the miner) is the role the founder plays today by hand: noticing recurring operational pain and hardening a response — i.e. the SCALE read→write-back, run manually.

Proposed resolutions (design-forward, not built): the miner's missing safety envelope → impact analysis (where-used, ADR-022 #2) → shadow/dry-run → human-approve (ADR-010) → activate with a rollback compensator (self-modify trips HS-1). Halting/bounds → per-top-task budget (max depth/fan-out/cost) + WIP admission cap (ADR-022 #4). Determinism → ADR-022 #1 (persist LLM output as an event; content-addressed replay).
