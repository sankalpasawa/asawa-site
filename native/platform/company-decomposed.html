This page is ONE VIEW of the loop — the cross-unit + edges view

Read this against the overview, the system, simply. Native is one feedback loop: INTENT → SHAPE → RUN → RECORD → EVIDENCE → GROW → (write state back) → next INTENT, with authority wrapping every step. This page is the loop seen from one angle: how many units sit next to each other, and the typed links between them. Two questions own this page:
  • CROSS-UNIT — who-may-call-whom across scopes (the GROW axis that writes back to the call graph). The default answer is nobody; the page shows both halves — the isolation hard-stop and the sanctioned exception (a revocable delegation edge).
  • EDGES — the typed links between two atoms (handoff · shared-resource · must-cohere), wired at SHAPE and grown at GROW.
The record→evidence boundary on this page: every box in the trace below leaves an append-only record row (DecisionProvenance / EngineEvents) while the run is live; that record becomes evidence the moment a later run reads it across runs — which is exactly when the CROSS-UNIT axis writes back. The write-back this page participates in: GROW reads the accumulated cross-unit record and updates who-may-call-whom — tightening an over-broad edge, or granting a new revocable handoff a sibling now repeatedly needs. The frame (Domain + Charter) is what makes that write-back safe to grant and safe to revoke.

What this page shows

We take one fictional company — Cascara & Crema Coffee Co., a 40-branch specialty coffee chain — and describe it entirely in Native's primitives. Two things happen at once, and keeping them apart is the whole point:
  • The frame. Domain (a scope of authority) and Charter (the rules) wrap everything. They are not steps in the work — they are the box the work runs inside. (Same frame as on the work-structure page, §6.)
  • The work. Inside a scope, under its rules, the work stacks: System → Workflow → Step — a System bundles Workflows, a Workflow is ordered Steps, a Step is one atom of real work (one LLM call or one skill call).
Scopes nest: the chain is a Domain holding function-Domains holding branch-Domains. The same frame-around-work shape repeats at every zoom level. We zoom from the whole company (L1) into one function — Branch Operations (L2) — down to one nightly close-the-branch workflow and its steps (L3), then place the same shape side-by-side at two levels (recursion), follow one full run (trace), and finally read the cross-scope picture two ways: cross-unit (who-may-call-whom) and edges (the typed links).

Dashed boxes = the frame (Domain scope, Charter rules). Solid/filled boxes = the work that runs inside it. The frame is never a step in the work.

L1 — the whole company as one Domain

The entire chain is one root Domain (D0), under one chain-wide Charter, holding five function sub-Domains. The Domain + Charter are the dashed frame; each sub-Domain is itself a scope with its own (stricter or looser) Charter. The work lives inside each — we drill in at L2/L3.

L1 — the chain as one root Domain D0 under one House Charter (the frame), holding five function sub-Domains (each its own scope, its own Charter). The work itself lives inside each; we drill in next.

L2 — one flagship function: Branch Operations

Zoom into D0.D2 Branch Operations. Same shape one level down: it is itself a Domain, with its own stricter Charter and its own sub-Domains. Two run "process / block" (opening, the floor close); one runs looser "directive / pause" (in-shift upkeep). Each sub-Domain would hold a PROPOSED System that bundles its Workflows.

L2 — inside the flagship. Branch Operations is itself a Domain with its own (stricter) Charter and three sub-Domains. Stringency is set per scope: two "process / block" (opening, the floor close), one "directive / pause" (upkeep). Each sub-Domain would hold a PROPOSED System (green-dashed) bundling its Workflows.

L3 — drilling to the bottom: System → Workflow → Steps

Drill into Floor & Service Run. Now the work ladder appears, inside the frame: the PROPOSED Floor Engine (System) holds the W-close-branch Workflow, which is four ordered Steps (atoms). Step 2 is the gate — an out-of-tolerance till halts the close until a named human approves.

L3 — the floor. The work ladder (System → Workflow → Steps) sits inside the Domain + Charter frame (the dashed boxes). Step 2 is the gate: an out-of-tolerance till halts the close into awaiting_approval until a named human approves; the Charter's on_override = block means trying to skip it is refused, not logged. The three Step→Step arrows here are handoff edges — the simplest typed link; the cross-unit and edges sections below pick that thread up.

Recursion — the same shape at two zoom levels

Recursion = the identical shape, side-by-side, at company scope and inside one branch. Same primitives, same fields, every label re-used. Going down, only two dials change: stringency tightens (principle → process) and override hardens (audit-only → block).

D0 has D0.D2; the Chain Engine has Branch Day Engines as its work-slots; the Branch Day Engine has W-close-branch — containment, never inheritance (nothing is-a kind of anything). The Tenant tree nests in parallel (root Tenant ⊃ branch sub-Tenant) — which is exactly why a cross-branch write is a tenant_boundary_violation (#26 / HS-3). Both System boxes are equally PROPOSED.

Trace — one nightly close, end to end, framed by Domain + Charter

Follow a single W-close-branch run from trigger to audited record. The frame is drawn as the two bands: Domain (top) says where the run may act; Charter (bottom) says how strict the gating is.

Trace — one nightly close. Domain (top band) frames where: the branch sub-Tenant isolates the run, so a cross-branch write hard-stops (#26 / HS-3). Charter (bottom band) frames how strict: process stringency makes the close non-improvisable and on_override=block refuses any skip. Scope says where; rules say how strict — together they turn a till-count into an audited, approval-gated, tenant-bounded run. The RECORD box on the right is the record→evidence boundary: a later run reads these rows and the cross-unit axis writes back.

Cross-unit — who-may-call-whom (both halves)

This is what the page owns. Once a company has many units side-by-side (five functions, forty branches), the live question is: may one unit reach into another? Native answers in two parts, and you need both.
  • The hard default is NO. Each Domain has its own Tenant; nothing is ambient. A write aimed at another scope is a tenant_boundary_violation (#26 / HS-3) — refused, not logged-and-allowed. Isolation is the hard default; an edge is the only sanctioned exception.
  • The positive answer is a DELEGATION EDGE. Units still cooperate — through an explicit, revocable handoff. A cross-unit edge is a named grant on the call graph, not open access: it says exactly which unit may hand exactly what to exactly which sibling, and it can be revoked the same way it was granted.
The CROSS-UNIT axis (a GROW axis — see axes + families) is the dial that moves between these. Its ladder is isolate → coordinate → delegate, and it writes back to who-may-call-whom — this is the loop write-back this page participates in. You start fully isolated; the record shows two siblings keep needing the same hand-off; GROW grants a revocable edge; if usage stops, GROW revokes it. The frame is what makes both directions safe.

Cross-unit is two-sided. Left: the hard default — isolation, with a cross-Tenant write hard-stopping as tenant_boundary_violation (#26 / HS-3). Right: the sanctioned exception — a single, named, revocable delegation handoff on the call graph. The CROSS-UNIT axis (isolate → coordinate → delegate) is what moves between them, writing back to who-may-call-whom; Authority gates the grant.

The two halves are not in tension — they are the same rule stated both ways: everything is isolated unless an edge says otherwise, and an edge is always explicit and revocable. That is why a delegation never degrades isolation: the edge is the audit trail of the one exception. See the typed-edge mechanics next, and the full edge taxonomy at edges.

The typed edges — the links between atoms

The other half of what this page owns. A workflow is nodes + edges: work-atoms are the nodes, an edge is the typed link between two of them. Three kinds, each born from a different shaping choice and each needing different handling. The Step→Step arrows in the L3 / Trace diagrams above are the simplest of these (handoffs); a cross-unit delegation is also a handoff — one that crosses a Tenant boundary. Full taxonomy: edges.
EdgeMeaningBorn fromNeedsThis company's example
handoffA's output → B's inputsequence (A before B)order + a usable outputtill-read → tolerance verdict (the L3 Step arrows); cross-unit: Beans & Supply hands a restock-order to Branch Ops
shared-resourceA & B want one finite thingconcurrency on a finite poolan allocation rule (FCFS/priority/budget)two branches' nightly closes hit one shared host-LLM rate limit → one waits
must-cohereA & B each make a piece of one wholeone output split into parallel partsa standard up-front, or an integration stepR&D drafts three menu cards that must share one house visual style
Each edge is the flip side of a shaping choice: sequence makes handoffs, concurrency on a finite thing makes shared-resource edges, decomposition of one output makes must-cohere edges. Edges are wired at SHAPE (the workflow shape is nodes + edges) and grown at GROW (the cross-unit axis decides who-may-call-whom). A shared-resource edge is the Resource axis seen between two atoms — the S2 (coordination) / S3 (resource) rungs of maturation; contention on it is also the scheduling side of Time.

How this ties together

This page is a worked example built from three siblings, read as one VIEW of the loop: the Work-Atom is the bottom unit (one Step = goal + constraints + context + work); Work structure is the abstract build-up (atom → workflow → system → recursive) and the Domain/Charter frame (§6) this page applies to a real company; Maturation is how that structure would grow over time (units → identity, S1–S5). Read together: Work-Atom = the brick, Work-structure = the shape, this page = one building drawn in that shape and read as the cross-unit + edges angle of the one loop, Maturation = how the building grows. As everywhere in Native today, the "System" layer is a PROPOSED scaffold — this page draws what a company would look like in primitives, it does not build one.
