Purpose

Ruled 2026-08-06 (sheet A1-FINAL-2, the frame collapse): only SYSTEMS exist as things — the old frame words survive as the names of SYSTEM PROPERTIES. Charter is a system's property: its goals, constraints, and authority — one-directional, only a System gets a charter, never the reverse. Domain names the fixed systems we have — the standing-system tree itself, the address view of that tree. Tenancy is a custody label whose design is explicitly DEFERRED by ruling ("later on, not right now"). This page exists to give each property its own contract and ownership (Contract) — three distinct properties, never blurred into one frame object. The charter appears as a property box on both sides of the hub diagram: pre-provisioned on the written Assembly, the rule-book of the grown System.

Charter

The codification ladder — how rules harden from task rule to charter to doctrine, with a decay counter-flow.

  • Holds rules, never work-state (sheet, work-state shelves note). Content: goals, constraints, authority.
  • Pre-provisioned at birth, even empty (A1-FINAL Ruling 1): every system gets its charter and internal-system slots hardcoded from the start so growth stays bounded. The 163 auto-minted charter stubs in the build are VALIDATED as intentional structure, not debt — the lean-minting alternative was recommended and rejected.
  • Mutation is operator-only through a gate; write-backs to governance targets are ALWAYS gated, never auto (sheet §2 edge table, GROW→write-backs).
  • Constraints can live at system level — the System's charter holds them (A1-FINAL constraint ruling). The cascade narrows downward: stringency goes up as rules flow down. HOW they flow (system → engine → workflow → atom) is the deferred named question CONSTRAINT-PROPAGATION (open questions).
  • Rules are earned upward via the hardening ladder: task rule → protocol → charter (ruled, stands).
  • Cross-cutting rules are the charter property of a SHADOW system — a structured overlay with its own glue engine that coordinates standing systems, never mutating them (hub, shadow systems). This dissolved the earlier charter-as-object argument (recorded explored-and-superseded).
RULED (A1-FINAL-4, sitting concluded 2026-08-17): the authority model — the 5-part model: authority is written at the system, narrowed below, earned by engines, exercised at atom gates, with min-wins (the ruled name for what this page earlier called "most-restrictive-wins"). Separate engine-evidence track; schema applies on all 219 records (sheet §11, Authority row).

Domain

  • Standing System ≈ Domain (Ruling 2, naming collapse): a standing system — engines + glue engines running daily for a particular goal (workflows live inside engines, X3 — ledger ruling #3) — IS what the domain tree names. Standing systems are allowed to be discrete and messy; they grow organically.
  • Axiom X4 as amended: standing systems are domain-drawn; use-case-drawn compositions are shadow systems.
  • The placement engine resolves work to addresses in this tree (ADR-028). Worked example (sheet §8c): a doc places at D0 Asawa > D1 Sutra OS > docs/knowledge — the department owning the SUBJECT owns the doc, resolved live.

Tenancy (today's posture: Authority + Tenancy)

  • Custody label. Design DEFERRED explicitly by ruling — custody label + gate posture remain as-is; no design work until called.
  • Distribution consequence already ruled (A1-ext): distribution ships templates only — instances and state never leave the tenant (D33 in one sentence).
Honest grounding: the build's own source disclaims isolation — placement_engine.py:242-244 states tenant filtering "never was isolation". What holds the line today is gate posture (HS-3). The wording-vs-code contradiction is an open founder item (s7).

Proposed — requirements and responsibilities as views

PROPOSED Source: founder direction 2026-08-07 (in-session) · sheet cards · zero new objects — composes existing primitives only.

Two candidate VIEWS — reports computed on read over records this page already documents. No new store, no new property, no new charter field beyond what the queued A12 card already proposes; the ruled property table and the charter contract above stay exactly as written.

REQUIREMENTS view — what the system would declareRESPONSIBILITIES view — what the system would owe
charter goals (list) + services (declared styles + accepted request types, per the queued A12 style cards) + bounds (the authority ceiling narrowed from above) — all existing or already-queued fields read togetherown charter goals + slices of OTHER charters accepted via gated edges; each row of the view = goal serviced + accountable-to + evidence owed
Both are VIEWS over existing records — candidate reports, not objects; nothing here would mint a new noun, store, or schema field.

Proposed (watermarked, not ruled): two overlapping scopes — Credit-Ops' own charter goals plus a Finance charter slice accepted via a gated edge into Credit-Ops' responsibility view.

Example (lending): Credit-Ops would service its own charter plus Finance's monthly-reconciliation slice; the slice would appear in Credit-Ops' responsibility view with Finance as accountable-to and the reconciliation evidence owed monthly.
