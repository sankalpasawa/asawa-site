Assembly and System — the written composition and the grown organism PLATFORM · zoom 4

Work-order header

idband / parentstatusversionowner
platform-model-assembly-systemPLATFORM / platform-the-modelDRAFTv1claude

Purpose

Assembly is the WRITTEN composition: which workflow types, which glue types, which edges, plus the pre-provisioned charter and internal-system slots. System is the GROWN organism: work engines + glue engines operating together, daily, for a goal — with its OWN goals, constraints, and verify (the meta-unit). You FOLLOW an Assembly; you RUN a System. This pair is the composition rung of the ruled vocabulary (founder sittings 2026-08-05/06, decision sheet A1 / A1-ext / A1-FINAL): it exists so that composition — not just single workflows — has a written, followable template side and a lived, accumulating side, with the written/grown distinction preserved exactly as it is one rung down for Workflow → Engine.

How it works

The three typed edges that wire a composition: handoff, shared-resource, must-cohere.

A system = work + glue; any slot can hold a sub-system.

The same shape nests: company, department, team, workflow.

Composition and recursion — atom to workflow to skill toward systems (migrated from the v2 page).

The two halves, side by side (see the hub diagram):

HalfLifeContentsState
AssemblyWRITTEN (template)workflow types + glue types + edges; pre-provisioned charter slot (may be empty) + five internal-system slots hardcoded from birthnone — stateless, FOLLOW-able
SystemGROWN (lived)work engines + glue engines — only engines, nothing else (X3); own goals + constraints + verifycomposition-owned state (delegation map, budgets, locks) held BY glue engines, never floating outside an engine (X3)

Rules that shape the pair:

  • System test: a collection of engines is a System when at least one GLUE ENGINE runs above the work engines, owned by none of them (sheet A1).
  • Standing systems = the domain tree (Ruling 2): departments ARE standing systems; the domain tree is their address book. Standing systems may grow "discrete and messy" — that is allowed.
  • Nesting is free (X3): a nested System appears to its parent as ONE Engine; systems cascade arbitrarily. A System viewed from outside is one bigger Engine.
  • Boundaries (X4, as amended by Ruling 3): standing systems are domain-drawn; use-case-drawn compositions are shadow systems — structured overlays with their own glue engine that coordinate standing systems and never mutate them.
  • Pre-provisioning (Ruling 1): every system gets its charter and internal-system slots hardcoded from the start, even empty — growth stays bounded, nothing evolves into undefined shapes.
  • Charter is a property of the system (A1-FINAL-2): goals, constraints, authority; one-directional — only a System gets a charter, never the reverse. Rules, never work-state.
  • Two dials (A1-FINAL): means = intelligence | procedure | composition; life = template | lived. Assembly is the seed, System the grown organism.

The birth story (maturation strip) — things earn their nouns: workflows accrete and, by living, become engines (X2); engines collide on shared resources; the FIRST glue engine enables composition — a pile becomes a System by first glue + goal; the use case draws the boundary (X4). The S1→S5 maturation ladder becomes "which glue engines exist yet" (sheet A1).

Invariants

  • X1 no naked work — canonical owner: Work-Atom — this page depends on it for the atom floor.
  • X2 no stateless execution — canonical owner: Workflow + Engine — this page depends on it for engine birth.
  • X3 engines all the way down — Systems contain only engines; nested System = one Engine to its parent; all composition state is held by glue engines.
  • X4 (amended) — standing systems are domain-drawn; use-case-drawn compositions are shadow systems.
  • System test — at least one glue engine above the work engines, owned by none of them.
  • Seam semantics (RULED, §9c G7 — 2026-08-17 sitting) — min-wins on gates, conjunction on constraints, escalate on unsatisfiable.
  • Charter is one-directional (only Systems have charters) and holds rules, never work-state.
  • Engine-Library rule — canonical owner: Workflow + Engine — this page depends on it for crystallization safety.
  • Shadow systems never mutate the standing systems they coordinate.
  • Pre-provisioning — charter + internal-system slots exist from birth; empty is fine.
  • Distribution ships templates only — canonical owner: Workflow + Engine (A1-ext consequence; D33 in one sentence).

Lifecycle

  • Authored: an Assembly is WRITTEN, starting from the use case (X4).
  • FOLLOW → RUN: following the Assembly brings a System to life; each member engine is born at its workflow's first run (X2).
  • Organic path: pile → System by first glue + goal; the maturation reading is "which glue engines exist yet".
  • Shadow path: created for a cross-system use case; retires or persists on its own terms.
  • Composition change: GROW write-backs (shapes, who-may-call-whom, catalog) are ALWAYS gated, never auto (sheet §2).

Ownership

  • Standing systems are addressed by the domain tree (Ruling 2); the charter is the system's own property.
  • Within a System: the coordination glue engine owns who-may-call-whom; the priority engine owns budgets (X3).
  • Assembly authoring/retiring authority: TODO(founder):

Failure modes

  • Verify fails repeatedly → retry budget exhausted → ESCALATED → Approval (sheet §8; budget home = Charter field retry_budget, default 3 — A8 RULED as REC at the 2026-08-17 sitting; grounding: no retry budget exists in the build yet).
  • Resource contention between engines → coordination glue sequences/locks (R12).
  • Un-workflowed mutation → cannot dispatch (X1); a workflowed-but-odd one surfaces via the audit glue engine within one cadence tick (R6).
  • Decay — green-never-consulted and red-never-fixed instruments flagged by the audit glue engine (R10).

Observability + audit

  • Every run appends to the append-only record (X2); the audit glue engine reads the record on cadence (R6, R9).
  • EVIDENCE schema RULED as REC, spec-only (A3, 2026-08-17 sitting — nothing reads it in-loop yet) — the GROW arms that would grow a System consume prose today. Ledger rows in the build are keyed by session+atom, never by workflow, so no engine slice is queryable per-workflow; flow-ledger.jsonl is the closest store (grounding §3).

Proposed architecture — system interaction (zero new objects)

PROPOSED Source: founder direction 2026-08-07 (in-session) · sheet cards · zero new objects — composes existing primitives only. Everything below reads over primitives that already exist (Workflow, Step, Trigger, Charter, Domain, ExecutionResult, EngineEvent, Approval), ruled model mechanisms, and already-queued cards; the typed contract is only the SHAPE an eventual A7 ruling could adopt — A7 stays DEFERRED.

The repeating cell (PROPOSED) — from outside, a system is ONE engine (ruled, X3); in this proposal everything would cross through these four seams: charter-in, intake, evidence-out, escalation-up. Slot semantics for the five glue engines: canonical on Internal System.

Worked example (lending, proposed) — Collections asks Product for an EMI-reminder nudge. The REQUEST (goal: nudge overdue EMI payers; due-by: before the next reconcile run) would land on Product's intent queue. Product's own priority glue orders it against Product's other work — autonomy stays with Product; Collections never reaches inside. On completion the RESULT would come back as an ExecutionResult with evidence attached — one thread id end to end: request, approval, run, evidence on the same thread.
