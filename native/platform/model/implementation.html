Purpose — building the model with the model

This page is the build plan for the ruled model — and it is written AS the model. Every unit of the plan carries the four particles (goal, constraints, context, HOW), one goal with ONE verify, and belongs to a written blueprint (s4). That is the WRITTEN column of the ladder applied as an engineering planning discipline: the plan for building the machine is shaped like the work the machine will one day run. Nothing more is claimed — read the guard.

NAMESPACE GUARD (read before any row below). The plan's units are BuildAtoms — planning artifacts for engineering, NOT runtime Work-Atom primitives. No row on this page is a runtime object, and no row implies the runtime exists. Per the grounding map: Workflow has ZERO runtime instances (user-kit has no workflows/ directory; the 2 real W-files are loose plans), and Engine, Assembly, and System are MISSING as objects. Every BuildAtom on this page carries not_runtime_state=true. The plan targets those gaps; it never presupposes them closed.

Fact sources are exactly two: the design decision sheet (rulings + open registers A2-A10, B1-B10, C1-C10) and the grounding map (as-built fidelity audit, 2026-08-06). RULED facts are stated plain; PROPOSED and OPEN items are marked; gaps stay bare TODO(founder): markers.

Proposed — the layer stack: what ships, what installs, what grows

PROPOSED Source: founder direction 2026-08-07 (in-session) · BUILDERS.md · sheet card A13 · zero new objects — composes existing primitives only. The builders named on this stack have their full anatomy + lifecycle on the Builders page.

Install day (proposed sequence): 1) plugin installs (L-SHIP lands) → 2) root builder interview reads the company → 3) skeleton minted (L-INSTALL: Assembly stubs, slots, zero-delta child-builder records, styles) → 4) work begins through the builders → 5) engines are born at first runs, glue slots fill by maturation — L-GROW accumulates. No System is pre-installed; each earns its noun by living (the grown column stays grown).

Update path (proposed, splits per codex): a plugin update replaces L-SHIP only. Children are version-pinned to the base they derived from — with a split: additive base updates (new options, docs, model pages) may stay pinned until convenient; floor updates (enforced invariants, security) fire a MANDATORY gated re-derivation per system — the child either migrates (deltas preserved, founder approves) or carries an explicit quarantine/compat status; silent staleness on a floor change is not a valid state. L-GROW is never directly mutated by an update; an update may only file gated tenant-local proposals. Alignment note: this rides the ruled distribution rule (templates ship; instances + state never leave the tenant) while true tenancy isolation remains deferred — gate-posture only today.

Maintenance is not building (proposed): re-wiring an existing engine = a GROW write-back amending the workflow registration under gate; re-drawing a live system boundary = an Assembly amendment or a shadow-system mint, gated, grown-state-preserving. No maintenance builders exist; the three builders build births only.
