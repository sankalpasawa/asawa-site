The ladder at a glance

Five capability versions. Each ships the smallest loop that closes; each next version is gated on evidence the previous one recorded — the platform versions itself the way it says companies should grow. Versions are operating modes, not release numbers: a version is done when its success number is hit.

Each arrow is an evidence gate: the next rung opens only when the previous rung's ledger proves its number. Gate details in the per-version cards below.

VersionPromiseSuccess number (version is done when…)
v1 FOLLOWA recurring piece of work runs through a written workflow with honest checks, every time.same workflow FOLLOWED 20×, verify pass rate visible, zero improvised repeats
v2 REMEMBERThe platform gets measurably better at the workflows it already runs.interrupts halved on the same work; honest ETAs from record-derived estimates
v3 COORDINATETwo departments exchange work without a human carrying it.one exchange brokered by nobody — one thread id end to end, with evidence
v4 ORGANIZEA cross-company effort runs through the platform, fully reconstructable afterward.one real launch end-to-end; founder interrupts beat the sim benchmark (19)
v5 DISTRIBUTEThe root builder installs the platform on a stranger’s computer and grows it there.one install on a computer Asawa never touched, growing on its own record

Self-sustaining — what it means, testably

A version is self-sustaining iff it can run a complete cycle with only its own modules, records, and documented human procedures. Two acceptance tests, applied per version:
  1. Deletion test — remove all later-version modules and docs; an operator can still complete this version’s promised workflow AND recover from errors using only recorded evidence.
  2. Fresh-operator test — a person who did not build it can run it from the runbook and records alone; no author interpretation required.
Plus: no circular gates (a version’s exit evidence is producible by THAT version alone) and a downgrade story (rolling back leaves enough records to keep operating — each card names its rollback floor).

Per-version cards

Each card: what ships · the gate to enter · the evidence that exits · the hard boundary (can / cannot / must-not-assume) · the rollback floor. Incremental by construction: v2 builds on v1’s ledger, v3 on v2’s evidence model, v4 on v3’s traffic, v5 on v4’s proof.

The module stack — the record is the API

Modules never call each other. Each reads and writes plain files (registries, JSONL ledgers); the next module consumes those files. Every module is independently usable — eight of ten are standalone micro-products.
