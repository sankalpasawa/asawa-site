Workflow and Engine — written and grown PLATFORM · zoom 4

Work-order header

Purpose

Workflow and Engine are one rung of the ruled ladder seen from its two columns. A Workflow is the WRITTEN blueprint — an authored, stateless artifact composing 1..n Work-Atoms with a pattern and a failure policy. An Engine is the GROWN form of that same workflow — the workflow plus everything it has accumulated by living: state envelope, record slice, learned patterns, and charter binding. The distinction exists because of two axioms ruled by the founder (2026-08-05/06): X1 no naked work — whatever is worked on always has a workflow, a single atom being a workflow of one — and X2 no stateless execution — every run executes inside an engine, born at its workflow's first run with an empty record slice. You author the written half; only the grown half runs. See the hub diagram for this rung in the full ladder.

How it works

One object, two columns — never conflate them:

HalfColumnDefinition (RULED, A1 family)StateStorage
WorkflowWRITTENStateless blueprint: 1..n atoms composed; steps, pattern, failure policynoneWorkflow primitive — unchanged
EngineGROWNWorkflow + statefulness: the workflow plus its accumulated cross-run statelive, across runsA NAME over 4 existing stores — no new storage

The written half: authoring and FOLLOW

  • A workflow composes 1..n Work-Atoms. Canonical owner of the atomicity rule (one goal, ONE verify): Work-Atom — this page depends on it for the split test.
  • Workflows are reached through the loop's resolution edge: a matching workflow type is FOLLOWed; none found means CONSTRUCT builds the skeleton. Resolution is child-custody-wins (ADR-026).
  • A workflow becomes FOLLOW-able through the reuse_tag C0→C1 promotion — the only crystallization step that is canon today. Paths earn the workflow-type noun by repetition.
  • Per X1 the FOLLOW/CONSTRUCT spine is total: nothing dispatches outside a workflow.

The grown half: engine birth and the four state stores

An engine is born at its workflow's first run, with an empty record slice (X2). From run 1, every run writes to some engine's record slice. The engine's statefulness is exactly four stores — a name over things that already exist, never new storage:

StoreScopeHolds
State envelopewithin-runthe live run's working state
Record slicedurable, cross-runthis workflow's slice of the record — history of runs, artifacts, corrections
Learned patternsbehavioral (B5.d)lessons that change how future runs behave
Charter bindingpolicywhich charter's constraints and authority bind this engine's runs
Engine-Library rule (RULED, A1): an engine's statefulness must be EXPLICIT inputs from the record — never hidden internal state — or crystallization to C2 code breaks. State you cannot point at in the record is not engine state.

Run 50 differs from run 1

The real proof is W-md-authoring (decision sheet §8c). On 2026-08-05 the founder ruled that diagrams in md files use mermaid, not ASCII art. That correction landed once — in the Md-Authoring Engine's learned patterns — and changed every future doc. The engine is the workflow (outline → author → audit) plus its record slice (docs + founder corrections) plus learned patterns (mermaid-not-ASCII, tables-over-prose, hub-and-spoke) plus its charter binding. Run 50 ≠ run 1, provably — and the written workflow file never changed.

Attempts are not objects at this level — canonical owner: Work-Atom s5 (attempt log = data field on the HOW particle); the retry budget reads that field.

Every run turns an 8-phase task clock (OBJECTIVE → OBSERVE → SHAPE → PLAN → EXECUTE → MEASURE → OPERATIONALIZE → LEARN) INSIDE the workflow object's governance ledger (PROPOSED → ACTIVE → PERSISTED → RETIRED). Invariants

  • X1 no naked work — nothing dispatches outside a workflow; a single atom is a workflow of one.
  • X2 no stateless execution — every run executes inside an engine; the engine is born at the workflow's first run with an empty record slice; every run writes to some engine's record slice from run 1.
  • Engine-Library rule — engine state = explicit inputs from the record, never hidden internal state; violation breaks C2 crystallization.
  • No new storage — Engine is a name over the four existing stores.
  • The written half never mutates at run time — all accumulation lands on the engine; the workflow file stays a stateless template (A1-ext grid).
  • Distribution ships templates only — instances and state never leave the tenant (A1-ext consequence; D33 in one sentence).
  • One goal, ONE verify per atom — canonical owner: Work-Atom (A1-ext).

Ownership

  • Engine state is owned by the record (SoR, ADR-013) and read as explicit inputs — the engine object itself is a name, canonized in a new ADR at S7 (number at mint, per C2).
  • C-state lives on the atom's HOW particle; Workflow/Engine state is a derived aggregate, mixed states allowed; promotions earned by run evidence (A9, ruled by consequence).
  • Charter holds rules, never work-state (A1-FINAL-2 + the open work-state-shelves proposal).
  • Followable workflow templates: the FOLLOW catalog — home is the user-kit workflow files with reuse_tag plus one index spec (A2, RULED as REC — 2026-08-17 sitting, Quick eight).

Proposed — the goal cascade

PROPOSED Source: founder direction 2026-08-07 (in-session) · sheet cards · zero new objects — composes existing primitives only.

X1 guard: sub-goals would be planned goal+verify cuts that become atom goals or child-workflow goals — they dispatch ONLY through FOLLOW/CONSTRUCT; there are no naked sub-goals. Proposed cut condition: a sub-goal is cut only when no single workflow reaches the goal — the cascade halts where a workflow exists, so a richer FOLLOW catalog would mean shallower cascades.

Example (lending): the goal "top-up delinquency back to forecast" would cut into 3 sub-goals — tighten the eligibility rule · collections outreach wave · credit-policy memo — each closed by one workflow, with the parent verify checking the delinquency curve itself.
