The Internal System — five glue engines PLATFORM · zoom 4

Work-order header

Purpose

The Internal System is the five glue engines — coordination, priority, audit, adaptation, identity — present pre-provisioned inside every system. The charter states what must be true; the internal system is the machinery that KEEPS it true. Ruled in the A1 family (founder sittings 2026-08-05/06): glue engines are engines too — the same four-store engine shape as any Engine (canonical owner: Workflow + Engine s2) pointed at other engines instead of at domain work. They hold the composition state (axiom X3: nothing floats outside an engine — the coordination engine owns who-may-call-whom, the priority engine owns budgets). The internal system exists so a system's upkeep is made of the same stuff as its work (engines all the way down), and so growth stays bounded: the five slots are hardcoded from birth, empty is fine.

How it works

The record→evidence boundary the audit + adaptation glue engines read.

The two growth ladders — scale (slots filling) and substance (C-states hardening) — are orthogonal. Fuller v2 treatments: Maturation and Crystallization (v2 pages; canonical home pending a founder call — see the fix report's queue).

Evidence drives four growths — each write-back lands in a different glue engine's territory.

The maturation loop — how the record's named pains fill the internal-system slots (human-gated).

Glue is not a new object kind. Each slot, when filled, is a grown Engine — born at its workflow's first run (X2), state as explicit inputs from the record, never hidden. What makes it glue is its target: it runs above the work engines and is owned by none of them. See the hub diagram for the five slots in place, and the hub's written/grown level for the Workflow (written blueprint) vs Engine (grown form) distinction every slot inherits.

Three ruled properties complete the mechanics:

  • Regress stop. There is no internal system of the internal system. The glue engines are crystallized invariants — their verifies ARE their governance; code invariants ARE the governance. The recursion ends here by construction.
  • Pre-provisioning (Ruling 1). Every system gets its charter and five internal-system slots hardcoded from birth, even empty — growth stays bounded, nothing evolves into undefined shapes. The 163 auto-minted charter stubs in the build are validated as intentional structure, not debt.
  • Crystallization speed. Glue engines are mostly CODE — they crystallize fastest of anything in the model. The maturation ladder (S1→S5) is exactly "which internal-system slots have filled yet": coordination (S2), priority/resource (S3), audit (S3*), adaptation (S4), identity (S5).

Invariants

  • System test (A1) — canonical owner: Assembly + System.
  • X3: composition state is held BY glue engines; nothing floats outside an engine.
  • Regress stop: no internal system of the internal system — code invariants ARE the governance; the glue engines' verifies ARE their governance.
  • Adaptation is sense → propose, never apply; GROW write-backs are ALWAYS gated, never auto (sheet §2).
  • The checking engine must not be the writing engine — asserted-done vs ACCEPTED by a counter-party (R8).
  • Charter holds rules, never work-state.
  • Engine-Library rule: a glue engine's statefulness is explicit inputs from the record, never hidden internal state.
  • X2: a glue engine is born at its workflow's first run, with an empty record slice.

Ownership and failure modes

The host system owns its internal system; no work engine owns any glue engine (that is the System test). Failure modes attested in the sources: CRITICAL audit finding (exit 1), resource contention between engines (R12), instrument decay — red-never-fixed / green-never-consulted (R10), and self-verifying instruments where writer and checker were the same engine (R8).

Honest ceiling (sheet §8b, carried from ADR-030 D6): T1 closable today; T2 partial (machine runs + records, human picks the question); T3 only inside ADR-010's detector; T4 sensing only. The glue engines for R6/R8/R10 are design-forward — only the daily governance audit (R9) and the docs guards (§8c) run today.

Observability

  • Audit findings append to a findings log; CRITICAL exits 1 (grounding §2).
  • Cadence is scheduled (launchd 09:07 audit, 09:37 triage); pass criterion: mean time-to-visibility for silent failure classes ≤ 1 cadence tick (R9).
  • Every proposal and ruling persists — write-backs leave a proposal + ruling trail (sheet §2, GROW edge).

Proposed — priority merge and deadline mechanics

PROPOSED Source: founder direction 2026-08-07 (in-session) · sheet cards · zero new objects — composes existing primitives only. Everything below is proposal phrasing: the priority glue engine WOULD merge and order this way if ruled. No new object, no new event type, no sixth slot — the inputs are the Charter, the priority slice's budgets, the intent queue's accepted entries, and the existing escalation flow; the output queue is the same intent queue card A11 already puts under this glue.

Proposed merge — four existing signals in, one ordering out. Not ruled; the sheet remains the authority.

Backward estimation, worked (lending). A request lands on the lending branch system: rework W-kyc-verify's document checks, accepted onto the intent queue with a due-by of Sep 15. The priority glue would read its record slice — similar reworks took 6 days — add a 2-day buffer, and count backward: latest start Sep 7. If the work has not started by Sep 7, a deadline-at-risk escalation would fire BEFORE the due-by, while it can still be met — not after the miss.

Proposed backward estimation on the W-kyc-verify rework — the escalation would fire at the latest-start line, not at the miss.

Not a new event type (codex constraint). “deadline-at-risk” reads like an event type; it is not one. It is a proposed priority-glue heuristic — a rule this engine would apply to its own queue — and the escalation it raises would travel as the existing workflow_escalated EngineEvent, gated through the existing Approval flow. The EngineEvent enum stays closed: “deadline-at-risk” would be at most a role named in the payload, never a new member of the enum.

The 6-day figure would come from the record slice, not a guess — the engine's accumulated state paying off. The estimation loop itself already runs in the Asawa build today (estimation-collector.sh hook → holding/ESTIMATION-LOG.jsonl, estimate vs actual per task); this proposal would reuse that loop, not reinvent it.
