F-ENG-01 Record slice as recovery authorityREUSE-AS-ISEffort LTODO

SourceTemporal durable execution — https://docs.temporal.io/workflow-execution
What industry runsTemporal keeps an append-only Event History per workflow execution; the record, not the running process, is the source of truth, and recovery is replay of that record. Battle-proven at trillion-action scale (Netflix, Stripe, OpenAI). Done-ness is structural, but the record-as-authority mechanic is exactly X2 enforced by a machine.
How it fits NativeLands on the Engine's `record_slice` store — one of the four ruled stores in workflow-engine.html §2/§5. Today's closest instrument is `.sutra/flow-ledger.jsonl` (the page's own 'closest engine-slice store') plus `.sutra/atom-ledger.jsonl`, which lack a stable `workflow_id`. NEW: a record-slice spec attached to the Engine contract declaring record = source of truth and envelope reconstruction = replay of record — the machine form of the already-ruled Engine-Library rule (explicit inputs from the record, never hidden state).
Build sketch
  1. Write the record-slice spec into the Engine contract (canon home per D54: NATIVE-ENGINE.md §): append-only JSONL keyed by workflow_id + run_id; record is authority, envelope is derived.
  2. Land BA-04's `workflow_id` field on flow-ledger rows (one field, one writer, ~1h per the implementation page) so every record row keys to an engine.
  3. Add `sutra-native engine rebuild --workflow-id <id>`: reconstruct engine.envelope + learned_patterns by folding record_slice rows in order.
  4. Add `engine verify-state`: diff live envelope vs replayed envelope; mismatch appends a deviation row for the audit glue engine.
  5. Charter rule: no writer mutates engine.envelope except through a record append — X2 by machine, not discipline.
Depends onBA-04 (stable workflow_id, TODO(founder)) + BA-05 (ledger keyed by workflow); founder ruling replay-grade vs audit-grade (engine.md §5)
Decision needed (founder)Does the record slice target replay-grade (record = recovery, Temporal style) or audit-grade (append-only, human/miner-readable, no replay guarantee)?

F-ENG-03 Glue-engine determinism ruleADAPTEffort MTODO

SourceTemporal determinism constraint + Resonate critique — https://journal.resonatehq.io/p/from-where-do-deterministic-constraints
What industry runsTemporal forbids workflow orchestration code from using wall-clock, random, or direct I/O so that replay against the recorded history is exact — a mismatch is a hard non-determinism error. It is the strongest self-verification known, and also Temporal's most-complained-about tax; the Resonate critique documents it as unnatural for LLM-heavy code.
How it fits NativeA Charter rule (Charter is a system property) scoped to exactly the Internal System's five glue engines — coordination, priority, audit, adaptation, identity — and explicitly NOT to LLM effectors, preserving the page's 'deterministic surface around a stochastic core' (P12) boundary. NEW: `glue-determinism` charter rule template plus a replay test harness attached to the glue engines' verify-templates.
Build sketch
  1. Write charter rule template `glue-determinism` into the Internal System charter: glue-engine code may not read wall-clock/random or do I/O outside record reads/appends; LLM effectors exempt by name.
  2. Build a replay harness: run each glue engine twice over the same recorded slice fixture; any output diff = non-determinism failure.
  3. Wire the harness into each glue engine's verify-template with a per-engine fixture slice.
  4. Require any glue step needing external input to declare it as a record read, so replay stays exact.
Depends onF-ENG-01 (record spec to replay against); founder ratification of the replay-for-glue-only split (engine.md §3 row 4 / §5)
Decision needed (founder)Do the five glue engines accept the full determinism tax (no wall-clock/random/direct I/O), or a weaker audit-grade discipline?

F-ENG-04 Three-phase blueprint patchingREUSE-AS-ISEffort LTODO

SourceTemporal versioning — https://docs.temporal.io/develop/python/versioning
What industry runsTemporal is the only tradition with a governed answer to 'the blueprint changed under a live instance': patch (new code behind a named marker; old executions replay the old branch), deprecate (once old executions finish), remove (after retention). Worker Versioning alternatively pins executions to the revision that started them.
How it fits NativeThe means-dial amendment protocol the two-dials model currently lacks. Lands on the Workflow object's governance ledger (PROPOSED → ACTIVE → PERSISTED → RETIRED) and composes with the ruled invariant 'the written half never mutates at run time'. NEW: `patches[]` field on the Workflow primitive (`primitives/workflow.md`, 15 fields today) + patch markers written into the engine's record_slice.
Build sketch
  1. Add `patches[]` to the workflow schema in primitives/workflow.md: {patch_id, introduced_at, phase: patched|deprecated|removed}.
  2. Write the amendment protocol into the Workflow lifecycle section: editing an ACTIVE workflow requires a patch entry; runs born pre-patch replay the old branch via a marker row in record_slice.
  3. Add `sutra-native workflow patch` / `deprecate-patch` commands writing phase transitions to the governance ledger.
  4. Hook-gate direct edits of ACTIVE workflow files without a patch entry; reroute to the protocol.
  5. Deprecate rule: phase 2 permitted only when the record shows zero open runs pinned to the pre-patch branch.
Depends onBA-03 (Workflow runtime registry — behind a founder decision) + BA-04 (workflow_id); F-ENG-01
Decision needed (founder)What retention window closes phase 2 — when are all old engine runs considered finished so markers can be removed?

F-ENG-07 Written-vs-grown conformance scoreREUSE-AS-ISEffort MTODO

SourceProcess-mining conformance checking — https://www.processmining.org/conformance.html
What industry runsConformance checking computes the divergence between a written model and its grown event log as numbers: fitness (can recorded traces replay on the model?) and precision (does the model allow behavior the log never shows?), via token replay (fast, heuristic) or alignments (optimal, expensive).
How it fits NativeMakes the means dial (written vs grown) numeric — the page holds it as a concept only. Lands as a `divergence` field beside BA-06's evidence read-model fields (unit_ref, window, run_count, output_variance, outcomes[], cost); reads `workflow.step_graph` as the written model and the record_slice as the grown log; the audit glue engine consumes the score (it already flags 'green-never-consulted instruments').
Build sketch
  1. Implement token-replay fitness: replay each recorded run's step sequence against workflow.step_graph; count missing/remaining steps.
  2. Compute precision: fraction of step_graph edges never exercised in the record window.
  3. Add `divergence: {fitness, precision, window}` to the BA-06 evidence read-model spec.
  4. Render the score on the Engine status surface; audit glue engine raises a finding below threshold.
  5. Hold any automatic consequence until the founder rules the threshold (composes with the §4.8 blueprint-freshness gap).
Depends onBA-03 (machine-readable step_graph instances) + F-ENG-06 or F-ENG-02 (typed record); BA-06 evidence spec (A3 UNRULED)
Decision needed (founder)What divergence threshold flags a rotting blueprint, and does crossing it trigger re-verification or just a finding?
