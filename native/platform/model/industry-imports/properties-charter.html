F-CHR-01 Charter CHANGE-CONTROL blockREUSE-AS-ISEffort STODO

SourceISO 9001 document control (clause 7.5.3) — https://www.isotracker.com/blog/document-control-in-iso-90012015-what-the-standard-requires/
What industry runsISO 9001 clause 7.5.3 imposes nine controls on every controlled document: availability, distribution/access, retrieval, storage, change control, version history, obsolete protection, retention, protection. A named approver owns each document, and changing a procedure outside the chain is itself an auditable nonconformity. Runs at 1.2M+ certified sites.
How it fits NativeLands in the Charter contract (properties.html s5) as a NEW mandatory `change_control` block beside domain_ref/authority/constraints/invariants/obligations, applied to both charter populations: the 13 prose docs at sutra/os/charters/ and the 163 C-*.json stubs at user-kit/charters/. The ruled invariant 'mutation is operator-only through a gate' already exists — this gives the gate a per-charter approver and version history to check against.
Build sketch
  1. Add `change_control: {approver, version, history[], supersedes}` to the C-*.json charter schema; backfill all 163 stubs (approver=founder, version=1).
  2. Add the same block as a metadata header template to the 13 prose charters in sutra/os/charters/.
  3. Extend the charter acl / permission-gate.sh identity-glue gate: reject charter edits where the acting operator does not match change_control.approver (or lacks an approval marker).
  4. Emit a version bump + history row on every gated charter mutation; archive superseded versions, never delete (obsolete-protection).
  5. Add a lint that fails any charter file missing the block; wire into the daily governance audit.
Depends onnone (shares the governance header with F-CHR-13 — land together)
Decision needed (founder)Does every Charter get its own ISO-style named-approver chain, or is repo-write authority (OPA-style) enough for T2-T4 client tiers?

F-CHR-02 Charter-edit nonconformity findingREUSE-AS-ISEffort MTODO

SourceISO 9001 — https://en.wikipedia.org/wiki/ISO_9000
What industry runsIn ISO 9001, changing a process definition without following document control is itself an auditable nonconformity: a recorded finding that requires a corrective-action record, with closure verified at the next audit. The exception becomes a controlled record rather than a silent event.
How it fits NativeLands in the audit glue engine — one of the 5 pre-provisioned Internal System engines; properties.html s6 notes the glue is real today (permission-gate.sh, enforce-boundaries.sh) but undeclared. NEW: a nonconformity finding record type in the audit engine's record slice, emitted when a write to sutra/os/charters/** or user-kit/charters/*.json bypasses F-CHR-01's change_control chain. This is X2 turned on the Charter itself.
Build sketch
  1. Add a PostToolUse/audit hook watching writes to sutra/os/charters/** and user-kit/charters/*.json.
  2. On mutation, check the diff against the charter's change_control block: approver match + version bump present.
  3. On mismatch, append a finding row {charter_id, actor, ts, diff_ref, rule:'change-without-approval'} to the audit engine's findings JSONL.
  4. Require a corrective-action Work-Atom (sutra-atom open, verify = finding resolved) before a finding can close.
  5. Surface open findings in the daily governance audit report.

Step 3 below is also the first runtime read of the charter→domain binding, closing the properties s6 gap 'binding unread by the atom runtime'.
Build sketch

  2. Add charter rule form `sign_off_required: {atom_class_pattern, approver}` to the Charter contract's constraints list.
  3. At sutra-atom open, resolve the governing charter via domain_ref and stamp sign_off if a rule matches.
  4. In cmd_close, after verify passes, block close until an approval marker from the named approver (distinct from the executing actor) exists; log both identities to the atom ledger.
  5. Fixture test: a same-actor verify+sign-off attempt dies with a separation-of-duties message.

How it fits NativeA first-class Charter section — the first concrete content model for the empty `authority` object on the 163 C-*.json stubs. Build sketch

  2. Author one real table for a lending charter: W-disburse-loan amounts (auto <=50K, credit-ops-lead <=5L, credit-committee >5L).
  3. Extend permission-gate.sh / dispatch-gate.sh to resolve the acting unit's decision_type + magnitude against the governing charter's doa rows, returning auto | named-approver | escalate.
  4. Log every doa consultation (matched row + outcome) to the audit slice — 'provable afterward'.
  5. Lint: bands must tile without gaps or overlaps per decision_type (fixture test in the F-CHR-07 lane).

F-CHR-06 Charter-to-hook compilation (deny-by-default)ADAPTEffort LTODO

SourceOPA/Rego policy-as-code — https://www.openpolicyagent.org/docs/latest/policy-language/
What industry runsOPA policies are versioned, testable code: `default allow := false` with allow only on explicit conditions; partial `deny contains msg` rules accumulate machine-readable reasons; the policy is consulted per request via a decision query. Kubernetes admission control unions all deny rules and returns allowed=false with reasons.
How it fits NativeThe Charter execution path. Today's identity-glue gates (permission-gate.sh, enforce-boundaries.sh, build-layer-check.sh, dispatch-gate.sh) already behave deny-by-default-with-reasons but are hand-written and disjoint from the charter files — the implementation.html s7 gap: 'identity-glue gates check shape, not rules'. NEW: a `charter-compile` step that generates hook predicates FROM C-*.json rule rows, making Charter-to-hook compilation the declared path instead of parallel hand-maintenance.
Build sketch
  1. Define an executable rule form in the charter schema: {rule_id, applies_to (tool/path/decision_type), condition, effect: deny, reason}, default-deny per applies_to scope.
  2. Write `charter-compile` in holding/bin/: reads a C-*.json, emits a predicate ruleset under the plugin hooks' read path.
  3. Pilot on one gate: permission-gate.sh loads compiled rulesets and unions deny reasons into its block message, using a lending charter rule (KYC not CLEAR -> deny disbursal atoms).
  4. On any gated charter mutation (F-CHR-01), recompile automatically; stale compiled artifacts fail a freshness check.
  5. Migrate remaining gates one at a time; surviving hand-written rules get back-ported into charter rows.
Depends onF-CHR-01 (recompile trigger); charter content-model ruling; rule-type vocabulary from F-CHR-05/F-CHR-12/F-CHR-14
Decision needed (founder)Deny-by-default (OPA) vs constraint-minimal freedom (VSM/mission command) — which is the default posture for a new system's Charter, and which contexts flip it?

  4. Wire into the daily governance audit and into every charter recompile (F-CHR-06 step 4).
  5. Log runtime gate decisions (input hash + rule + outcome) so production divergence from fixtures is detectable.

What industry runsCommander's intent has exactly three fields — expanded purpose (why), key tasks (what must happen, never how), end state (conditions defining done) — kept to five-six lines.   3. Lint the brief: end_state must derive from the atom's declared verify; key_tasks carry no method verbs (LLM check).

Build sketch
