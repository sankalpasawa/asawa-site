F-ATM-01 Verify-mode flag: DO-CONFIRM vs READ-DOREUSE-AS-ISEffort STODO

SourceChecklists/Gawande — https://www.shortform.com/blog/checklist-checklist/
What industry runsGawande's checklist discipline requires every checklist to declare its execution mode explicitly: DO-CONFIRM (work from memory, then pause and confirm all items done) or READ-DO (execute each item as you read it, recipe-style). The WHO surgical checklist ran this discipline and cut in-hospital deaths 1.5% to 0.8%. Expert executors on hot paths want DO-CONFIRM; novel or high-risk work wants READ-DO.
How it fits NativeLands on the Work-Atom Contract data model (work-atom.html s5): NEW field `verify_mode: confirm-after|step-through` beside the existing `verify` field (3 pinned templates: file-exists, grep-count, named-test). Written into atom.json by `holding/bin/sutra-atom` at open, same enforcement point as the goal+verify pairing (sutra-atom:267). The step-through branch only becomes meaningful once the atom's internal-steps representation (open TODO in s7) is ruled.
Build sketch
  1. Add `verify_mode` enum field (confirm-after | step-through, default confirm-after) to the atom schema in holding/bin/sutra-atom cmd_open; bump SCHEMA_VERSION with null-safe old-key read per the 0.2->0.3 precedent at sutra-atom:32.
  2. Branch cmd_close: confirm-after runs the single verify once at close (today's behavior); step-through stores the flag now and runs the verify after each internal step once the internal-steps field exists.
  3. Add the field row to the work-atom.html s5 Contract data-model table, source 'Gawande DO-CONFIRM/READ-DO'.
  4. Write a Charter rule template: charter-flagged high-risk atom classes (e.g. lending money movement) default to step-through; hot-path C1+ HOWs default to confirm-after.
  5. Verify: `sutra-atom open ... && jq '.verify_mode' atom.json` returns confirm-after; opening with --verify-mode step-through persists the value.
Depends onInternal-steps representation ruling (work-atom.html s7 TODO) for the step-through branch; report Q1 founder ruling on per-class defaults
Decision needed (founder)Default verify_mode per atom class — DO-CONFIRM for expert hot-path classes, READ-DO for novel/high-risk?

F-ATM-02 Pause points: verify placement anchored to named breaksADAPTEffort MTODO

SourceGawande/WHO — https://www.nejm.org/doi/full/10.1056/NEJMsa0810119
What industry runsThe WHO surgical checklist put 19 items at exactly THREE named pause points (Sign-In before anesthesia, Time-Out before incision, Sign-Out before the patient leaves the OR) rather than gating every step — and cut deaths ~47% and major complications ~36%. The checklist is anchored to a natural break in the action, never free-floating.
How it fits NativeLands in the Workflow schema, not the atom: NEW `pause_points[]` field on the canon workflow type at primitives/workflow.md (15 fields, step_graph) that BA-05's registry validates. Pause-point steps carry the heavyweight gate-grade verifies (external-env kind, human acceptance per the R8 split); steps between pause points still carry their ONE verify per X1, but at Charter-floor weight (F-ATM-07). In W-disburse-loan terms: the pre-disbursal pause point holds the 5-killer-item gate atom.
Build sketch
  1. Add `pause_points[]` (list of {step_id, name}) to the workflow canon type spec in primitives/workflow.md.
  2. Extend BA-05 registry validation: every declared pause_point must reference an existing step in step_graph; parse failure rejects registration.
  3. Write the placement rule: a pause-point step's atom must carry a gate-grade verify (verify_kind external-env or tool per F-ATM-12); non-pause steps may run at Charter-floor weight without extra human gates.
  4. Declare the first instance on W-disburse-loan: pause point 'pre-disbursal' on the gate step (sanction signed, KYC verified, penny-drop confirmed, amount match, no duplicate active loan).
  5. Document the field on the workflow-engine.html model page and cross-link from work-atom.html s2.
Depends onBA-05 (workflow registry founder decision — pause points need a registered workflow shape to live on); F-ATM-07 (Charter floor defines the non-pause weight); F-ATM-12 (verify-kind vocabulary)
Decision needed (founder)Does X1 permit lighter (floor-only) verifies on non-pause steps, or must every atom's verify stay gate-grade regardless of pause placement?

SourceTWI Job Instruction — https://artoflean.com/reference/job-instruction/
What industry runsTWI's 4-step cycle: prepare the learner; present in three passes (steps, +key points, +reasons); try-out where the learner performs WHILE stating back key points and reasons; tapered follow-up. Accountability is inverted — 'if the worker hasn't learned, the instructor hasn't taught' — so the verify sits on the transmitter, not the receiver.
How it fits NativeNEW transfer protocol attached to the HOW particle's C-state machinery (A9: gated C0->C1 reuse_tag promotions, work-atom.html s4 Growth row). Handing an atom class's HOW to a new executor requires a transfer atom whose verify is the teach-back; failure is logged against the transmitting engine in the atom ledger, not the learner. Qualification records live on the reuse_tag index row that BA-08 builds; dispatch-gate consults them at bind.
Build sketch
  1. Define a transfer-atom template: goal 'executor X qualified on HOW class Y'; verify = a performed try-out run passes the class verify AND stated-back key_points/reasons match how.key_points/how.reasons (LLM-graded).
  2. Add `qualified_executors[]` to the BA-08 reuse_tag index row schema, listing executors that passed try-out for that HOW class.
  3. Write the Charter rule template: dispatching a C1+ HOW to an executor absent from qualified_executors requires a transfer atom first; transfer failure appends an audit finding against the TRANSMITTER.
  4. Wire holding/hooks/dispatch-gate.sh: at bind, check qualified_executors for atoms whose HOW carries reuse_tag C1+; block with the rule id when unqualified.
  5. Verify: `sutra-dispatch bind` on a C1 HOW with an unlisted executor exits 2; ledger carries the transmitter-charged finding after a failed transfer.
Depends onF-ATM-04 (key_points/reasons are the teach-back content); BA-01; BA-08 (reuse_tag index); A9 promotion machinery
