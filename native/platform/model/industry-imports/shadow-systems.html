F-SHD-01 Auto-spawn trigger predicatesREUSE-AS-ISEffort STODO

SourceICS / PagerDuty / Google SRE — https://sre.google/sre-book/managing-incidents/
What industry runsAn alert becomes a declared incident when ANY observable predicate fires: a second team is needed, customers can see the outage, or the issue is unsolved after one hour of focused analysis. The overlay is forced into existence by charter-level rules, not by an escalation judgment call.
How it fits NativeNEW: charter rule type `spawn-shadow-on(predicates)` attaching to the Charter system property (today 163 auto-minted C-*.json stubs, shape-without-rules; the charter content model is the s7 open question on implementation.html). Evaluation attaches as a new detector beside the Internal System's six EMERGE NAMED-PAIN detectors that already read the record; its action is 'mint shadow system from Assembly template' instead of 'propose'. The minted object lands on the shadow contract of shadow-systems.html §s5 (charter, own glue engine, coordinated-standing-system refs, verify) — as a stub JSON birth record until the System schema exists (W5).
Build sketch
  1. 1. Add a `spawn_shadow_on: [{predicate, threshold, use_case_tag}]` array to the C-*.json charter stub schema; ship the three ICS predicates (second_system_needed, customer_visible, unsolved_minutes>60) as the default table.
  2. 2. Write a detector script in the EMERGE detector style that evaluates the predicates over .sutra/flow-ledger.jsonl rows and open-atom age (BA-03 workflow_id keying makes the per-workflow query possible).
  3. 3. On predicate truth, mint the shadow birth record (goal, coordinated standing-system refs, charter ref, use_case_tag) and emit an EngineEvent + audit ledger row.
  4. 4. Fixture test: synthetic ledger rows crossing the >1h-unsolved predicate spawn exactly one shadow record; rows below threshold spawn none.
  5. 5. Lending fixture: disbursal-pipeline halt marked customer-visible spawns the overlay across Disbursal + Treasury + KYC standing-system refs.

What industry runsPagerDuty's severity ladder determines which roles activate: SEV-1/2 spawn the full major-incident org with an IC, SEV-3 pages only the service team, SEV-5 is a ticket. The overlay provisions more of its own organization as a function of the declared severity — elastic cost, small incident gets small overlay.
How it fits NativeAttaches to Ruling 1 pre-provisioning on shadow-systems.html §s5: charter + internal-system slots are hardcoded from birth and 'empty is fine' — the SEV dial is the policy that decides which of the five glue slots (coordination, priority, audit, adaptation, identity — S1..S5 on internal-system.html) instantiate ACTIVE versus stay empty. NEW: `severity` field on the shadow spawn contract plus a slot-activation map in the shadow Assembly template. No schema change to the Internal System itself; report §4 row 6 warns that without this dial our overlays are SAFe-shaped cargo cult.
Build sketch

  2. 2. Write the slot-activation map into the shadow Assembly template: e.g. SEV-1/2 -> all five slots; SEV-3 -> coordination + audit only; SEV-4/5 -> coordination only.
  3. 3. Make glue-slot instantiation at spawn read the map and mark unactivated slots empty (Ruling 1 already permits this).
  4. 4. Emit an audit row listing which slots activated and why; severity upgrade re-runs activation and appends a delta row.
  5. 5. Fixture test: SEV-3 spawn creates record slices for exactly two glue slots.

SourceICS — https://response.pagerduty.com/training/incident_commander/
What industry runsThe Incident Commander becomes the highest-ranking individual on any major incident call regardless of day-to-day rank, with power to remove even the CEO — scoped strictly to the overlay's lifetime. Authority inverts at declaration and reverts automatically at close.

  3. 3. Append grant + revoke EngineEvent pairs to the audit glue engine's record slice (same two-event shape A7 records for delegation edges).
  4. 4. Make Approval routing for ESCALATED atoms inside the shadow's scope resolve the ruler via active inversions first, org seniority second.
  5. 5. Fixture test: an inversion older than its shadow's close event fails the audit sweep (expiry cannot be skipped).

What industry runsICS re-issues a fresh written Incident Action Plan every operational period, derived through a fixed chain: 202 objectives -> 215 tactics -> 204 assignments. The blueprint is re-grown on cadence instead of drifting — plan decay inside a live incident is solved structurally.
How it fits NativeLands in the shadow's OWN glue engine (shadow-systems.html §s5: 'the shadow's OWN coordinator, owned by none of the standing systems'), as its coordination behavior. NEW: `operational_period` field on the spawn contract plus a period-end re-plan loop. Each period's blueprint is a registered Workflow in the user-kit registry (~/.sutra-native/user-kit/workflows/ — BA-05 territory), so the re-issued plan is the same Workflow object everything else uses, not a shadow-specific formalism (report §4 row 4: any second notation dies the CMMN death).
Build sketch
  1. 1. Add `operational_period: <duration>` to the shadow birth record; declare it at spawn.
  2. 2. At period end, the shadow glue engine opens a re-plan Work-Atom via holding/bin/sutra-atom (goal: fresh period blueprint; verify: registered Workflow file parses and every step carries a verify).
  3. 3. Write the new blueprint as W-<shadow-id>-p<N>.json into ~/.sutra-native/user-kit/workflows/; archive the previous period's file, never edit it in place.
  4. 4. Log planned-vs-actual deviations from the closing period into the shadow's activity log before the new plan is cut.
  5. 5. Lending fixture: disbursal-outage shadow re-issues period-2 objectives ('verify no double-disbursals') as a new registered Workflow.
Depends onBA-05 (workflow registry + founder registry decision); F-SHD-01

Build sketch

  2. 2. Make F-SHD-01's mint step write the birth record as the shadow's first slice entry.
  3. 3. Hook atom lifecycle events within the shadow's scope to append activity-log rows automatically (writer: the audit glue slot).
  4. 4. Generate the status snapshot as a read-only view over the other slices, BA-11 shelf-view style — never hand-authored.
  5. 5. Fixture test: a spawned shadow with zero manual writes still has a valid birth record and a non-empty activity log after its first atom closes.

SourceICS 221 — https://training.fema.gov/emiweb/is/icsresource/assets/ics%20forms%20descriptions.pdf
What industry runsICS 221 ensures every resource checking out has completed all incident business before release — a per-resource checklist that gates dissolution. Nothing borrowed leaves un-returned; the overlay cannot end by evaporation.
How it fits NativeAttaches to the retirement stage of the shadow lifecycle (shadow-systems.html §s5: 'retires when its verify passes'). NEW: a demob gate inserted between verify-pass and dissolved — one close Work-Atom per borrowed resource listed in the birth record, opened via the existing holding/bin/sutra-atom. For resources reached through crossing edges, the check-out verify is the A7 revoke shape (Approval + typed edge + two EngineEvents). Report §4 row 7: a disband RULE without this CHECKLIST historically does not produce disbanding — this makes the 'never mutate standing systems' promise auditable at close.
Build sketch
  1. 1. Track a `borrowed_resources[]` list in the birth record (seats pulled from standing systems, delegation grants, compute/budget envelopes).
  2. 2. On retirement trigger, auto-open one close Work-Atom per resource via sutra-atom open, verify template: 'resource returned / grant revoked, EngineEvent pair present' — an external check, never self-declared.
  3. 3. Block the dissolution ledger row until every check-out atom is CLOSED; a shadow with open check-outs cannot reach dissolved state.
  4. 4. Append a demob-complete row to the audit slice referencing all check-out atom ids.
  5. 5. Lending fixture: disbursal-outage shadow cannot dissolve while the Treasury on-call seat is still assigned to it.
Depends onA7 delegation-edge spec (revoke semantics); F-SHD-05 (birth record lists the resources)

F-SHD-10 Nine-pathology drift watch-listADAPTEffort MTODO

SourceDavis & Lawrence 1978 — https://hbr.org/1978/05/problems-of-matrix-organizations
What industry runsThe canonical catalog of what happens when a temporary overlay refuses to die: power struggles, anarchy, groupitis, collapse under crunch, excessive overhead, decision strangulation, sinking, layering, navel gazing. Fifty years of matrix failure reduced to nine named, observable signatures.
How it fits NativeLands in the adaptation glue engine slot (S4 on internal-system.html — the second-order loop) as a runnable watch-list over live shadows, sibling in kind to the six EMERGE NAMED-PAIN detectors that already read the record. NEW: pathology predicates evaluated over the shadow record slices F-SHD-05 defines — layering reads birth records (a shadow whose parent is a shadow), strangulation reads atom wait-times in the ledger, permanence reads shadow age against its endpoint. Findings file into the adaptation engine's proposal queue for human ruling, never auto-act.
Build sketch
  1. 1. Encode each adoptable pathology as a predicate over record slices: layering = birth record with shadow parent; strangulation = median atom wait-on-approval above threshold; sinking = shadow atoms touching systems outside its declared scope; permanence = age > N operational periods with endpoint-verify unmet and unamended; groupitis = ratio of coordination events to closed atoms above threshold.
  2. 2. Run the predicate sweep on the audit cadence alongside the existing daily governance audit pattern (holding/scripts/daily-governance-audit.sh is the named glue precedent on shadow-systems.html §s6).
  3. 3. File each hit as a finding row into the adaptation engine's proposal queue shelf with the evidence rows attached.
  4. 4. Route persistent findings (same pathology, 3 sweeps) to Approval — a human rules on kill / restructure / promote.
  5. 5. Fixture test: a synthetic shadow spawning a sub-shadow trips the layering predicate on the next sweep.
Depends onF-SHD-05 (record slices to read); F-SHD-04 (operational periods for the permanence clock)
