F-WFL-01 Machine-validated Workflow specADAPTEffort LTODO

SourceAmazon States Language (ASL) — https://states-language.net/spec.html
What industry runsASL publishes the workflow-definition language as a standalone spec with required fields (States, StartAt, per-state Type, Next/End) and every state machine is machine-validated against that spec before any execution can start. Malformed blueprints die at authoring time, not at run time. It is the only industry tradition with a formal, published blueprint schema.
How it fits NativeThe canon type already exists — primitives/workflow.md, 15 fields including step_graph, pattern, failure_policy (workflow-engine.html s5/s6) — but it is a type doc with zero runtime instances and no validator. This lands as NEW: a versioned machine validator attached to the BA-05 registry (~/.sutra-native/user-kit/workflows/), whose own verify already demands 'parses against the canon type; every step carries a verify'. The spec formalizes BA-05's parse check into a versioned schema plus a runnable gate on registration and on FOLLOW resolution (ADR-026).
Build sketch
  1. Extract the 15-field canon type from primitives/workflow.md into a versioned JSON Schema (workflow.schema.json) with required fields: goal, step_graph[], per-step verify, failure_policy, plus a spec_version field.
  2. Write a validator command (holding/bin or sutra-native validate-workflow <file>) that validates any W-*.json against the schema and rejects any step lacking a verify.
  3. Wire the validator into BA-05 registration: a file enters ~/.sutra-native/user-kit/workflows/ only after validation passes.
  4. Gate FOLLOW resolution (ADR-026 path) so it refuses unvalidated/unregistered workflow files.
  5. Mint the spec decision as an ADR via the D54 canon route (NATIVE-ENGINE.md + new ADR).
  6. Verify: register W-kyc-verify with one verify-less step -> validator exits non-zero; fix -> registration succeeds.
Depends onBA-05 (founder registry decision); composes with F-WFL-13
Decision needed (founder)Internal validation tool only, or an open spec inviting outside implementers? ASL's near-zero external adoption without open governance is the warning (report section 5 TODO).

F-WFL-02 Retry/Catch error algebra as failure-policy fieldsREUSE-AS-ISEffort STODO

SourceAmazon States Language (ASL) — https://states-language.net/spec.html
What industry runsASL's Retrier (ErrorEquals, IntervalSeconds default 1, MaxAttempts default 3, BackoffRate default 2.0, MaxDelaySeconds, JitterStrategy) plus Catchers (ErrorEquals, Next) plus reserved error names (States.ALL, States.Timeout, ...) form the most complete declared-failure vocabulary in industry, spec-defined with defaults. Industry has retry-without-verify; Sutra has verify-without-retry — this is the missing half.
How it fits NativeLands as the concrete content of workflow.failure_policy (existing field on primitives/workflow.md, today typed only as 'policy') and as failure-policy fields on the Work-Atom envelope sitting NEXT TO the atom's ONE verify, never replacing it. Composes with charter.retry_budget (A8, UNRULED, REC default 3) and how.attempt_log; BA-02 already enforces a retry budget at sutra-atom close — this replaces its hard-coded budget with declared per-atom fields.
Build sketch
  1. Define the failure_policy sub-schema on the workflow canon type: retry[] {error_equals[], interval_s, max_attempts, backoff_rate, max_delay_s} + catch[] {error_equals[], next} + reserved Sutra error names (e.g. Sutra.VerifyFail, Sutra.Timeout).
  2. Add the same fields to the atom envelope in sutra-atom open (SCHEMA_VERSION bump with null-safe legacy read, per the BA-01 0.2->0.3 precedent).
  3. Make the sutra-atom close fix-loop read the declared retry fields instead of a fixed 3 (extends BA-02); attempts keep logging to how.attempt_log.
  4. Verify: test atom with max_attempts=2 whose verify fails twice -> close dies with ESCALATED; jq shows the retry fields on atom.json.
Depends onA8 ruling (retry_budget home); BA-01, BA-02
Decision needed (founder)Do failure-policy fields live on the Work-Atom, on the Workflow step, or both with override (report section 5 TODO)?

What industry runsAn Airflow Sensor makes an external-world condition an explicit first-class step: wait until the bank settlement file lands, until an API condition holds. The check is external to the actor doing the work, so it cannot be gamed by self-declaration.
How it fits NativeLands in the Work-Atom verify-kind vocabulary: a verify.kind enum on the atom's verify field (workflow-engine.html one-goal-ONE-verify invariant) with environment kinds — file-exists, api-condition, alarm-cleared, ledger-delta. Site of record: sutra-atom's verify-template plus the step verify field on primitives/workflow.md.
Build sketch

  2. Make sutra-atom close execute env-kind checks mechanically (test -f / curl / jq predicate) before accepting close — no self-declared pass for env kinds.
  3. Add a Charter preference-ladder rule: external-world check > independent tool check > self-declared (twin of F-ATM-12; this card owns the workflow-step side).
  4. Verify: W-emi-reconcile fixture step whose verify is 'settlement file present AND ledger delta = 0' — close fails while the fixture file is absent, passes once present.
Depends onnone (F-ATM-12 is the atom-side twin)

F-WFL-05 Variance note — per-step deviation recordREUSE-AS-ISEffort STODO

SourceClinical pathways — https://www.sciencedirect.com/topics/medicine-and-dentistry/care-pathway
What industry runsClinical pathways chart every pathway element as met or varied; a variance note records planned vs actual plus mandatory rationale. Deviation is legal and analyzable, not an error — philosophically distinct from BPMN (divergence = error) and ISO (divergence = nonconformity). It converts blueprint drift into data.
How it fits NativeLands as an Engine record-slice row schema. The record slice is one of the Engine's four stores (workflow-engine.html s2); the closest store on disk is .sutra/flow-ledger.jsonl (BA-03 adds workflow_id). NEW row type 'variance': {workflow_id, step_ref, planned, actual, rationale, ts, actor} — distinct from the verify-fail decision_trail (verify-fail = check failed; variance = check passed but the path deviated).
Build sketch
  1. Define the variance row schema in the flow-ledger writer (one writer, append-only stays true): workflow_id, step_ref, planned, actual, rationale, ts, actor.
  2. Emit a variance row whenever a FOLLOWed run executes a step differently from the registered workflow's step_graph (skip, reorder, substitute).
  3. Enforce mandatory rationale: the writer rejects variance rows with an empty rationale field.
  4. Give the adaptation glue engine a standard read: variance count per step per window -> blueprint-revision candidates.
  5. Verify: replay a W-md-authoring run with one skipped step -> exactly one variance row, rationale non-empty.
Depends onBA-03 (workflow_id on flow-ledger); BA-05 (a registered blueprint to deviate from)

F-WFL-06 Migration plan for a Workflow under a living EngineADAPTEffort LTODO

SourceCamunda — https://docs.camunda.org/manual/latest/webapps/cockpit/bpmn/process-instance-migration/
What industry runsA Camunda migration plan is a set of source-activity -> target-activity mappings between two definition versions; a draft is auto-generated for unchanged activities, active-but-unmapped activities are flagged, and the plan is complete only when instructions cover ALL active source activities. It is industry's engineered answer to 'blueprint changed mid-run'.
How it fits NativeNEW: a life-dial migration protocol attaching to the Workflow object state machine (PROPOSED -> ACTIVE -> PERSISTED -> RETIRED, workflow-engine.html) and the Engine's record slice. Runs pin to the workflow version they started under (needs the stable workflow_id BA-03 introduces plus a version field the canon type lacks); amending a Workflow whose Engine has open atoms requires a migration map covering every open atom before the new version activates.
Build sketch
  1. Add workflow_version to the canon type and stamp it (with workflow_id) onto every flow-ledger run row, pinning runs to the version they started under.
  2. Write sutra-native migrate-workflow --from vN --to vN+1 --map <json>: refuses to complete unless every open atom (ledger rows with no close) is mapped source-step -> target-step.
  3. Auto-generate a draft map for steps unchanged between versions; flag unmapped active steps by id.
  4. Log the migration as an audit-engine event; the record slice keeps rows from both versions, queryable by workflow_version.
  5. Verify: attempt migration with one unmapped open atom -> command dies naming the atom; map it -> migration completes.
Depends onBA-03, BA-05; pending founder ruling — is mid-run amendment legal in v1 or force run-to-completion (report section 5 TODO)

The counter-lesson is ASL: a published spec under single-party control got near-zero external adoption.
How it fits NativeNEW: a Sutra conformance suite attaching to the plugin distribution layer (L0, the T4 fleet channel) — example Workflow files plus expected validation/resolution outcomes, runnable against any Sutra instance. It tests the F-WFL-01 spec plus RESOLVE behavior (ADR-026). Only worth building once more than one Sutra instance exists; F-CHR-15 is the charter-side kin (fixtures for charter-executing hooks).
Build sketch

  2. Write a runner script: validate + resolve each fixture on the target instance and diff actual vs expected.
  3. Ship the runner in the plugin bin (L0) so any fleet instance can self-test after install/update.
