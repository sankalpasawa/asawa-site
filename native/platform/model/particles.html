Particles — goal, constraints, context, HOW PLATFORM · zoom 4

Work-order header

idband / parentstatusversionowner
platform-model-particlesPLATFORM / platform-the-modelDRAFTv1claude

Purpose

Particles are the four sub-atomic parts every unit of work is made of: goal, constraints, context, and HOW. They repeat at every level of the model — self-similarity is the design — but none can run alone: a particle has no verify and no state of its own. They exist so the smallest accountable unit, the Work-Atom, is fully specified before anything runs: what done looks like (goal), what must hold regardless of progress (constraints), what slice of the record the motor may read (context), and which motor runs (HOW). Ruled in A1-ext (founder sitting 2026-08-05); the fourth particle was renamed to HOW in A1-FINAL-3 (2026-08-06), removing the word "work" everywhere, including the pending runtime field rename.

How it works

Each particle carries a ruled definition and a runnable test. The tests are mis-cut detectors: an atom whose particles fail their tests is wrongly cut, not merely under-documented. The four boxes in the hub diagram show the particles inside their Work-Atom container.

ParticleRuled definition (A1-ext)Runnable test
goalTarget state + the check that detects it. The check is the atom's ONE verify.No verify = a wish, not a goal.
constraintsConditions that hold independent of goal progress.Checkable without knowing progress.
contextMinimal record slice the HOW needs.Remove it → quality drops; add to it → only cost grows.
HOWThe swappable motor — skill | LLM | code. Home of the C-state and the attempt log.Swappable without touching the other particles; otherwise the atom is mis-cut.
Naming history: A1-ext originally named the fourth particle "means". A1-FINAL-3 supersedes that: the particle is HOW, and the word "work" is removed everywhere — including the runtime field rename work → how (see implementation today).

When an atom's how is undecided, it defaults to the intelligence floor — hand it to the LLM (A1-FINAL ladder, rung 1). An atom is atomic in accountability, not size: one goal, one verify, 1..n internal steps; the moment an internal step needs its own verify, split into two atoms.

The attempt log — a data field on HOW, never an object

Attempt was deleted as a ladder noun (A1-FINAL-3). It returns only as a logged field on the HOW particle: an attempt count plus history, kept for systemic purposes. Each live run of the atom increments it. The retry budget reads this field to decide whether another attempt is allowed.

RULED as REC — A8 (sheet §11, Quick eight: "A2 A3 A5 A6 A8 A10 as REC; budgets = labeled v1 dials", sitting concluded 2026-08-17): the retry budget lives in the Charter as retry_budget (default 3), a labeled v1 dial. Canonical owner of the budget's home: Properties s5 — charter contract; this page keeps only the attempt-log mechanics. The S6 walkthrough gap ("attempt 2 of N — N undefined") is closed by the ruling; runtime enforcement remains a build gap (see s6).

C-state — crystallization stage lives on HOW

The crystallization loop that moves a HOW up its C-ladder — declare at authoring, earn at runtime. Only the C0→C1 rung is canon today; the rest of the loop is DEFERRED until run data exists (s7).

How a HOW gets chosen: the lens primitive (value ⇆ axis) cutting DOWN (decompose), UP (generalize), or ACROSS (reframe). Canonical owner: Method §3 — this page depends on it for the lens doctrine and its labels (Realization / Reflection).

A9 (ruled by consequence of A1-ext): the crystallization stage of an atom's motor lives on the HOW particle, written side. Workflow and Engine C-state is a derived aggregate over their atoms' HOW particles — mixed stages are allowed. Promotions are earned by attempt evidence, and are always proposed and gated, never automatic. Today only the C0→C1 rung (via reuse_tag) is canon; everything past C1 is deferred until run data exists.

Invariants

  • Sub-atomic: no particle runs alone — no verify, no state of its own (A1-ext).
  • One goal, ONE verify per atom; an internal step needing its own verify means split into two atoms — atomic in accountability, not size.
  • Goal test: no verify = a wish, not a goal.
  • Constraints test: checkable without knowing goal progress.
  • Context test: remove → quality drops; add → only cost grows.
  • HOW test: swappable without touching the other three particles; failing this test means the atom is mis-cut.
  • Attempt is never an object or ladder noun — only logged data on HOW (A1-FINAL-3).
  • C-state lives on HOW; Workflow/Engine C-state is a derived aggregate, mixed allowed; promotions earned by attempt evidence (A9).
  • Particles repeat at every level of the ladder — self-similarity (A1-FINAL, rung 0).
  • X1: the atom the particles compose always sits in a Workflow — a single atom is a workflow of one. X2: every run happens inside an Engine, writing to its record slice from run 1.

Lifecycle

  • Authored (written side): all four particles fixed at atom construction; the goal's check pre-declared before any run.
  • Run (grown side): each attempt appends to HOW's attempt log and writes to the owning Engine's record slice (X2).
  • Verify loop: fail → fail-retry up to N → fail-escalate, with Approval on escalate and the decision_trail persisted (sheet §2 edge contract). N's home is ruled: Charter retry_budget (A8 as REC, sheet §11 Quick eight).
  • C-state: C0 → C1 via reuse_tag (canon); rungs past C1 deferred until run data exists (sheet §9).

Ownership and custody

  • The Work-Atom owns its particles (written side); the runtime writes the attempt log at close.
  • Distribution ships templates only — instances and state never leave the tenant (A1-ext consequence; D33 in one sentence).

Failure modes

  • Verify fail → fail-retry → fail-escalate → Approval (the only ruled failure route for an atom; run-outcome enum, sheet A14).
  • Mis-cut atom (HOW not swappable, or a step needing its own verify) → split; the particle tests are the detectors.
  • Today-behavior: constraints ship as unpopulated prose and context is read by nothing, so neither is enforced at run time (grounding map §1).

Observability

  • Every close/abandon appends an atom-ledger row (sutra-atom:361-388); rows are keyed by session+atom, not by workflow — which is why no Engine is ever born today (grounding X2 row).
  • Attempt increments are visible in the atom record; the only budget-like cap running today is the model-escalation cap (sutra-dispatch:237-239).

Output looks like

The persisted artifact the four particles produce is the atom record — the runtime JSON that fixes all four particles at construction and accumulates the attempt count. Today's runtime shape, exactly the fields of the s5 contract (the work key is the pending rename to how, A1-FINAL-3):

{
  "goal": {
    "text": "PAN verified for applicant A-2214 (W-kyc-verify, step 2)",
    "check": "grep -q 'pan_status: VERIFIED' records/kyc/A-2214.yaml"
  },
  "constraints": [ { "text": "no applicant PII leaves the tenant", "check": null } ],
  "context_refs": [ "records/kyc/A-2214/", "user-kit/charters/C-credit-ops.json" ],
  "work": { "dispatch_kind": "llm", "ref": "skills/kyc-verify" },
  "attempt": 1
}

On close or abandon, the runtime appends an atom-ledger row keyed by session+atom (sutra-atom:361-388) — that ledger is where an operator sees particle outcomes; the attempt counter above is the only budget-relevant state persisted today.
