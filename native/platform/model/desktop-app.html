1 · The two UI states, as they actually exist today

The app already ships both states you asked for — and they are not two skins of one thing. They are architecturally different products that happen to sit behind the same brand.

The finding that matters most: in the panel, every per-turn governance element is produced by a single function — gvChipHtml() at js/05-chat.js:775 — and a sibling (gvBody/parseGov, 05-chat.js:749-763) removes the governance text from the prose before it is displayed. There is exactly one governance renderer in 460KB of app code. That is why a governance mode is cheap to build here — and why getting its semantics right matters more than the implementation.

2 · Governance modes — and why "ON / OFF" is the wrong switch

Correction before design (codex consult, 10 P1 objections, 2026-08-18). A single governance ON/OFF switch would be dishonest, because three independent things hide behind the word "governance", and they live at three different places in the code:
HookWhereWhat turning it off actually does
A · the chip05-chat.js:775the derived chip and panel stop rendering. Display only.
B · the strip05-chat.js:749-763governance text stops being removed from the prose — it appears inline, as the model wrote it
C · the injection02-helpers.js:28the PLACEMENT grounding preamble is no longer prepended to your message. The model behaves differently. This is not a display setting.
Turning off A alone is the worst possible state: the prose is still stripped and the chip is gone, so the operator sees neither the model's original words nor the derived summary. Evidence disappears silently.

The honest design is two axes, not one switch: governance behavior (is the system steering the model?) and governance visibility (how much of that do I see?).

AxisValuesPersistenceRule
BehaviorON (grounding injected, gates enforced) · OFF (no injection — plain assistant)server-side — it changes what the model receives, so it must be consistent across machines and auditableOnly this axis may use the word OFF. Switching it is a consequential action and gets a confirm.
VisibilityFULL (chip + expandable panel) · QUIET (one small always-on indicator) · RAW (inline, unstripped)per-browser (localStorage) — it is a display preferenceNever silently drops evidence: QUIET still shows that governance is active and stays one click from the detail.
The labelling law that falls out of this: while behavior is ON, no surface may say "governance off". The permitted words are "details hidden" / "quiet". The system is still steering the model, and a user who read "off" would have been deceived. That single rule is the substance of this whole section.

Mode 4 · TERMINAL · quiet — requires a real decision, not a CSS rule

PROPOSED Terminal quiet cannot be built the way panel quiet is. Three candidate answers, in ascending honesty and cost:
OptionHowCost / risk
T1 · scope the settingthe visibility switch is labelled Panel only; terminal always shows rawfree; but the same setting means different things in two places unless the label says so
T2 · upstream quietthe session runs with a governance-terse profile (the existing caveman checkbox is the precedent — it is applied on reconnect via a WebSocket param)changes what the model emits, not what the UI shows — it is a behavior change wearing a visibility label
T3 · filter the PTY streamthe server strips governance blocks from the byte stream before they reach xtermreal work, and it puts a regex between the operator and the machine’s actual voice — the thing a terminal exists to avoid
Recommendation: T1 for v1, with the switch honestly labelled. A terminal that hides things is no longer a terminal.
Two more consult findings that constrain any implementation: (1) the chip is built by parsing the model’s own text — it never reads h-sutra.jsonl or atom-ledger.jsonl. So it is a rendering, not an audit: false positives can strip normal prose, format drift can leak blocks, and a forged block in pasted content could render as real governance. Anything compliance-grade must come from the server records, never from the chip. (2) Whatever the visibility setting says, governance-OFF must never remove audit logging, approval gates, escalation paths, permission checks, or dangerous-action confirmations — and if those stay on, the UI must say so plainly.

3 · Design system — the import delta

You asked to import the documented design system into the Native pages. Before that can happen, an uncomfortable fact has to be recorded: the documented design system and the shipping app are two different systems that share four token names — and disagree on all four.

MeasureDocumented (design-system.html + tokens.css)Live (panel.css)
Tokens3631

TypographyPlayfair Display + Inter (webfonts)system serif/sans stacks, no webfont load
Import recommendation. The documented stack is the only internally consistent system, so it stays the base for Native pages — but the import cannot be a copy-paste. Five decisions must be made first:
  1. Semantic names: rename the doc to decide/review/done/alert (match the implementation) or rename the implementation to clay/steel/forest/rose (match the doc). Values already agree. Rec: match the implementation — code is the thing that runs.
  2. Dark: the documented palette has no dark half. Native pages that render in a viewer’s theme need one authored, or an explicit light-only commitment.
  3. Type: keep Playfair+Inter (self-hosted) or adopt the live system stacks. Rec: keep the brand for editorial pages, system stacks in-app.
  4. Status tier: the live app has 9 tokens the doc has never heard of (ok/warn/block × base/bg/line). Pass/warn/block outcomes are a different idea from involvement states — rec: document as a fifth semantic family.
  5. T15: is the .ds-* import still live? Zero adoption today. If it is dead, the component table describes a prototype, and the doc should say so.
Two smaller repairs found on the way: --gold-glow is implemented and load-bearing but missing from the doc’s token table, and the doc’s own figure claims "buttons" and "empty/offline states" are shared components while the 13-row table lists neither (the live app ships 7 button families and 8 distinct empty states).

P7 · Pattern extrapolation — what generalizes, what must not be inferred

  • Generalizes: the card grammar (dot + title + meta + primary/quiet actions) to any new decision type; the chip grammar to any new status; the two-pane session shape to any new record-bound conversation; the quiet-line to any new queue.
  • Must NOT be inferred: new semantic colors (4 is the set); dark mode (single warm-light theme is a commitment); new rail tabs without a founder gate (L1 open); any card without a persisted entity (P4 rule); density beyond max-3-chips; shadows beyond cards.

P8 · Acceptance criteria (screen-design definition of done)

  1. Every screen names its cards, and every card names its P4 record + truth-class tag.

  4. Semantic colors used for meaning only; tokens from tokens.css exclusively.
  5. Escalation/approval cards carry: why, risk, reversibility, safe default, once-vs-rule.
  6. Version gating respected: a screen may not render capabilities its version has not earned (chapter below).

Zero-state doctrine for every future screen: an empty surface states what is empty, what that means, and offers exactly one primary next step. A degraded surface additionally states what still works, what does not, and — only where a record actually guarantees it — where in-flight work is safe.
