What a builder is

A builder is a shipped workflow type that constructs model objects: it enforces the documented contract deterministically and judges the rest — "stochastic reasoning rides on deterministic, testable primitives." The child builder TYPE is WRITTEN; the builder ENGINE its runs birth is GROWN — never conflate the columns.

The set (RULED at A13, sheet §11: the FULL five-type table + root, per BUILDERS.md §3):

BuilderOne line
W-build-atomconstructs a Work-Atom definition — one goal + ONE verify instantiated from the pinned registry (G1), 4 particles present, constraints inherited in writing
W-build-workflowconstructs a workflow definition — X1-valid step graph, failure policy + retry budget wired, per-step verifies pre-declared, full Workflow-primitive field set
W-build-enginewrites the engine's wiring — X2 empty birth, record slice keyed by stable workflow_id, state = explicit record inputs only (Engine-Library rule); the engine itself is still born at first run, never at build
W-build-systemconstructs an Assembly + slots + child builders — pre-provisioned charter/system slots, X3/X4 boundary, ≥1-glue-engine test, styles seeded (A12), child-builder records minted; the System earns its noun later by living
Root (OS) builder = the Sutra pluginall of the above plus every mint gated, every artifact recorded, and the model vocabulary itself; reads the company at install day and mints the skeleton that then grows
Per the A13 ruling (sheet §11): every builder ships CONTRACT + DoD (autonomous-CAPABLE per A16a); zero-delta child mint is mandatory at install. Rejected alternative: the compressed set (3 + root, BUILDERS.md §2b) — REJECTED by the founder at A13.

In programming-world terms, builders are the helper functions and scaffolding of the OS — small shared constructors that everything else calls instead of hand-rolling its own.

The lifecycle — from intent to retirement

The centerpiece: one arc, walked start to finish. The standing thread: Credit-Ops (the digital lending company) needs a top-up eligibility workflow that does not exist yet.

The proposed builder lifecycle, intent to retirement. The PROPOSE→APPROVE gate is drawn heavy on purpose — the no-auto-registration doctrine (codex P1).

The same arc as a numbered story (the lending thread throughout):

  1. Intent hits the router: Credit-Ops asks for a top-up eligibility workflow. RESOLVE finds no matching workflow type — the intent falls through to the CONSTRUCT door.
  2. The CONSTRUCT door invokes the builder: Credit-Ops' child W-build-workflow (child resolves before the shipped base — the proposed ADR-026 extension).
  3. VALIDATE — contract preconditions checked deterministically; a request that cannot satisfy the floor is rejected before anything is built.
  4. CONSTRUCT — the skeleton is laid down with the enforced fields stamped: X1-valid step graph, failure policy, retry-budget wiring, per-step verify slots.
  5. JUDGE — the LLM fills the judgment slots reading the system's charter + its declared problem styles (A12) + its house instructions: the child builder's mindset. Credit-Ops' house rule lands here — every money-touching workflow includes a reconciliation atom + a compliance countersigned verify.
  6. VERIFY — the output contract: schema-complete against the Workflow primitive, every step carrying a verify. (Attempts against this check are a logged field on the atom's HOW particle — never a run-noun.)
  7. PROPOSE — the built draft lands as a proposal, not as a registered object.
  8. APPROVE — gated. Every mint is gated; there is NEVER auto-registration (codex P1). Denial, quarantine and replay live at this gate too — see the gaps register: the ledger that would hold this draft state does not exist yet.
  9. REGISTER — the approved workflow gets its catalog row + record entry.
  10. The workflow RUNS — W-topup-eligibility executes in Credit-Ops.
  11. The first run BIRTHS the engine — empty record slice (X2). The written child-builder TYPE stays WRITTEN; everything from here accumulates on the GROWN side.
  12. The engine accumulates learned patterns — after a year, Credit-Ops' slice has learned that reconciliation atoms always follow disbursal atoms.
  13. Those patterns feed the child builder's future builds — the feedback arrow: the next W-build-workflow run in Credit-Ops constructs with what the engine learned.
  14. Hot paths crystallize / codify by evidence (C0→C1 reuse_tag promotion, proposed + gated); a workflow that outlives its use retires via the ledger (G4) — gated, its record slice preserved append-closed.

Anatomy — what a builder consists of

(a) The staged pipeline is a template method

The base fixes the skeleton: the validate / construct / verify / propose stages are FIXED — a child never reorders or removes them. A child overrides ONLY the judge hooks, and it may ADD validate rules — narrowing-only, never relax. A child that relaxes the base floor is invalid at derivation time, not merely denied at run time. The base/child mechanism itself is now ruled type-system ground: A17 (sheet §11) rules Workflow as the FIRST base/child split — see Type System.

Template method: the base owns the stages, the child owns only the judgment inside them.

(b) A builder is itself a Workflow-primitive object

CRITICAL (codex P1): a builder is a full Workflow-primitive object — content-addressed id + immutability, domain_ref, typed preconditions/postconditions, failure_policy, stringency, reuse_tag, non-null return_contract, custody_owner, approval, decommission semantics — none optional. The template-method hooks live INSIDE that contract, never instead of it.

Two linked child mechanisms ride the same identity thread without being the same object:

MechanismColumnWhat it is
Child builder TYPEWRITTENthe derived template: base + the system's extra attributes / house instructions (its mindset)
Builder ENGINEGROWNthe runtime state that accumulates when that child builder runs: record slice + learned building patterns
