Crystallization — the SUBSTANCE arm of the one loop PLATFORM · the soft→hard write-back

STATUS: PLANNED · v3 · NOT BUILT. This page is one view of the one loop: it owns the substance question of the GROW stage — how a unit of work moves from soft (an LLM works it out each run) to hard (frozen code runs it every time). The first hop — reuse_tag → Skill — exists in canon. The auto-promotion + de-optimization loop and the crystallization_target field are genuinely new (design-forward, same bucket as the proposed System primitive); nothing here is built.
Where crystallization sits in the loop. The spine is one feedback loop for work: INTENT → SHAPE → RUN → RECORD → EVIDENCE → GROW → write-back → next INTENT (see the system, simply). GROW reads the record and improves things. GROW has two arms: scale (Maturation, S1→S5) and substance — this page. Crystallization is not a standalone catalog of states; it is the GROW write-back that reads the record's evidence (run-count · output-variance · cost) and writes back to one place: the Work-Atom's dispatch (LLM → Skill → Code). Same loop, one arm of it.

1 · The boundary this view names — record → evidence → dispatch

The record is read, not just written. RUN leaves a RECORD; the record becomes EVIDENCE the moment it is read across runs (the read-model form, before GROW). Crystallization is the GROW write-back that crosses that boundary in one direction-pair: it reads three evidence signals off the record — run-count, output-variance, cost — and writes back to exactly one thing: the Work-Atom's dispatch (the LLM | skill | code slot). Nothing else on the atom changes; the goal and the verify stay put. That is what makes it an arm of the loop and not a separate machine.

One read (record→evidence: run-count · variance · cost) and one write (back to the atom's dispatch). The harden write-back is an arm of the one loop, not a standalone state catalog — its inputs and its target both live on the spine.

2 · This is the substance arm, not the scale arm

Two GROW arms, two different questions, both read the same record. Maturation asks "how does a pile of work grow into a big, self-governing system?" — that's scale & self-rule (more workflows → coordination → metasystem; S1→S5). Crystallization asks a different question: "what is each piece made of — soft thinking, or hard code?" — that's substance (LLM → Skill → Code). They're independent. A big system can still be all-soft; a tiny task can be fully compiled. A B2B software product is high on both. Both arms live under the Evolution hub.

Canonical owner: Evolution — the GROW hub (two-ladders diagram) — this page depends on it for the scale⊥substance orthogonality picture. One line here: maturation moves you right (bigger, more self-governing), crystallization moves you up (soft → hard), and a mature B2B product is high on both.

3 · What the write-back changes — the C0→C3 ladder on a unit of work

Crystallization is not a per-run dial (like task-tier, certainty, or lens — those are SHAPE axes chosen fresh each run). It is a lifetime state of the unit that advances over many runs as the record proves the work out. Each promotion is one write-back to the atom's dispatch.

Each rung swaps softer material for harder: the LLM call becomes a named Skill, then a Skill that's settled becomes frozen code, then many frozen pieces + a UI + tenants become a product. Every rung is one write-back to the atom's dispatch — matching the GROW table on the system, simply (SUBSTANCE: C0 LLM → C2 code, writes back to the atom's dispatch).

4 · When is it decided? Both — declare at authoring, earn at runtime from the evidence

You can't decide it all up front (you don't yet have proof it's deterministic) and you shouldn't leave it all to chance. So: declare a target + policy at authoring, then earn the actual promotion at runtime from the record's evidence — gated, and reversible. Promote and de-opt are tied to the same three signals the record exposes; the climb up and the fall back read identical evidence in opposite directions.

Tiered-JIT for work: run interpreted (LLM), let the record profile the hot+stable paths, compile those (gated), and de-optimize back to LLM when the same record shows the world drifting. Authoring sets the ceiling; the runs earn the climb. Promote and de-opt both read run-count/variance/cost off the record — one evidence stream, two directions.

5 · The three inputs — and what each one governs

All three are read off the same record evidence (§1). Each governs a different part of the promote/de-opt decision.

InputThe question it answersReads (off the record)Its roleIf you get it wrong
Determinism (certainty / Cynefin)CAN it be code? (same in → same out, no judgment)output-variance over runsGATE — if no, pinned soft foreverfreeze judgment → brittle, confidently-wrong software
Frequency (volume)Is it WORTH compiling?run-count + costTRIGGER — hot paths promote, cold stays softcompile cold code → effort wasted, no payoff
StringencyHow CAREFUL must the promotion be?set by governance + failure-history in the recordCARE — more tests/review before freeze; easier rollbackfreeze without proof → fast wrong answers at scale

Stringency does NOT mean "compile it." High stringency on a judgment step means the opposite — keep it soft or human-gated. Determinism decides whether you can compile; frequency decides whether it's worth it; stringency decides how much proof first. The same variance signal that gates a promotion also fires a de-opt when it rises again.

6 · The proven pattern it borrows from — tiered JIT

JIT compiler (HotSpot / V8 / PyPy)Native crystallization
interpreter — runs anything, slowlyLLM call (C0) — handles anything, slowly
profiler — counts calls, finds hot pathsthe append-only record — run-count, variance, cost (the evidence in §1)
JIT compile — freeze the hot, stable codecompile a hot, deterministic workflow into code (C2) — write-back to dispatch
deoptimize — fall back when assumptions breakde-opt — write dispatch back to LLM when the same record drifts

Decades-proven in language runtimes. Crystallization applies the same idea one level up — to units of work instead of units of bytecode. The profiler is the record; the compile and the deopt are both write-backs to the atom's dispatch.

7 · How it ties together — one loop, two GROW arms, ten primitives

Crystallization is the substance twin of maturation's scale: maturation grows a system outward (S1→S5, systems-of-systems); crystallization hardens its pieces inward (C0→C2). They compose — a mature company-system is made of crystallized parts, and a B2B product is the corner where both arms are high. It reuses canon: reuse_tag→Skill is the C0→C1 hop; ADR-008 (markdown-vs-code) is the C1→C2 boundary; the record is the profiler whose evidence it reads; the approval gate (ADR-009) guards the risky freeze. The Work-Atom is the unit that carries the C-state and whose dispatch is the single write-back target. And under RULED decision #2 (WHAT-WE-DECIDED.md, 2026-08-05), the profiler IS the Engine's record slice: the evidence store this page reads (run-count · variance · cost per unit) is Engine state — a name over existing stores, not a free-floating profiler. 9 · Open gaps — founder queue

  • Genuinely new (not built). crystallization_target + crystallization_policy fields, the auto-promotion trigger, and the de-opt fallback are design-forward — same bucket as the proposed System primitive. Only C0→C1 (reuse_tag) exists today.
  • Determinism measurement. "Same in → same out" needs a concrete metric (output-variance over N runs, tolerance bands) before auto-promotion can be safe — spec the profiler signal this view reads.
  • Who pulls the C1→C2 trigger. Auto vs human-gated per stringency band; the gate reuses ADR-009 (Approval) but the promotion-policy ladder is unspecified.
  • De-opt criteria. What error-rate / drift signal in the record triggers a fall-back to LLM, and does it re-pin or just re-soften once? Reversibility is the safety property; its trigger off the evidence is undefined.
  • Where C-state lives — RULED (WHAT-WE-DECIDED.md #6, 2026-08-05): C-state lives on the HOW particle. The particles are goal / constraints / context / HOW (the sheet's wording used the pre-ruling label “means” for the fourth particle); since particles repeat at every level, the dispatch slot this page writes back to IS the C-state on the unit's HOW. Still open: only the mixed-granularity mechanics — a Workflow can be C2 while one Step inside it stays C0.

Output looks like

The persisted artifact of one crystallization turn is the promotion (or de-opt) event plus the atom's updated dispatch slot — the C-state on the HOW particle (ruling #6). The gate decision rides the Approval primitive; the evidence read is the Engine's record slice (ruling #2).
