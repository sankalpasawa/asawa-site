GROW — functional spec SPEC · Codify

STATUS: WORKING DRAFT (2026-06-16). Functional spec for the GROW family (worked axis: Codify). Product altitude (the WHAT, not the HOW). Produced by the A→B bootstrap path as bounded Work-Atoms (write → critique → fix), rendered deterministically. Spine: D62 P1 (directional/bounded/structured) + P2 (placement).

GROW reads the accumulated record after runs and, at an operator-set sustained-evidence threshold, writes an improvement back so the NEXT shaping of the work starts smarter than the last — Codify being the axis that hardens a proven, repeated practice into doctrine the team follows instead of re-deciding.

1. Abstract

GROW is the family of axes that read the accumulated record and write an improvement back, so the next pass of the work starts smarter than the last. The one thing every GROW axis shares — its answer to the sorting test — is that it accumulates on the unit across runs (not a fresh read of one input, not a gate on a single transition): proof builds up, and at an operator-set threshold the system reshapes itself. GROW fires over time, after runs, as the loop's correction leg — INTENT sets the aim, EVIDENCE measures the gap, GROW closes it by changing the next SHAPE. The reader gets the part of Native that makes it a learning loop rather than a re-run loop: a worked practice becomes doctrine, a proven step gets cheaper, a pile of work earns more autonomy. Where SHAPE decides this run, GROW decides how the next run is even allowed to be shaped.

2. What it does

For the operator, GROW means the system stops asking the team to re-decide things it has already watched succeed many times over. A practice that ran the same way enough times and never failed is noticed, surfaced, and — once approved — written into the catalog the next run reads from, so the team follows it instead of rebuilding the decision from scratch; a step the system has watched prove itself enough times can be hardened so it runs cheaper and more reliably; a body of work that has grown enough coordination earns a larger operating shape and more standing autonomy. Crucially, none of this touches the run in flight — GROW reshapes the NEXT run. The operator feels a system that compounds: every completed loop leaves the next loop a little more capable, and the improvements are explicit, approvable, and reversible rather than silent drift.

3. Why this is its own family

GROW solves a problem no other family owns: the work keeps relearning what it already knows, because nothing reads the long record and acts on it. SHAPE reads one input fresh and forgets; GOVERN judges one transition and moves on; only GROW treats the accumulated history as the thing to read and the next run as the thing to change. That cross-run, write-back character is the load-bearing reason it is a closed family of its own and not folded into SHAPE: SHAPE consumes improvements, GROW produces them, and collapsing the two would erase the direction of learning. GROW takes one of six closed family slots — a closed skeleton the sorting test fills (every axis sorts into exactly one family) — so the skeleton stays small and closed while the axes inside it stay open and minted.

4. Place in the loop

On the shared loop diagram used on every page — INTENT, SHAPE, RUN, RECORD, EVIDENCE, GROW, with GOVERN wrapping every transition — only the GROW highlight moves to the end of the arc, and the write-back arrow from GROW to the next INTENT is the emphasized edge. GROW reads the accumulated record (its WHAT) and fires over time, after runs (its WHEN), exactly as its master-family-table row states. Its defining act is the loop closure: GROW is where this completed run reshapes the next one, so the reader's eye is meant to follow the arrow that leaves GROW and re-enters the top of the loop. GOVERN sits over that write-back edge too — an improvement is proposed by GROW but only admitted by an authority gate, which hands the reader toward the GOVERN sibling.

5. The axes

GROW's open set currently catalogs three peer write-backs, each a categorical-to-sort dimension that moves a unit up a named value-ladder and writes the result back to a different part of the loop. Codify (reads execution history; fires at an operator-set sustained-repetition threshold; ladder one-off to doctrine) writes proven practice into the catalog the next SHAPE follows. Substance (reads how reliably a step has performed; fires once a step has proven itself past an operator-set bar; ladder least-hardened to most-hardened) writes back to how the step is carried out, making a proven step cheaper and steadier. Scale (reads how much coordination a body of work has accumulated; fires as that coordination grows past an operator-set bar; ladder a loose pile to a self-governing system) writes back to which operating shapes and how much autonomy are available. Alongside these three sits Cross-unit — GROW (a slice of Scale, read sideways across an owner boundary): same-owner depth is the composition mechanism, different-owner width is cross-unit (reads how a relationship between units has actually been used over time; fires as usage accrues past an operator-set bar; ladder isolate to coordinate to delegate), writing back to who-may-call-whom by growing a revocable handoff grant whose typed link is owned by EDGE, not by GROW. Each row carries its own reads / fires / value-ladder coordinates; the shared trait that sorts every one of them into GROW is the same — accumulation across runs, then a write-back. The numeric thing they aggregate (run counts, failure rates, usage tallies) is the evidence feeding the categorical ladder rung, never the rung itself.

6. One axis, walked

Codify is the load-bearing GROW axis because it is the clearest case of the family's whole move — accumulate, threshold, write back, be followed — so we walk one run of it. Takeaway first: an approval practice that the system watches succeed identically run after run climbs from a one-off, past an operator-set sustained-evidence threshold, into doctrine the next run follows without re-deciding. The trace: across many completed loops the same approval step runs the same way and never fails; the record accumulates that count, that zero-failure streak, that low variance; once the count crosses the operator-set threshold a detector proposes promoting the practice up its ladder; an authority gate approves the promotion; the practice is written into the catalog the next SHAPE reads; on the following intent the team follows the codified practice instead of rebuilding the decision. If the practice later starts drifting — outcomes diverge from the proof that earned it — the same axis walks it back down, de-codifying it. One trace, one axis; the other two peer write-backs (Substance, Scale) — and Scale's sideways slice, Cross-unit — follow the identical accumulate-then-write-back rhythm against their own ladders.

7. Boundaries — what this family is NOT

GROW owns improvement that accrues across runs and writes back; it does not own the five near-misses that look like it. A dimension that reads this run's input fresh and shapes only this run is not GROW — it is SHAPE; the flip is the sorting test's first question (fresh input versus accumulated record), and SHAPE is the sibling that consumes the improvements GROW produces. A dimension that approves or blocks a single transition (auto / ask / deny) is not GROW even though GROW proposes write-backs — it is GOVERN; the flip is gate-a-transition versus accumulate-then-reshape, and GOVERN is the sibling whose authority gate must admit every GROW improvement. A dimension that is the typed link between two units is not GROW — it is EDGE; the flip is that GROW grows a cross-unit edge over time but the typed link itself lives in EDGE (the two compose: an edge is wired at SHAPE and grown at GROW, and the cross-unit handoff GROW grows is one of EDGE's three typed links). A dimension about a finite stock the work spends is not GROW — it is RESOURCE; GROW may read spend trends, but allocation and reconciliation belong to RESOURCE. A dimension about when work runs or how it behaves over time is not GROW — it is TIME, the one family that owns the schedule-and-dynamics reading. Each near-miss is handed to its named sibling so GROW's outer edge is closed, not hand-waved.

8. Why this grouping

These write-backs group under one family because they pass the same sorting question — accumulate on the unit across runs, then write back — and splitting them would scatter the single mechanism of learning across the doc-set while merging GROW into SHAPE would erase the producer/consumer direction that makes the loop close. The peers are Codify, Substance, and Scale; Cross-unit is not a fourth independent peer but Scale read sideways across an owner boundary — same-owner depth is the composition mechanism, different-owner width is cross-unit, the tenancy boundary being what separates the two — which is why it writes back to who-may-call-whom yet sorts as a slice of Scale rather than as its own axis. The rejected alternative was to file each improvement type under the stage it writes back to (Codify under SHAPE, Substance under the step, Scale under structure); that was rejected because it hides the shared move and breaks the sorting test, which keys on where an axis reads from, not where it writes to. The grouping rule is the closed-skeleton / open-flesh principle: GROW is one fixed slot, its write-backs are open and minted, and any new learning axis joins here precisely when it reads the accumulated record.

9. Path to productization

A new GROW axis has a known path, which is what makes the open-set claim concrete rather than aspirational: name and define it against the sorting test (does it accumulate across runs?), show its need / advantage / ladder / example, thread it onto the family's owning evolution page beside its siblings, cross-link it into the loop's GROW stage and to the authority gate that ratifies its write-backs, and ratify it as a named direction. This doc stays in explanation mode and does not re-run that method — it points across to the axis-productization path and down to the evolution platform page, where the family's siblings (the practice-hardening and coordination-maturation rungs, with the cross-unit delegation map worked through on the company-decomposed page) already live. Closing the loop on its own subject: the GROW family, having been defined, placed, cataloged, bounded, and justified, here shows how it itself grows.

Acceptance criteria (black-box tests)

  • Abstract (section 1) survives standalone: a reader who sees only it can state what GROW is, the one thing every GROW axis shares (it accumulates on the unit across runs and writes an improvement back), where it fires (over time, after runs), and what they get — in under 30 seconds.
  • GROW's reads-WHAT / fires-WHEN match its master-family-table row verbatim: reads = the accumulated record; fires = over time, after runs — and no section contradicts that row.
  • The section-5 catalog presents Codify, Substance, and Scale as the peer GROW write-backs, and presents Cross-unit as a slice of Scale read sideways across an owner boundary (NOT a co-equal fourth axis); each row carries its own reads / fires / value-ladder coordinates and is marked categorical-to-sort vs numeric-to-aggregate; the worked trace (section 6) animates exactly one of them (Codify).
  • Section 7 names the EXACT sibling family that owns each adjacent near-miss (SHAPE, GOVERN, EDGE, RESOURCE, TIME) via convert->flip->flag, links to each by name — never 'see other families' — and its stated near-miss count matches the list it actually walks.
  • The doc stays at product altitude end to end: no schema, no code, no field-level implementation, and no imperative 'do this / configure X' sentence; section 9 points OUT to the productization path and DOWN to evolution rather than re-explaining the HOW.
  • The shared loop diagram is reused with only the GROW stage highlighted (and the write-back arrow to the next INTENT emphasized); the map itself is unchanged from every sibling doc.
  • Cross-unit is consistently framed across sections 5, 7, and 8 as a sideways slice of Scale (same-owner depth = composition mechanism; different-owner width = cross-unit) whose typed handoff link is owned by EDGE while GROW grows the revocable grant — never canonized as a flat orthogonal peer.
