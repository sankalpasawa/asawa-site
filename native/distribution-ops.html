§6.3 Onboarding flow

Per the Sutra-onboard 8-phase playbook (intake → market → shape → decide → architect → configure → deploy → activate). New CoS operator goes through:

STAGE 2 Charter setupOperator declares fixed Charters for each company in portfolio
STAGE 3 ConnectSlack · email · tools per Charter
STAGE 4 First-turnOperator types intent; CoS responds; Authority gate dialed conservative by default
STAGE 5 OngoingOperator dials autonomy + feeds patterns; B5.d learns; CoS becomes faster per company

§6.3.1 Install + onboard responsibility per tier

Per §6.0 Asawa Client Taxonomy, install/onboard responsibility differs per tier. The §A.2.2 zero-terminal post-onboarding rule means SOMEONE handles the one-time technical setup; this matrix names who, per tier.

§6.5 Transformation Cycle — customer onboarding journey beyond install

New CoS operators come from existing organizational contexts. The transformation cycle is the structured path from "I have an existing workflow" to "CoS-on-Native runs my workflow." Workshops + sessions + co-working — not just install.

§6.5.1 Five-stage transformation cycle

Stage labels T1-T5 below are transformation-cycle stages (as in master), distinct from the T1-T4 client tiers of §6.0.

StageWindowWhat happens
T1 DISCOVERYweek 01-on-1 session: founder/operator articulates portfolio · existing workflow inventory · pain-point mapping · skill mode baseline detection · Charter sketch per company
T2 ARTICULATIONweek 1Workshop: founder + Asawa Forge writes ratified Charters per company (fixed-vs-flexible scope) · Connector setup per Charter (Slack/email/tools) · First 5 trial tasks identified (low-risk T0/T1)
T3 PILOTweeks 2-3Operator runs 5 trial tasks · CoS executes · operator dials autonomy + feeds correction signals · Daily Pulse surfaces what CoS got right + drifted on · B5.d learned patterns seeded
T4 EXPANSIONweeks 4-8Charter scope widens · more tasks routed to CoS · T2/T3 tasks introduced (iterative + Charter-tier) · Autonomy thresholds tuned · skill mode mix refined · Operator-facing CoS voice converges
T5 STEADY STATEweek 9+S4 engagement state per company stabilizes · Operator transitions to "I just type intent" mode · Quarterly review: drift check · Charter audit · workforce health · re-onboard new domains as needed

§6.5.3 Acceptance criteria (Transformation Cycle v1)

  • Discovery → Articulation in ≤1 week per operator.
  • Pilot tasks have explicit success/fail criteria (per §4.5 Test-before-conclude).
  • Steady-state target: operator confidence + CoS accuracy KPI both ≥80% by end of Expansion stage.
  • Quarterly review surfaces drift signals from §7 Observability; re-onboard triggered if drift >15%.

§6.7 Module distribution + lifecycle

How Modules (per §1.4 Product Hierarchy) reach operators. §6.0-§6.6 cover Product-level distribution; §6.7 covers Module-level distribution within an operator's existing CoS install.

§6.7.1 Module lifecycle (cradle to retire)

StageWhat happensAuthority
ProposedCapability already exists in CSM (cap-NNN); composing it into a Module candidateAsawa Forge proposes
DesignedModule SPEC drafted; binding schema declared; codex+deepseek review (per §4.5 test gate)Asawa Forge designs; Sutra plugin core approves
Built + ShippedSPEC merged to plugin and PUBLISHED to the catalog; installs receive an "update available" signal — the update lands when the OPERATOR pulls it (PULL-default per founder doctrine D22, resolved N33 2026-06-12). PUSH (forced auto-roll) is reserved for security/foundational fixes only, and announces itselfNative platform publishes; operator pulls (push = security exception)
Operator-installedOperator chooses Module from approved catalog (v1.5+); creates BINDING for a CharterOperator (per §1.4.3 phase)
ActiveRUNTIME STATE accumulates; observability metrics tracked; drift detectedNative runtime
DeprecatedModule marked end-of-life in CSM; sunset window announced; operators notified via feedback channelNative platform + operator-affecting notification
RetiredSPEC archived; existing BINDINGs frozen-readable; RUNTIME STATE preserved for replay window per D.12Native platform
Update policy (N33 resolution, 2026-06-12): PULL is the default for every behavior-affecting Module update — operators choose when their company's setup changes (doctrine D22). PUSH is the override, reserved for security and foundational fixes, always operator-visible (release-note callout + audit row). This matches how the Sutra plugin behaves today (/core:update is a manual pull).

§6.7.2 v1 distribution scope (per R7 reviewer convergence)

  • v1 — Native platform + Asawa Forge author + ship Modules; operators consume passively (bound by Forge for them)
  • v1.5 — operator self-serve binding from approved Module catalog (still no author-new-Module privilege)
  • v2+ — third-party developers gated by review + permissioning + audit (marketplace concern)

§6.7.3 Acceptance criteria (Module distribution v1)

  • Module catalog is operator-discoverable via sutra-capability skill (single source of truth: §4.8 CSM).
  • Module retirement preserves replay capability for operator-held BINDINGs (per D.12).
  • Cross-Product Module reuse is designed for, not guaranteed in v1 — interfaces stay clean enough to extract later when 2nd Product exists.

Prose — what this page is
