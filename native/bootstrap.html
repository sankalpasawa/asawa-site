The Native bootstrap — how Native builds anything OVERVIEW · method

STATUS: WORKING DRAFT (2026-06-16). The general method: how Native grows anything — itself included — from the smallest seed, coherently, with no one-offs. The method is the asset; the six family specs are just one run of it. Instantiates D62 (the foundational principles). Productization, not implementation.

Work order

FieldThis page
WHATDocument the general Native method (core → grow via placement → any target), then show one worked instance (core → the six specs).
WHYSo nothing is built as a one-off. Every target — a spec, a feature, a whole company, Native itself — is reached by the same method, which is what keeps the system coherent as it grows.
INPUTThe core (D62) + a target.
OUTPUTA reusable method (seed + two-component step + graduation ladder + requirements taxonomy) + the six-spec instance.
VERIFYThe method reaches the six specs by the same rungs it claims for any target; the core is shown to grow itself (placement is a Work-Atom).

The problem this solves

A new thing always comes up — ours while building, or the user's while using. The failure mode is writing it as a one-off. The bootstrap is the answer: start from a tiny seed and reach any target by repeatedly placing inputs into the system — never inventing outside the method. Build scientifically, not by accretion.

1 · The core (the seed)

Nothing smaller grows Native. Two nouns, two laws.

The load-bearing trick: placement is itself a Work-Atom, and well-formed by P1 — directional (home this input), bounded (by one input + the current system state + the no-orphan invariant), structured (the D62 placement pipeline), verify = placed / coherent / logged-reject + cascade handled. So the seed needs nothing outside itself to grow — it grows by running its own unit on new inputs. (value↔axis is the bootstrap’s primitive; the 10 typed canon primitives are grown downstream, not part of the seed.)

2 · The universal step (the two components)

Every move in the method has the same shape. Two components, one operation.

place(input, system) → system′. The journey is just this step, repeated, until the system reaches the target. The placement engine (distill → classify → fit-test → assimilate | accommodate | reject → cascade → adjust) is specified in D62.

3 · The graduation ladder (general form)

The method has no fixed sequence of rungs. It is the universal step, repeated — and each input placed is one of three classes: A content, B method, or C structure (§4). They interleave in whatever order the target needs; you stop at the target. So “the ladder” is a pattern (place an A/B/C input, repeat), not a fixed staircase.

Altitudes are emergent, not a fixed stack — grown only when a real input needs a home that does not yet exist. “Altitude” (abstraction level) and “facet” (kind of concern) are different structures; let both emerge (D62). The three middle rungs are not ordered — A/B/C placements interleave as the target needs.

4 · What every journey consumes (the requirements taxonomy)

For any target, the inputs fall into four classes. The first three are placed; the fourth is what the system must be able to do.

ClassWhat it isNote
A · Contentdomain observations — the raw things to placee.g. “work gets cut up”, “this keeps repeating”
B · Methodsthe tools used at a rungeach method is itself a placed input (lives at the method altitude)
C · Structureskeleton decisions — a new family, altitude, or loop stagecore-author-gated (the rare accommodate)
D · Capabilitiesthe placement sub-skills the system must run: mint · classify · fit-test · cascade · adjustrun by us today; the Native product later
A target is reachable when its A + B + C are in hand and the system has D. “What are all the requirements?” = list A, B, C for that target.

6 · Use it for anything

The six specs are just today's target. The same method reaches the others:

TargetWhat the ladder produces
A user's companytheir domains, their axes, their workflows — grown from the same core
A new featureplaced at the right altitude, with implications cascaded — never a one-off

Native itself (L3 code)each backing-primitive field + engine behavior, by the build order on the roadmap
One method, every target. That is the “completeness” of D62 in practice: nothing enters the system except through the bootstrap — so the system stays coherent no matter how much it grows.

How A→B runs (the build path)

Creating the path from the core to a target is itself part of the bootstrap. This page’s own targets — the six functional specs — were produced by running this path, not by a direct LLM call. The LLM appears only inside the bounded nodes N0–N12 (each fenced by a goal + constraints + a schema = its verify); N13–N16 are deterministic code/skill, no LLM.
