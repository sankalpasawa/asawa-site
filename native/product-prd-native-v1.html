Project Native — Design Document v1

An operating system whose substrate is workflows of agents — so the person running their company can focus on the work that matters.

§ES Executive Summary #

Read this first. Two pages. No prior context required. The rest of the document is the receipt for every claim made here.

What it is, in one line

Native gives the person running a company an AI chief of staff — a system that takes work off your plate, makes the calls you'd make, asks when it shouldn't guess, and remembers everything so it gets sharper every week.

Why now

The person running a company spends 60-80% of their week on context-switching. The same decisions get re-decided. The same context gets re-explained to every tool, every meeting, every assistant. Existing tools are chatbots (answer one question, then forget) or trackers (record work but don't do it). Nothing actually compounds across your real work.

The bottom layer is a workforce of AI agents — some specialists, some generalists, some project managers. The product on top (Chief of Staff today; Project Manager and others later) is the surface you actually talk to. Native picks the right product, and the right team inside it, for the task you bring.

You bring an ask — in your own words, not in some form. The system figures out what you mean, gathers what it already knows about your work, drafts the answer or runs the task, and either does it (if it's safe and routine) or asks you (if it's a real call only you should make). Every step is recorded; next week, when you ask something similar, the system starts further along.

  • Your cognitive load drops 40%+ on routine work within 8 weeks.
  • The system gets ≥80% of routine outputs right the first time.
  • The output sounds like you by week 8 — your voice, your decisions visible.
  • Anything it did in the last day can be replayed in 30 seconds.

§0 What we are bringing into the world #

For: a person reading Native for the first time, in their first 90 seconds with this document.

What we want you to feel by the end: someone has thought hard about your work, your expertise can finally compound, and you are not alone in the fight.

A Tuesday, today

It is Tuesday, 9am. Paisa's Slack has a debate over loan-policy thresholds for the MVP cohort. DayFlow's reviewer kicked the APK back over a permissions string. Dharmik's board update is due Thursday, and you still owe Testlify a product-review pass before the founder check-in.

By 11am you have answered the same three questions you answered last Tuesday — what is the right risk threshold for Paisa, who owns the Play Store fix at DayFlow, what is the one slide that decides Dharmik's board. None of those decisions write back anywhere. Wednesday you will re-explain the context to whichever assistant or person asks.

The week is full. The substrate is empty. The bleed underneath the calendar is not the meetings — it is the work that never compounds.

A Tuesday, eight weeks in

Same Tuesday, 9am. CoS — running on Native — has already pulled the three Charters that frame today's work: Paisa risk-policy, DayFlow Play Store fix, Dharmik board prep.

The Paisa loan-policy debate arrived in Slack at 7am. CoS drafted three positions with the prior decision-provenance attached, surfaced the one threshold that needs your judgment, and queued the rest to auto-execute on your approval.

The DayFlow APK fix was picked up by an agent under your Charter overnight. The reviewer's reply is drafted in your voice; the patch is in a PR awaiting your authorize.

The Dharmik board slide is drafted from last quarter's pattern plus this quarter's metrics. One paragraph needs your eye.

Three decisions today, not nine. Every one of them writes back. Next Tuesday starts further ahead.

§1.4.1 Module eligibility — strict 4-test rule

A capability becomes a Module only if it satisfies ALL four:

#TestWhat it means
1Independent lifecycleCan be added / updated / retired without touching the host Product's release cycle
2Explicit configuration surfaceHas per-Deployment binding config (not hardcoded into Product code)
3Own runtime state / observabilityProduces its own audit rows, metrics, replay artifacts (not just inherits Product's)
4Possible reuseDesigned so a future second Product could compose it (cross-product reuse designed for, not guaranteed in v1)

If a capability fails any test → it's a feature of Product, not a Module. Avoid Module-bloat (every feature inflated into a Module). Daily Pulse + Feedback Engine pass; small UI panels don't.

§1.4.2 Capability vs Module — distinct concepts

ConceptDefinitionExamples
Capability (cap-NNN)Atomic platform/product primitive · single technical service · tracked in CSM (§4.8)cap-001 Input Routing · cap-002 Depth Estimation · cap-003 Blueprint · cap-007 SBOM

Capabilities are building blocks. Modules are deployable units. CSM tracks both: capabilities flat-indexed; modules referenced as compositions.

A.4 Vision #

Native is a workforce-deployment platform — it scopes, deploys, and supervises a workforce of agents under Charters, with Method routing, Authority gates, and a full audit trail.

Chief of Staff is the first product deployed on Native. CoS frames the operator's work, executes end-to-end where the path is known, surfaces decisions where operator judgment is needed, and closes the loop by writing what was decided + what shipped back into the substrate so the next iteration starts further ahead. CoS is an implementation consultant for the operator — accountable through the loop, not a day-organizer.

Every utterance + decision + outcome enters a compounding cognitive substrate. The operator's next ask is answered faster because the deployed CoS (running on Native) already knows the operator's patterns, charters, and history.

§4.5 Test-before-conclude gate (accuracy primitive)

Native does NOT mark a task done before testing the output. Accuracy is a per-workflow KPI. Test happens BEFORE concluding, not after. Output is rejected back to B3 retry if test fails.

StepWhat happens
1 · Pre-declare testFor each task tier, Native pre-declares the verification criteria BEFORE running. For T0 (atomic): grep / file-exists / contract-match. For T1 (multi-action): step-by-step verify + final integration check. For T2 (iterative): operator-visible 1-min iteration verification. For T3 (Charter): milestone-gate verification at goal-transition points.
2 · Generate outputB3 produces output (auto-execute path).
3 · Run testNative runs the pre-declared test against produced output. Determinism: same input + same Charter → same expected output shape.
4 · Conditional concludeIf test passes → conclude + write audit row + present to operator. If test fails → loop to B3 retry (max N retries per Charter); after N failures → escalate to operator (Authority gate).
5 · Post-concludeOperator's feedback (drop / accept / refine) becomes test signal for B5.d learned patterns. Test thresholds adapt over time per workflow.

Why before-conclude, not after — testing AFTER means the operator sees a failure and has to ask CoS to redo. Testing BEFORE means CoS catches its own failures and retries silently. Accuracy KPI in §7 Observability measures: % of CoS outputs that passed first-time-test vs needed retry.
