ADR-011 + ADR-012 — closed 5-set failure policy; typed PNC predicates over proseadr-decisionADR-011: "Native engine MUST define step.on_failure as exactly one of {rollback, escalate, pause, abort, continue} — closed 5-set, no extension without ADR." rollback compensates steps in reverse (workflow_rollback_started → _complete or _partial); escalate emits workflow_escalated and routes to the founder channel; pause emits step_paused, persists a queue entry, resumes on signal; abort emits workflow_failed immediately; continue logs the failure, advances to step[i+1], sets partial=true. ADR-017 — cadence scheduling: daemon-side setInterval tick, never external cronadr-decisionDecision: "Native engine MUST implement cadence scheduling as a daemon-side setInterval tick; MUST NOT depend on external cron / launchd." CadenceScheduler.start(intervalMs) runs inside the daemon process; on each tick, scheduled cadences whose next-fire time falls within the ±5 min window (I-12) fire TriggerEvent rows routed to the Workflow registry; each fire emits an EngineEvent + DecisionProvenance — replayable like any other Trigger. Test-before-conclude gate (§4.5 accuracy primitive)master-spec"Native does NOT mark a task done before testing the output. Accuracy is a per-workflow KPI. Test happens BEFORE concluding, not after." Five steps: (1) pre-declare the test per task tier — T0 atomic: grep / file-exists / contract-match; T1 multi-action: step-by-step verify + final integration check; T2 iterative: operator-visible 1-min iteration verification; T3 Charter: milestone-gate verification at goal-transition points; (2) B3 generates output (auto-execute path); (3) run the pre-declared test — determinism: same input + same Charter → same expected output shape; (4) pass → conclude + write audit row + present; fail → loop to B3 retry (max N retries per Charter), after N failures escalate to operator via Authority gate; (5) operator feedback (drop / accept / refine) becomes test signal for B5.d learned patterns; test thresholds adapt over time per workflow. Rationale verbatim: "testing AFTER means the operator sees a failure and has to ask CoS to redo. Testing BEFORE means CoS catches its own failures and retries silently." The Accuracy KPI in §7 measures % of outputs that passed first-time-test vs needed retry.master/index.html#section-4-5-test-before-conclude
