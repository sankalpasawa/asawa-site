Lifecycle — the one entity that has runtime state

Nine of the ten primitives are either registry records (Domain, Charter, Workflow, Step, Trigger, Tenant) or inert append-only audit rows (EngineEvent, DecisionProvenance, and the Approval ledger row). They have no runtime state machine beyond mint-and-persist. The one primitive with a real lifecycle is ExecutionResult — its state field is the system's only moving part, and every operator-meaningful change flows through it.

I-14 invariant (the spine of the whole audit model). Every Execution emits exactly one terminal EngineEvent from {workflow_completed, workflow_failed, approval_requested}. Rollback events (workflow_rollback_started → workflow_rollback_complete|workflow_rollback_partial) are RECOVERY transitions after workflow_failed under failure_policy='rollback' — they are NOT terminal. This is why the audit trail is replayable: derive full state from the append-only log, and exactly one terminal per Execution anchors each run.

Why this view exists (and what it deliberately does not do)

The 13 per-part engineering pages each answer "how does THIS part work?" — SoP details the Workflow runner, Authority+Tenancy details the Tenant/Charter gates, Observability details the EngineEvent catalog. None of them answers "what is the complete set of typed things Native works with, and how do they reference each other across part boundaries?" That whole-system question is what this page exists for — it is the engineering High-Level-Design data model, assembled once, citing the parts.

It deliberately does NOT restate any part page's mechanism rows. The mint-time checks, the executor call sequence, the persistence layout — those live on the owning part page and in canon (D54). Two boxes, same question → merge: there is exactly one home for each field, and this page links it. (BUILD-PROTOCOL principle 7; hard rules 3 + 5.)

Open gaps — founder queue

  • Primitive-set name drift across the doc system. The old skeleton's "Planned sections" list (tech-design/HLD/02-data-model.html) and the work-order prompt both name a set that diverges from canon: they include Artifact and Module (NOT §4.1 primitives — Artifact governance is §9 D.12, Module is a §10 catalog concept) and use WorkflowStep/Execution as primitive names. Canon (master §4.1 + sutra/os/native/primitives/) is the authoritative 10: Domain, Charter, Workflow, Step, Trigger, ExecutionResult, EngineEvent, Tenant, Approval, DecisionProvenance. This page uses canon. Founder: ratify the canon set as the single name, retire the divergent lists.
  • Approval is not a §2-listed primitive. Canon approval.md flags that Approval is described via its ledger row + 4 events (#15-#18) but is not yet a §2 field-table primitive (likely future §2.10). It is counted in the "10" via ADR-009. Founder: confirm Approval stays as the 10th primitive or elevate to a §2 field table.
  • declared_gap has no event-type. ExecutionResult state declared_gap exists in the 6-state enum but no matching event lives in the 26-event catalog (§3.2). Canon flags it as a runtime-implementation choice / future ADR. Founder: add a typed event or codify as a DecisionProvenance row.
  • paused vs awaiting_approval resumption. Both are non-running Execution states but only awaiting_approval has fully specified resumption (resumeApproved). Resumption semantics for paused (from on_failure='pause') are not specified in canon. Founder: codify or accept as runtime choice.
  • Approval resumption: mutate or mint child? Whether resumeApproved(execId) continues the original Execution or mints a child Execution with parent_exec_id is not specified in canon (approval.md + exec-result.md both flag it). Affects how the I-14 "exactly one terminal" reads across approve/reject. Founder: codify.
