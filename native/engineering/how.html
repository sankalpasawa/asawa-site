§3 section contract — purpose, ownership, boundarymaster-spec§3 is "Native's IP: not 'do the work' — 'do the work via the right way of looking at this task.'" It owns the Lens primitive, the axes (Realization + Reflection as the recommended pair; many others available), the value-is-an-axis recursion, the examples, the decision procedure, and the operator-facing surface of HOW. It depends on §2 task tier (T0-T3), §4 Native runtime (where Lens choices manifest), and §7 Observability (where Lens accuracy is measured). It does NOT own execution (§4 runtime), operator surface (§2), transport (§5), or "the DAG / build / Native-primitive implementation (Claude-suggested, archived — not committed design)." One-sentence theory: every piece of design knowledge is a "way of looking" (a Lens); there are many possible lenses, not capped; the two recommended for building anything are Realization (abstract idea → running thing) and Reflection (instance → axis → meta-axis → … → grammar). The section self-declares: "This section is THEORY work; productization is the next step."holding/website/native/master/index.html#section-3-how-methodology
§3.1 The atom — a value is just an axismaster-specThe smallest move is classification: a value is an item; an axis is a set of values. The role is RELATIVE to level — "a thing is a VALUE seen from the axis above it; the same thing is an AXIS seen from the values below it." "Value" and "axis" are the same kind of object viewed from one level up or down. This is the only primitive; everything else is this move repeated. Formal grounding cited by the master: type-universe relativity; Tarski's object-language / meta-language stratification.holding/website/native/master/index.html#section-3-1-atom
§3.2 Axes — many possible, two recommended; the coupling rulemaster-specAn axis is a particular Lens — one way of looking at the thing being built; there can be MANY axes (viewpoint · concern · time · ownership · scale · certainty · …) and "you are not capped to any number. You pick the lenses that change a decision for this idea and ignore the rest." The two recommended axes: Realization (abstract idea → concrete running thing; example values worldview · vision · strategy · capability · architecture · feature · contract · implementation) and Reflection (instance → axis → meta-axis → method → framework → paradigm → grammar; M0-M6, the recursion uncapped). Other available lenses are added per idea only if they change a decision: viewpoint (user / system / governance), concern (security / cost / accuracy), time (past / now / next / later · v1 / v2 / v3), ownership (human / AI / human-in-loop), scale (fleet / cohort / instance). Coupling of the recommended pair: "as you ascend Reflection to mint a structure (an axis, a schema), the forward Realization journey then consumes that structure instead of re-deriving it. Climb to write a schema once; descend and every instance conforms. The abstraction is carried forward as an input, not copied."holding/website/native/master/index.html#section-3-2-axes
§3.3 Dynamic — nothing is capped; three stop rulesmaster-specThe number of Realization levels and Reflection heights is NOT fixed; it is decided per idea. Dimensions are generated, not listed: each dimension = (interrogative × mechanism) — a finite generator mints an open set on demand. Realization stops by atomicity (downward — stop decomposing at the smallest buildable unit); Reflection stops by reflexivity (upward — stop climbing at the level that describes itself); both stop by the decision test (the practical cap): add a level or a dimension only while it still changes what you build or who reads it. Callout: "Possibility is not obligation. The space is astronomic; you instantiate only the corner a destination needs."holding/website/native/master/index.html#section-3-3-dynamic

§3.5 Decision procedure with Lenses (6 steps + worked decision)master-specA decision is choosing which lens to apply; a good decision is one that changes the path to your destination — "the framework's biggest gift is telling you which decisions you do not have to make yet." The six steps: 1 ANCHOR (name the destination; no destination → no decision) · 2 ON-PATH? (if not in the destination's required sub-graph → DEFER; "Most 'decisions' die here") · 3 LEVEL (find the decision's level/dimension and pick the matching lens — "Decide architecture with the architecture lens, not the implementation lens") · 4 REAL? (do options lead to DIFFERENT downstream sub-graphs? if not, pick either and move on) · 5 WEIGH (reversible → decide fast, revise later; irreversible → apply MULTIPLE lenses; "where the lenses DISAGREE is the actual tradeoff to resolve") · 6 RECORD (node + provenance: destination, lenses used, choice, why). The worked decision "B1 classifier: single LLM call vs fine-tuned model?" resolves to single-call for v1 — reversible-ish (intent{} contract unchanged either way), lenses [cost, time, accuracy, reversibility] agree, with recorded revisit trigger "if eval pass-rate drops below 90%." Net effect per the master: eliminates off-path agonizing (step 2), false decisions (step 4), wrong-level thrash (step 3); adds effort calibrated to reversibility, multi-lens only for the genuinely hard ones, and replayable rationale.holding/website/native/master/index.html#section-3-5-decisions-with-lenses
§3.6 The 6 HOW dimensions — operator-facing surfacemaster-specThe 6 dimensions are the operator-facing surface of §3.2's axes — the specific lenses an operator picks when working with Native today; each row reads "what the operator is choosing" and "the values available." Approach: top-down (goal → factors → tasks), bottom-up (data → patterns → conclusion), or by analogy (this looks like prior X). Mindset: optimize (maximize known metric) · explore (surface options) · repair (fix broken state) · audit (verify-only). Structure: tree of sub-tasks (T3 Charter decomposition) · sequential pipeline (T1 multi-action) · parallel scan (T2 iterative) · iteration loop (refinement). Detailing: coarse first pass + sharpen (T0/T1 fast iterations) vs fully detailed from start (T3 charter with locked requirements). Decomposition: 3-factor (forced parsimony) / 7-factor (completeness) / by-stakeholder (comms-heavy) / by-deliverable / by-risk (high-stakes). Cascading: when a sub-task gets stuck, recurse on the sub-task — a sub-T3 spawns a child T3 with its own Lens choices, depth bounded by complexity budget.holding/website/native/master/index.html#section-3-6-how-dimensions
§3.7 Lens selection flow → lens manifest in state envelopemaster-specSelection takes operator intent (B1) + task tier (T0-T3) as input. The LENS SELECTION block runs five steps: 1. read Charter scope (§4 primitive) · 2. read past patterns from B5.d · 3. choose lens values (approach · mindset · structure · detailing · decomposition) · 4. estimate complexity → cascade depth · 5. declare lens choice to operator (B3a if explicit; silent if known). Output: "lens manifest emitted into state envelope (§4.3); §4 Native runtime executes." If a sub-task gets stuck the flow recurses lens selection (cascade) with depth--. The master maps this flow onto the §3.5 decision procedure: Anchor → Level → Real? → Weigh → Record.holding/website/native/master/index.html#section-3-7-how-selection-flow
