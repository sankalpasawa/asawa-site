Engineering · Governance — how the gate is built across the whole machine ENGINEERING · cross-cutting · zoom 5

This is the cross-cutting ENGINEERING view of governance — the whole-system build. It spans all platform parts and answers one question no single per-part page answers: where, how, and in what order is the Authority + Tenancy gate physically built and fired across every block, and what records every decision? The 13 per-part engineering pages each answer “how does governance work inside THIS part”; this page stitches them into one whole-system design and cites them — it never restates their mechanism rows (principle 7, one-home). Distinct from the GOVERNANCE WRAP page, which is the policy home (WHY the gate exists, D-directions, charters, KRs G1-G6) — cross-linked here, never duplicated.

1 · The whole-system shape — one gate, many firing points

Governance in Native is not a block; it is a cross-cutting wrap. The §1.0 runtime schema draws Authority + Tenancy as a dashed envelope around every block (“gates every access”) rather than an in-line stage on one edge. The engineering question this whole-system view answers — and that no single part page answers — is: the gate is one decision pipeline, but it fires at several physical crossings, and each crossing is owned by a different part page. This page maps the pipeline to its firing points and cites the part page that builds each one. It does not restate their mechanism rows.

2 · Authority model — the 6 dimensions (whole-system, verbatim-anchored)

The decision of auto-execute vs ask-operator is made by the D.6 Authority Model. Master states six dimensions; they apply cross-pillar, heaviest in the B3 action gate and B4 delegation. The dimensions themselves are a governance-policy fact (full WHY + KRs at governance/ §D.6); this engineering view records them only as the inputs the gate engine reads at every firing point above.

#DimensionAuto when…Ask when…
1by domain (per-Charter company scope)inside the Charter's granted domaintouches a domain outside scope (→ tenancy half, HS-3)
2by toollow-stakes tool (e.g. Slack)high-stakes tool with no standing auth (e.g. bank-API)
3by stakeholderinternal teamboard / regulator / external party → escalate
4by dollar threshold≤ $X> $X
5by reversibilityreversible actionirreversible action (F.2 tag = “not reversible”)
6by confidence levelhigh confidencelow confidence

The classification output (AUTO / GATE / ESCALATE) then runs the F.1/F.5 ask-vs-act cascade in order: irreversible? → high-risk? → new authority? → first-time channel? → else ACT and report after. ASK outcomes become an Approval primitive (ADR-009); operator verdicts climb the F.4 trust ladder (rung 1 day 0-14 ask-all → rung 4 day 90+ standing routines), which shifts future cascade outcomes from ask toward auto. Anchor: master §2.F. Part-page detail for the A+T block itself: Eng: Authority + Tenancy.

3 · Hardstops HS-1..HS-8 — the whole-system catalog (operator-visible)

The hardstop catalog is the system's set of unbreakable rules. When one fires, the runtime drops into PAUSED and the operator sees a boxed BLOCKED with WHAT-happened + next-action + audit-row link (the UX contract). Full engine spec is canon-only (sutra/os/native/hardstops/HS-*.md, D54); the operator-visible behavior is master §4.10.1. A dedicated engineering/catalog-hardstops.html per-hardstop index is a planned SEED sibling (manifest eng-catalog-hardstops); until it is authored this whole-system view carries the catalog and links the master anchor + the owning part page per row.

4 · Tenant boundary — how isolation is built across parts

Tenancy is the other half of the wrap. The boundary is a typed schema field (the Domain.tenant_id per ADR-006), not an after-the-fact firewall — it is checked both at primitive-mint and at execution. The mechanism rows that build this (the Tenant primitive, assertCrossTenantAllowed, the tenant_boundary_violation event #26) live on the Eng: Authority + Tenancy part page and are cited here, not copied.

LayerWhat enforces tenancy hereOwning part page
Schema / primitiveEvery Domain owned by exactly one Tenant; tenant_id required (no nullable); checked at primitive-mintEng: A+T
ExecutionExecution.tenant_context carries {tenant_id}; assertCrossTenantAllowed(src,dst,op) called unconditionally when a step touches a different tenant; fail-closed without delegates_toEng: SoP · Eng: A+T
Data accessEvery SoR read/write scoped by Domain; cross-tenant audit queries also default-denyEng: SoR
Defense-in-depthD33 settings.json client firewall stays as intent-level backstop (ADR-006 rejected relying on it alone — it is not capability-enforced)Eng: A+T · Eng: Compute

The boundary unit is the operator's portfolio, not the company — one operator running several companies is one tenancy decision surface. Anchor: master §4.10.1 + the §2 B5 acceptance row. Hierarchical / nested tenancy is declared in schema but execution semantics are v1.x backlog (see gaps).

5 · DecisionProvenance — the audit substrate every part writes to

Every decision that crosses the gate — anywhere in the machine — writes one DecisionProvenance row. This is the whole-system property that makes the gate auditable: the row schema (ADR-007) is fixed, the write is 3-channel (gate-log + provenance + artifact, ADR-013), and it is append-only (zero silent overwrites). HS-4 fires if the write fails across all three channels. The operator never reads raw JSONL — F.3 replay reads the trail back on the same chat surface (“what was asked, what Native did, why”).

Row schemafactors · authority verdict · output · audit chain (ADR-007); one row per decision/artifact-writeEng: SoR (B5.c)
Write channels3-channel: DecisionProvenance JSONL + stderr beacon + tmp fallback (ADR-013)Eng: SoR · Eng: Compute
Coverage invariant100% of decisions carry a row; replay any task end-to-end in ≤30s (single-day window)Eng: Observability §7
Failure modeHS-4: unwritable across all 3 channels → full STOP, no silent unaudited executionEng: SoR

6 · Failure states — what the runtime enters when the gate or a hardstop blocks

The happy-path workforce state machine (PROPOSED → ACTIVE → PERSISTED → RETIRED) extends with three failure states the gate can drive the whole machine into. These are whole-system states, not per-part — any part's firing can trigger them. Mechanism detail (retry budgets, compensation) lives on the named part pages.

StateEntered whenOperator seesExit
PAUSEDHardstop fires OR Charter Authority requires explicit operator decision (D.6)“task paused at step X — decision needed” + context + recommended next actionoperator decides → ACTIVE (resume) OR RETIRED (cancel)
ESCALATEDB3 retry budget exhausted OR Authority gate triggers ESCALATE class (ADR-018 contract 1)“auto-retry exhausted; your judgment needed” + B3a THINK 3-angle brainstormoperator confirms direction → ACTIVE OR RETIRED
DEGRADEDConnector half-fails (send succeeded but audit write missed) OR partial side-effect“step partially completed — reconciliation needed” + compensation optionsidempotent retry OR manual log-write → ACTIVE OR PAUSED

Anchor: master §4.10.2. The state machine itself is built on the daemon (Eng: Daemon Runtime §4); the SoP-side gating that drives PAUSED/ESCALATED lives on Eng: System of Process; the DEGRADED reconciliation path is a Eng: Connector concern.

Open gaps — founder queue

  • Per-edge firing completeness. The §1.0 SVG wraps ALL blocks (incl. Human→UI and Host→Daemon), but master only names enforcement at three edges (SoP execution, connector sends, SoR tenancy). Is UI→Host / Host→Daemon gated by the same mechanism, or are those crossings ungated today? (carried from master §A+T gap 1)
  • Orchestration gating. Is the process-selection step in Orchestration itself authority-gated, or does gating only begin once System of Process executes? (master §A+T gap 2)
  • “grant always” storage. F.1 “grant always” implies a persisted permission template — which block stores it (Charter? SoR?) and what schema? (master §A+T gap 3)
  • Trust-ladder state owner. Which block owns trust-ladder state (current rung / operator dial), and is it scoped per-operator, per-Charter, or per-tenant? (master §A+T gap 4)
  • HS-4..HS-8 mechanism. Five of eight hardstops are doctrine, mechanism-pending — no live detectors. The failure-state table assumes they fire. Ship the detectors or keep flagged? (master §4.10.1 callout + §10.10 P0 #1)
  • HS-3 live scope. HS-3 is “partial enforcement via existing plugin hooks” — what exactly is enforced live today vs doctrine-only? (master §A+T gap 5)
  • Compute-layer tenancy. Per-tenant key/data isolation appears only in the deferred cloud-hosted channel gate (§1.4.5), not for the v1 own-machine case — is there a Compute-boundary enforcement story for v1? (master §A+T gap 6)
  • DecisionProvenance home block. Master leaves the audit trail's home block as an open question (inside SoR or a separate store?). The ADR-007 row contract is named; its home block is not. (master §A+T gap 7)
  • Nested tenancy execution. Hierarchical/nested tenancy is declared in the Tenant schema but execution semantics are v1.x backlog (carried from the A+T part page).
