Engineering · Catalog: Hardstops — HS-1..HS-8, one row each ENGINEERING · cross-cutting · zoom 5

This is a reference INDEX, not a mechanism page. It lists every hardstop Native ships — the unbreakable rules — with one row each: id · what it blocks · override path · canon/anchor. It is a whole-system view because the eight hardstops fire across different parts (Host, SoP, SoR, Runtime daemon, Observability), so no single per-part engineering page holds the complete catalog. This page cites the owning part pages + the cross-cutting Eng: Governance gate-design view; it never restates their mechanism rows (principle 7, one-home). The full engine spec is canon-only (sutra/os/native/hardstops/HS-*.md, D54); the operator-visible behavior + override semantics trace to master §4.10.1 + §4.10.2.

The catalog — HS-1..HS-8, one row each (id · what it blocks · override path · canon/anchor)

The override path is what the operator does to get past a fired hardstop. It is read from the operator-visible behavior + the failure-state exit paths in master §4.10.1 / §4.10.2 — not invented here. "Enforcement" = whether a live detector exists in the shipped runtime today (master §4.10.1 MECHANISM-PENDING callout).

HS-1
reflexive-check		 A Workflow attempting to modify Sutra core primitives without a cleared reflexive_check Constraint — blocks the system editing its own rules. System REFUSES to self-modify and surfaces “this change touches Sutra's own rules — please ratify directly”; operator authorizes (ratify directly) or cancels → PAUSED exits on operator decision. partial (plugin hooks) Eng: SoP · Eng: A+T hardstops/HS-1*.md · §4.10.1
HS-2
governance-overhead		 Per-turn governance overhead exceeding 25% of the token budget — blocks a turn from spending more on governance than on work. System aborts the current turn; operator sees “turn aborted (governance overhead exceeded budget)”; no operator action required — the next turn proceeds normally per canon (override = retry on the next turn). partial (plugin hooks) Eng: Host · Eng: Orchestration hardstops/HS-2*.md · §4.10.1
HS-3
tenant-boundary		 Execution attempting cross-tenant access without an explicit delegates_to edge — blocks one company's data touching another's. Cross-company action DENIED; operator gets “this action would touch <other-company>; explicit delegates_to authorization required”. Override = operator grants an explicit delegates_to edge (ADR-006); otherwise the action stays blocked. partial (plugin hooks) Eng: SoR · Eng: A+T hardstops/HS-3*.md · ADR-006 · §4.10.1
HS-4
audit-unwritable		 A decision that cannot be recorded — DecisionProvenance log unwritable across all 3 fallback channels. Blocks silent unaudited execution. System STOPS and surfaces “cannot record this decision; halting until audit recovers”. Override = restore the audit sink (resolve the write failure); there is no operator-authorize bypass — by design, no unaudited execution is permitted. doctrine, mechanism pending Eng: SoR · Eng: Observability hardstops/HS-4*.md · ADR-013 · §4.10.1
HS-5
cutover-rollback-fails		 A cutover whose rollback path itself fails to restore the prior state — blocks an unrecoverable migration from proceeding automatically. Cutover PAUSED; operator + Tenant owner brought into HITL (human-in-the-loop) for the decision; no automated retry. Override = the HITL pair decides the recovery path manually. doctrine, mechanism pending Eng: Daemon Runtime §4 hardstops/HS-5*.md · §4.10.1
HS-6
governance-hooks-fail		 3+ distinct governance hooks failing within the same turn — blocks a session continuing while its guardrails are broken. SESSION SUSPENDED; resume requires manual investigation of the failing hooks before re-engagement. Override = fix the hooks, then re-engage the session. doctrine, mechanism pending Eng: Host · Eng: Compute hardstops/HS-6*.md · §4.10.1
HS-7
codex-queue-stale		 A codex review queue exceeding 20 items OR any item more than 7 days stale — blocks shipping while review is saturated. Shipment broadly BLOCKED until queue drains; operator sees “review queue saturated — shipments paused”. Override = drain the review queue (clear/age out the backlog); shipments resume once the threshold clears. doctrine, mechanism pending Eng: Daemon Runtime §4 hardstops/HS-7*.md · §4.10.1
HS-8
canary-regression		 A production canary observing a regression against cutover behavior_invariants — blocks a regressing version from staying live. Auto-ROLLBACK to the prior version per canon; founder notified. Override path is automatic (no operator action needed to roll back); operator's role is to investigate + decide whether to re-attempt the cutover. doctrine, mechanism pending Eng: Observability §7 · Eng: Daemon Runtime §4 hardstops/HS-8*.md · §4.10.1

The shared override surface — the Hardstop UX contract

Every hardstop, whatever it blocks, exits through the same operator surface. That is what makes the override paths above legible rather than eight separate error dialects. Per master §4.10.1, every fired hardstop produces exactly three things:

#The system always emitsWhy it matters for override
aa 1-2 sentence operator-facing message stating WHAT happened (in operator words, no stack trace)the operator can tell which rule fired without reading engineer-level detail
ba recommended NEXT ACTION — one of: decide / authorize / wait / investigatethis is the override path, named in four verbs; the table above maps each HS to its verb
ca link to the audit row for the eventthe override is itself recorded; the operator can replay why the block happened (F.3 replay)

Failure-state mapping (master §4.10.2): a fired hardstop drops the runtime into PAUSED (exit: operator decides → ACTIVE or RETIRED) except where the catalog names a different terminal — HS-4 STOPS the runtime, HS-6 SUSPENDS the session, HS-7 BLOCKS shipments, HS-8 auto-ROLLS-BACK. The full gate-firing design across the machine lives on the Eng: Governance cross-cutting view; this page is the per-hardstop index it points back to.

Name-pending RESOLVED — what changed since the old skeleton

The old skeleton (tech-design/LLD/hardstops.html) listed HS-5..HS-8 as name-pending ("(5th hardstop)" … "(8th hardstop)"). That gap is now RESOLVED in master §4.10.1: HS-5 cutover-rollback-fails · HS-6 governance-hooks-fail · HS-7 codex-queue-stale · HS-8 canary-regression are all named, with triggers + operator-visible behavior. The remaining open gap is not naming but mechanism — see below.

Open gaps — founder queue

  • HS-4..HS-8 mechanism (the live gap). Five of eight hardstops are doctrine, mechanism-pending — the master §4.10.1 callout (added 2026-05-13, codex Lane A R12 P1) confirms live detectors/executors do NOT yet exist in the shipped Native runtime. The failure-state table assumes they fire. Resolution path per §10.10 P0 #1: ship the detectors OR keep the canon entries flagged "doctrine, mechanism pending". (This is the same gap carried on Eng: Governance; one home, cited here.)
  • HS-3 live scope. HS-3 is “partial enforcement via existing plugin hooks” — what exactly is enforced live today vs doctrine-only? (master §A+T gap 5; carried on Eng: Governance.)
  • Override path for STOP-class hardstops. HS-4 (audit-unwritable) has no operator-authorize bypass by design — the only override is restoring the sink. Is there a founder-level break-glass for a prolonged audit-sink outage, or does the system stay halted indefinitely? Not stated in master. (new, surfaced by the override-path column.)
