The index — 6 runtime surfaces, one row each (master §4.11; canon linked, D54)

Per master §4.11, the runtime exposes exactly 6 surfaces — “runtime interfaces between daemon + workflows + operator”. A surface is a contract, not a CLI screen and not a UI: it is the named boundary where the daemon, the Workflows, and the operator meet. This is a lookup table: name, what it does, its invariant family (cited — full text lives on the owning page + canon), the part page that OWNS its mechanism rows, and its canon file (D54). No mechanism row, dispatch chain, or full invariant text is copied here — click through.

#SurfaceWhat it does (one line)Invariant family (cited)Owning part page (mechanism home)Canon file (D54)
1ROUTE Classify an operator utterance (via the H-Sutra event bus, §5.3) into a matched Workflow OR, on no match, a candidate for the pattern detector. Router.route(evt) returns a synchronous RoutingDecision; no Workflow fires inside ROUTE. ROUTE-I1..I5 — one routing_decision per HSutraEvent; execution_id=null; matched id resolves in registry; no-match → k++; routing precedes every action (I5, PROTO-006 lesson-port) orchestration.html surfaces/route.md
2RUN Fire a matched Workflow → dispatch each WorkflowStep → for action='invoke_host_llm' steps hand the prompt to the configured host (claude --bare | codex exec) → persist a typed Execution log. Runs inside the daemon; the host-LLM session is the effector boundary (§5.1) where side effects actually happen. RUN-I1..I7 — one workflow_started per fire; one step_started per dispatch; invoke_host_llm requires host ∈ {claude, codex} + non-null prompt (RUN-I4); per-step timeout_ms host-class default (60s claude --bare; ≥300s codex) when null (RUN-I7) system-of-process.html · host.html surfaces/run.md
3GATE Authority + Approval. Reaching a requires_approval=true step pauses the Execution to awaiting_approval (fail-CLOSED) and persists a ledger row at user-kit/pending-approvals/E-<id>.json; resolved by the operator's approve/reject utterance (the daemon is detached from stdin). Approval is a first-class primitive (ADR-009), not a hook. GATE-I1..I5 — reaching a requires_approval step emits approval_requested + step_paused; state → awaiting_approval; approve → resumeApproved + approval_granted; reject → approval_denied + terminate; idempotent re-fire → approval_already_handled authority-tenancy.html surfaces/gate.md
4EMERGE Pattern emergence over accumulated history (ADR-010), NOT a step on the synchronous turn. When an unmatched pattern's running count reaches k (=4), the detector emits pattern_proposed; approve P-<id> mints a real Workflow into user-kit, which ROUTE can then match. Off the hot path by design. EMERGE-I1..I4 — pattern_proposed once at k; approve/reject emit proposal_approved/proposal_rejected; false-positive guard pauses emergence if ≥3 rejects/week; approval makes the candidate a registered routable Workflow platform/maturation.html (v2 · PLANNED) · system-of-record.html surfaces/emerge.md
5AUDIT Persistence + replay. Every state transition across every surface emits exactly one typed EngineEvent + (for consequential decisions) one DecisionProvenance row; AUDIT is the durable sink for those rows (ADR-013) and the replay surface (§6.1, ≤30s for a single-day window). Not directly invoked — every other surface writes into it. AUDIT-I1..I8 — ≥1 EngineEvent per transition (append-only); exactly one DecisionProvenance per consequential decision; monotonic ts_ms; sanitized reason; durability (fsync + 3-channel + stderr beacon); fail-CLOSED (HS-4); non-empty policy_id/version; chain-shaped agent_identity (ADR-015) observability.html · system-of-record.html surfaces/audit.md
6TENANT The multi-company isolation boundary: each Tenant gets an isolated audit log + ACL; cross-Tenant operations require an explicit delegates_to edge, else fail-CLOSED. Not a CLI surface — enforced via TenantIsolation.assertCrossTenantAllowed, which throws on deny (ADR-006 + HS-3). TENANT-I1..I6 — every Domain has non-null tenant_id; every Tenant has name + absolute audit_log_path; cross-Tenant ops require delegation else throw + #26 + HS-3; fail-CLOSED on undefined tenant context; private DP JSONL per Tenant; HS-3 block+log+escalate on violation authority-tenancy.html surfaces/tenant.md
Surface vs UX-surface — a naming collision to keep straight. The 6 here are the runtime orchestration surfaces (master §4.11): contracts between daemon, Workflows, and operator. The master also uses “surface” in §2.F for operator UX surfaces (Ask / Receive / Daily Pulse / capability map). Different concept — those live on ui.html, not here. This index is only the 6 runtime surfaces.

How to read this index (and what it deliberately does not do)

This page answers one question: "what is the complete, canonical set of runtime contracts the daemon exposes, what does each guarantee, and where do I go for the mechanism?" It is the table of contents for the runtime surface set. Each row routes to two homes:

  • Owning part page (column 5) — the engineering page that holds the surface's mechanism rows: the dispatch chain, the C4 diagram, the event emission, the per-step contract. That part page is the one home for those mechanisms (BUILD-PROTOCOL principle 7).
  • Canon file (column 6) — sutra/os/native/surfaces/<name>.md, which carries the full invariant table (every I-number with its source) and the operator-facing interface. Linked, never copied (D54).

It deliberately does NOT carry the full invariant text, the dispatch chains, the C4 diagrams, or the per-turn firing order. Invariant text lives in canon; mechanism rows live on the owning part pages; the per-turn sequence (which surface fires at which step of one operator turn) lives on control-flow.html §3. Two homes for “surfaces” would be two truths → merge: control-flow owns the temporal view (one turn, in order), this catalog owns the reference view (all 6, with their contracts). Neither restates the other.

Open gaps — founder queue

  • GATE-I and EMERGE-I invariants are in canon but not yet ported to the engineering part pages. Canon gate.md defines GATE-I1..I5 and emerge.md defines EMERGE-I1..I4, but the owning engineering pages (authority-tenancy.html for GATE, platform/maturation.html for EMERGE) carry the prose contract without the numbered I-table that ROUTE/RUN/AUDIT/TENANT pages already render. This index cites the canon families directly; the engineering pages should port the I-tables so the “invariant family” column deep-links to a rendered table, not just canon. (Editing those pages is outside this work-order.)
  • EMERGE's owning engineering home is split and partly in the PLATFORM band. The EMERGE detail lives on platform/maturation.html (marked v2 / PLANNED, ADR-022/ADR-023) with a secondary home on system-of-record.html; there is no dedicated engineering/emerge.html part page like the other surfaces have. Founder: confirm whether EMERGE earns its own engineering part page once ADR-023 lands, or stays documented on maturation (cross-band).
  • The ROUTE→EMERGE data-flow direction is a canon-open seam. emerge.md states canon does not specify the exact flow between ROUTE's unmatched routing_decisions and EMERGE's pattern detector (detector tails events vs. ROUTE calls a detector method) — an implementation choice deferred to a future ADR. The interaction table above reflects the read-side option; the edge stays soft until canon codifies it.
  • RUN's resumption wire (on_host_llm_result) is open per §8 OS-1. Canon run.md declares NativeEngine.on_host_llm_result(execId, stepIdx, r) as the host-LLM resumption callback but notes “the exact wire is open”; RUN's contract for awaiting that callback is implementation-shaped, not canon-shaped. Tracked on host.html + system-of-process.html; named here so the surface inventory is honest about the one not-fully-wired contract.
