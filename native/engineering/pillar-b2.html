Why this page exists — what the matrix + per-part pages miss

B2 is the only pillar whose PRIMARY block (System of Process, context-build) is not where its data lives (System of Record) nor where its output is consumed (the Host's LLM call). The matrix gives the B2 row eight cells — traceability: which block plays which role (SoP PRIMARY; SoR/Host/UI/A+T/Compute/External World SUPPORTING; Orchestration empty). The per-part engineering pages give each block's local mechanisms in full. Neither states the pillar as ONE flow with its cross-part invariants. This page does only that — the span, not the parts.

Reading this pillar LLD

One pillar = one horizontal SPAN through the platform parts. B2 enters on B1's intent, reads its three concentric sources across two parts (SoR for "my own", External World for "world's best", peer Native for B2.c v2+), ranks + budgets them inside the System of Process, hands the composed envelope to the Host's LLM call via B11 PromptBuilder, and records the context manifest in the System of Record for replay. The matrix (products/cos/matrix.html) is the traceability grid — which block, which role. The per-part pages are the local mechanism detail. THIS page is the only home for the cross-part invariants (B2-X1–X5) and the non-local properties (envelope round-trip, whole-pillar budget, peer-Sutra zone). Every claim traces to a cited master anchor, the matrix B2 row, or a per-part page — extraction, never invention; the founder-voice Ring 1 of B2 and the Phase-2 retrieval mechanism are gaps, surfaced below, not filled here.

Open gaps — founder queue

  • B2 Ring 1 (Surface — operator voice) is entirely "Awaiting founder fill" (T-G1-05/06/07) — problem space / need / solution direction for the Context pillar undefined; could founder voice shift the PRIMARY assignment (SoP) once filled? (master #pillar-b2).
  • B2 Ring 3 mechanism is Phase-2 pending (context-retrieval-design.md, T-G3-02) — the physical retrieval + rank + budget engine behind context-build is unspecified; this page documents the contract-level span, not the Phase-2 build (master #pillar-b2).
  • Token-budget ALLOCATION MODEL undefined: "within declared budget" states a constraint but not the per-source split (my_own vs worlds_best vs peer) nor per-source caps nor the drop-order policy beyond "over-budget items drop" — cross-part allocation has no stated owner.
  • SoP-side context-GATHER/BUILD mechanism gap (carried from eng/system-of-process draft gap 4): §1.0 says context-build is second-level detail inside SoP, but the cited §4 ranges only show the context_envelope arriving "from B2" — the SoP-side build mechanism is not specified at §4 level.
  • Which block ISSUES B2's retrieval/ranking LLM call (if any) is unstated: B1's parse is "model work on Host" and v1 B2 ranking is metadata-driven (no LLM), but v2 semantic ranking via F1 implies an LLM call — whose Step, on which host? (master #pillar-b2 + eng/host ADR-005).
  • B2.c peer-Sutra federation protocol (sutra-federation-design.md) deferred to v2+ — the trust model, the wire, and whether peer reads traverse the Connector or a dedicated A2A path are all open (master #b2c-peer-sutras).
  • No B2-specific retrieval latency budget exists; per-task phase-resolution latency profiling + the <15% governance-overhead budget are absent fleet-wide (carried from eng/SoR SHIPPED-SOLUTIONS charter/speed gap).
  • Mapping of the §2.F.E 5 memory layers onto B5.a–d time-horizon stores is unresolved (one substrate, two taxonomies, or separate stores?) — this directly governs what B2.a actually reads (carried from eng/SoR gap; master #section-2-f-5).
