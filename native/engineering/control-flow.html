Engineering — Control Flow: one operator turn across all parts ENGINEERING · zoom 5

What this page is. A WHOLE-SYSTEM view. The 13 per-part engineering pages answer “how does THIS part work”. This page answers a question no single part page answers: what happens, in order, across ALL parts, during one operator turn — UI → Host → Orchestration (route) → System of Process (run) → host-LLM dispatch → System of Record (record) → back to UI, with Authority + Tenancy gating throughout. It cites each part page for the mechanism detail; it never restates a mechanism row (one home, cite the rest — BUILD-PROTOCOL principle 7; D54 for canon).

Prose — reading the turn as one system

The thirteen per-part engineering pages each answer “how does my box work”. None of them answers “what is the order of events when an operator asks for something” — because that order is a property of the whole machine, not any one part. This page is that whole-system view.

The shape is deliberately constrained by the locked §1.0 schema. Three facts pin the sequence so it can't be drawn any other way: (a) the UI carries, it does not think — so reasoning never happens in step 1 or step 6; (b) only System of Process calls the Host — so the host-LLM dispatch (4a) sits inside RUN, never inside ROUTE; (c) Authority + Tenancy wraps everything — so the gate is not a step you can skip past, it is a check at every boundary. Everything else (which channel, which method, whether comms fire) is variable per turn.

The state machine is the other half. The sequence is what happens when the turn goes right; the state machine is the complete set of states the turn can be in, including the three failure states that extend ACTIVE. A reader debugging a stuck turn starts here: find the step (sequence table), find the state (state machine), then click through to the owning part page for the mechanism that's misbehaving.

Open gaps — founder queue

  • Orchestration→Host confirm-back edge unspecified (carried from Eng: Orchestration mech-orch-02, gap 6). §1.0 shows no upward return edge for the step-3 ASK BACK; the sequence assumes it returns via the same channel but the wire-level edge isn't drawn in the cited master ranges. Cross-cut consequence: step 3→UI clarification is asserted, not schema-grounded.
  • Process-finder matching mechanism not named (carried from Eng: Orchestration mech-orch-03, gap 2). Step 3 “find the relevant process” — the matching algorithm (registry lookup vs LLM classify vs hybrid) isn't specified in the cited master ranges. The sequence states THAT a process is found, not HOW.
  • EMERGE on-turn vs async boundary is doc-asserted, not enforced. This page places EMERGE off the synchronous hot path per master §4.11. No runtime artifact confirms EMERGE never fires inline; if a future Step triggered emergence synchronously the sequence would need a 7th surface row.
  • HOW selection has zero runtime enforcement (carried from Eng: Method §3; FQ1 PROPOSED). Step 4's method cascade is doctrine, not a wired gate today. The turn is therefore less deterministic at the method layer than the table implies; resolution gated on FQ1 founder ratification.
  • DEGRADED reconciliation idempotency unproven. §4.10.2 names “idempotent retry” as the DEGRADED exit but no per-connector idempotency contract is cited; the interfaces cross-cut (Eng: Interfaces) is the home that must specify it.
