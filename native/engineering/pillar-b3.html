Smart escalation is the spine of B3 (master §2.B Ring 2): “auto when path is known, ask when material/risky/ambiguous, remember the answer, operationalize from that point.” That single rule is what stitches THINK (ask), DO (auto), and the Authority gate (the decision point) into one pillar — rendered as the cross-part cascade below.

Cross-part invariant 1 — the decision-trail round-trips zero-loss (HS-4)

B3 does not run in isolation: it reads intent{} + task_tier from B1 and the context_envelope from B2, writes its own decision_trail, and hands forward to B4/B5. The non-local property — owned by no single B3 mode — is that this hand-off must survive intact. Per the state envelope (master §4.3, carried on the SoP page):

  • B3 contributes decision_trail [{phase, factors, authority_verdict, output_ref}] to the typed pillar-handoff envelope (alongside B1 intent, B2 context_envelope, B4 outbound, B5 b5_writes).
  • Native enforces shape + authority on every handoff; the envelope must round-trip with zero data loss or HS-4 fires (§4.4 acceptance).
  • HS-4 STOPS the system when DecisionProvenance is unwritable across all 3 channels — “no silent unaudited execution” (§4.10.1, on the Hardstops catalog).

Why this is a pillar-LLD fact and not a part fact: the matrix shows B3→SoP as one PRIMARY cell and B3a→UI as a SUPPORTING cell, but the guarantee that the decision-trail B3 writes is the same one B4 reads is a property of the seam between those cells. The SoP page owns the envelope mechanism; this page owns the B3-specific claim that B3’s slice of it (the decision_trail) is one of the round-tripped fields gated by HS-4.

Cross-part invariant 2 — the run→measure loop (B3b generates, §4.5 gates, retry or escalate)

The defining B3 non-local property: Native does not mark a B3 task done before testing the output — “Test happens BEFORE concluding, not after” (master §4.5, on SoP). This is a loop that no single mode owns; it spans B3b DO (Host reasoning), the §4.5 gate (SoP), and back. The five steps (carried verbatim on the SoP page; cited here):

#Step (§4.5)Part doing the work
1Pre-declare the test per task tier (T0 grep/file-exists/contract-match · T1 step-by-step + integration · T2 operator-visible 1-min iteration · T3 milestone-gate at goal transitions).SoP (tier from B1; method profile from D.11)
2B3 generates output (the auto-execute / DO path).Host reasoning (N16), dispatched by SoP
3Run the pre-declared test — determinism: same input + same Charter → same expected output shape.SoP (§4.5 gate)
4Pass → conclude + write audit row + present (B3c). Fail → loop to B3 retry (max N per Charter); after N failures escalate via Authority gate.SoP → Host (retry) → Authority (on exhaustion)
5Operator feedback (drop / accept / refine) becomes test signal for B5.d learned patterns; thresholds adapt over time per workflow.SoP → B5 (write) → Observability KPI

Rationale (verbatim, §4.5): “testing AFTER means the operator sees a failure and has to ask CoS to redo. Testing BEFORE means CoS catches its own failures and retries silently.” The Accuracy KPI in §7 measures % of outputs that passed first-time-test vs needed retry — the loop’s observable signal (on the Observability page). This is the matrix’s “self-checks before presenting (N03)” cell, rendered as its full cross-part loop.

Cross-part invariant 3 — the escalation cascade (SoP → Method → Host → Authority)

When the run→measure loop cannot succeed silently, B3 escalates — and the escalation path crosses all three spanned parts plus Authority. This cascade is the single most cross-part property of B3; the per-part pages each see only their own hop.

Host-LLM dispatch — how B3 reasoning actually runs (cited, not re-stated)

B3’s decide/execute reasoning is model work on the Host (Host page, B3 SUPPORTING row: “Decide/execute reasoning is model work; method-routing gives problem classes different solving strategies (N16)”). The dispatch contract that carries a B3 reasoning step (owned by the Host + SoP pages; summarized here for the pillar reader):

  • A SoP WorkflowStep with action === 'invoke_host_llm' spawns a host subprocess; host ∈ {claude, codex} and prompt_template are required IFF that action (ADR-005, on the Host page).
  • Per-workflow host slot: the Host position is a selectable slot, not hardwired to Claude — so a B3 reasoning step can route to claude --bare (recursion-safe) or codex (read-only sandbox) per workflow (ADR-005).
  • Resumption after the model returns is the declared callback NativeEngine.on_host_llm_result(execId, stepIdx, r) — flagged on the Host page as an open wire (§8 OS-1).

Pillar-level reading: the same Step primitive is the only LLM-call site for all three B3 modes — THINK, DO, and the verify inside the run→measure loop all dispatch through it. The method profile chosen by D.11 (T0 speed/fast model · T1 reliability/per-step verify · T2 responsiveness/1-min loop · T3 long-horizon quality/best model + ensemble) is what makes “different problem classes get different solving strategies” concrete — its home is master §9 Meta (D.11), cited not restated.
