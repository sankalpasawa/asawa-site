Cron / scheduling facility — daemon-side tick, not OS cron (ADR-017)adr-decisionADR-017 decides: 'Native engine MUST implement cadence scheduling as a daemon-side setInterval tick; MUST NOT depend on external cron / launchd.' CadenceScheduler.start(intervalMs) runs inside the daemon process; on each tick, scheduled cadences whose next-fire time falls within the ±5 min window (I-12) fire TriggerEvent rows, and each fire emits an EngineEvent + DecisionProvenance — replayable like any other Trigger. External cron/launchd was rejected as not portable across macOS/Linux, with no integration with Native's TriggerEvent lifecycle and no DecisionProvenance on fire; a cron-style escape hatch survives only as TriggerSpec.cadence.cron, evaluated by the daemon at tick time. Stated consequences: portable, auditable, ±5min verifiable inside the engine; but 'daemon must stay running for cadences to fire (start/stop discipline matters)' and per-tick CPU cost is non-zero. Master §4.0 cadence row: per-Workflow trigger spec with cadence field; the daemon fires triggers on schedule and dispatches matching Workflows; the operator 'sees the SCHEDULED OUTPUT (daily pulse, weekly synthesis, etc.); not the cron firing'. The second-order draft draws cron feeding the process facility twice: as a START trigger (alongside plugin launch and cold boot) and as recurring cadence ticks the daemon turns into Workflow dispatches per ADR-017.sutra/os/decisions/ADR-017-cron-daemon-cadence-tick.md#decision

On-disk durability — fsync'd JSONL append (ADR-013)adr-decisionADR-013 decides Native MUST persist EngineEvent and DecisionProvenance as fsync'd JSONL append-only files on disk: one JSONL line per event/decision, UTF-8, fsync per append — 'never lose a row on crash'. A stderr beacon fallback fires when the primary path is unwritable, with dual fallback to /tmp (the HS-4 chain). The shape was chosen against four constraints — survives daemon restart, zero new dependency, append-only audit, multi-process safe (POSIX atomic line-level appends); in-memory ring buffer and SQLite were both rejected. Stated costs: disk I/O per event (fsync is not free), and no indexed query — replay is sequential scan. This is the durability contract for everything Compute stores under ~/.sutra-native/.sutra/os/decisions/ADR-013-telemetry-sink-fsync-jsonl.md#decision

Isolated replica kits via SUTRA_NATIVE_HOME (ADR-016)adr-decisionADR-016 decides: 'Native engine MUST honor SUTRA_NATIVE_HOME env var to redirect user-kit reads/writes; the Asawa replica MUST live at $HOME/.sutra-native-asawa-replica/.' Primary user-kit stays at $HOME/.sutra-native/user-kit/ (production / fleet / emergent); the replica gets distinct PID locks + distinct telemetry JSONL so 'daemons can run side-by-side without interference'. Adding the replica primitives to the primary kit was rejected for contamination risk: Workflow ID collision, mixed telemetry in the same JSONL, and no clean reset path. A reset script (bash holding/scripts/build-asawa-native-replica.sh) is idempotent — wipes + rebuilds the replica without touching primary. Stated costs: two daemons mean two memory + CPU footprints when both run, and the operator must remember to set SUTRA_NATIVE_HOME; the decision 'sets pattern for future per-tenant kit isolation as multi-tenant matures'.sutra/os/decisions/ADR-016-replica-as-isolated-user-kit.md#decision

Behavior contracts — shipped-production dossiers folded on this part

No dossiers were assigned to eng-compute in this fanout (0 folded). The Compute layer's behavior contracts live as ADR decisions, carried in-table above: ADR-017 (daemon-side cron tick, ±5min I-12, EngineEvent + DecisionProvenance per fire), ADR-013 (fsync'd JSONL append-only durability, HS-4 stderr+tmp fallback chain), and ADR-016 (SUTRA_NATIVE_HOME replica isolation with distinct PID locks + telemetry). Each ADR's stated decision + consequences are the testable contract; the redo recipe for each is its consequence-set (e.g. ADR-013: implement append-only JSONL with fsync-per-append + stderr/tmp fallback, accept sequential-scan replay). Rationale never copied — full ADR text lives at the linked sutra/os/decisions/ADR-0NN-*.md paths (D54). If a later fanout wave assigns Compute-side dossiers, they fold here as id="contract-<dossier-id>" subsections per the engineering acceptance clause.

Open gaps — founder queue

  • No hardware/OS requirements for Compute anywhere in the doc (supported OS, CPU/memory/disk minimums) — what does an operator's machine need? (_block-compute.html gap 1)
  • Is Host + Daemon co-location on one machine a hard constraint, or can they split across machines? §1.0 only says both 'run on the Compute'. (_block-compute.html gap 2)
  • Compute failure semantics beyond 'cold boot → START': what happens to in-flight Workflow executions when the machine sleeps, crashes, or loses power mid-run? (_block-compute.html gap 3)
  • Cloud-hosted channel (§1.4.5) defers managed compute to v2+ but never says how the §1.0 schema changes when compute is not operator-local — where does the Host (Claude CLI) run in that channel? (_block-compute.html gap 4)
  • No resource governance on the operator's machine: nothing caps daemon CPU/disk usage or defines retention/rotation for decision-provenance.jsonl and native.log growth. (_block-compute.html gap 5)
  • Authority + Tenancy 'gates every access' wraps the Compute box in the diagram, but no compute-level enforcement mechanism (disk encryption, key storage location, local access control) is named. (_block-compute.html gap 6)
  • Section 1.0 gives Compute no pillar-differentiated role — does B5 'keep it mine' imply local-compute data residency on the host machine, or is Compute a uniform substrate for all pillars? (_matrix.html open question)
  • Authority+Tenancy draft gap touching Compute: per-tenant key/data isolation appears only in the deferred cloud-hosted channel activation gate (§1.4.5), not for the v1 own-machine case. (master/index.html#L2369, _block-authority-tenancy)
