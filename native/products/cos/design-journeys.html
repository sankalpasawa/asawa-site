What a journey is

A journey is what the operator lives through from utterance to outcome. Each of the 5 intent types has its own shape, its own approval moments, its own success and failure surfaces. Same engine underneath — different choreography on top.

C.1 TASK journey — "do X for me"

Typical utterance. "Draft the partner update for this week." / "Move the Friday standup to Thursday and send the new invite."

Flow:

  1. Operator states the task.
  2. Native reads intent + scope — names the deliverable in one line back ("OK, drafting the weekly partner update covering Paisa + Testlify").
  3. If the task is reversible and low-risk: Native proceeds. If irreversible (sending email, deleting, charging, scheduling external): Native produces the artifact and asks for go-ahead before the external action.
  4. Native does the work, surfaces the result in-channel.
  5. Operator approves, edits, or rejects. Edits feed forward into the next similar task (see §C.4).
  6. Native confirms completion in one line ("Sent. Logged under partner-updates.").
BranchNative's move
Confidence lowNative confirms scope before starting ("I have two partner lists — Paisa investors or T4 users?").
Native disagrees / can't do itNative says so plainly ("I don't have access to the invoice tool yet — want me to draft the message and you send it?"). No fake completion.
Operator changes mind mid-flow"Stop, do it differently" cancels the in-flight task and restarts from the corrected ask. The half-finished draft is kept for one turn so the operator can salvage parts.
SuccessOperator sees the finished artifact + a one-line "what I did" summary. Time-to-result is in seconds for drafting, minutes for multi-step.
FailureNative states what it tried, where it stopped, and what it needs to finish — never silent, never fabricated. "I drafted the email but couldn't pull the Q2 number — sheet access denied. Paste the number and I'll finish."

C.2 QUERY journey — "tell me Y"

Typical utterance. "What did we decide about Paisa pricing last week?" / "How many T4 users used the plugin yesterday?"

Flow:

  1. Operator asks.
  2. Native picks the source — memory, prior session, connected data, web — and declares it.
  3. Native returns the answer with confidence level (high / moderate / low / unknown) and sources named inline.
  4. If the answer needs synthesis across sources, Native shows the synthesis + a "based on" line.
  5. Native offers one follow-up branch if obvious ("Want me to draft the reply to Benzy about this?").
BranchNative's move
Confidence lowNative returns the partial answer and labels what it doesn't know ("I see two pricing discussions — I'm not sure which you mean. Both are below.").
Native can't find it"I don't have a record of that decision. Want me to check your email / Slack / docs?" — never invents.
Operator changes mind"Actually, just give me the Testlify number instead" — Native drops the prior answer, re-runs against the new ask.
SuccessAnswer + source + confidence, on one screen, no hunting.
Failure"I don't know" stated plainly, with what Native checked and what's left to try. No fabrication, no padding.

C.3 DIRECTIVE journey — "from now on, do Z"

Typical utterance. "From now on, always cite sources." / "Stop emailing me on weekends unless it's urgent."

Flow:

  1. Operator issues the directive.
  2. Native reads scope — one-time vs standing, this project vs all projects, this session vs forever.
  3. Native confirms scope back in one line ("Got it — applies to all research output, across every project, until you say otherwise. Logged.").
  4. Native stores it in the operator's charter (a visible, editable list — see §2.F.E on design-surfaces).
  5. Next time a matching context appears, Native applies the directive and shows a small marker ("applied: cite-sources").
  6. Operator can list, edit, or revoke any standing directive in one ask ("show my standing rules" / "drop the weekend rule").
BranchNative's move
Confidence low (scope unclear)Native asks one disambiguation — "Just for Paisa or everywhere?"
Native sees a conflict with an existing directiveNative surfaces both ("This conflicts with 'always email me daily summaries'. Drop the old one, or keep both with weekend exception?").
Operator changes mind"Actually, just for this week" — Native re-scopes to time-bounded and notes the expiry.

C.4 FEEDBACK journey — "that was wrong, try again"

Typical utterance. "That summary missed the actual decision." / "Too long, cut by half next time."

Flow:

  1. Operator corrects.
  2. Native reads what changed: format, content, tone, scope, or accuracy.
  3. Two-track response: now (re-do this output applying the correction) and future (carry the correction forward to similar work).
  4. Native re-runs the immediate output and surfaces it.
  5. Native names what it's carrying forward ("Got it — keeping summaries to ~5 lines for partner updates going forward.").
  6. Operator confirms the future-rule sticks, or scopes it down ("just for this one, not standing").
BranchNative's move
Confidence low (what to change is unclear)Native asks one targeted question — "Cut what — the context section, or the action items too?"
Native disagrees with the correctionNative says so once, with reason, then complies — "I included the decision because it changed mid-week, but cutting it now. Flag if you want it back."
Operator changes mind"Actually, the first version was right" — Native restores and unlearns the queued correction.
SuccessImmediate redo lands; the same miss does not repeat in the next 24 hours on similar work. Operator sees both what changed now and what changed forward.
FailureIf Native can't tell what to change, it asks once and stops — does not loop guessing.

C.5 NEW IDEA journey — "I want a new capability"

Typical utterance. "What if Native could pre-brief every meeting from my calendar?" / "Explore using OHS/wk to score departments."

Flow:

  1. Operator floats the idea.
  2. Native does NOT immediately build or commit. It enters ideation mode — reflects the idea back in sharper words, names the question underneath, lists 2-3 shapes the idea could take.
  3. Operator picks a shape, parks it, or drops it.
  4. If parked: idea goes into the operator's parking lot — visible, named, dated.
  5. Native nudges the parked idea back at a relevant moment ("You parked 'pre-brief meetings' two weeks ago — calendar access just landed. Want to try it?").
  6. If the operator commits: Native proposes a small first version + what success looks like before any build.
BranchNative's move
Confidence low (idea is vague)Native asks two sharpening questions — "Pre-brief with what? Last meeting notes, or open threads with that person?"
Native sees this is already a capabilityNative says so + shows how to use it now ("This already runs as Daily Pulse — want me to add the meeting layer?").
Operator changes mind"Drop it" — idea leaves the parking lot; Native confirms the drop so it doesn't resurface.
NEW IDEA FLOW

operator: "what if..."

        ▼
   reflect back ──► sharpen ──► show 2-3 shapes
        │

SuccessThe idea is either alive (committed with a v1 in motion), warm (parked with a clear re-surface trigger), or cleanly killed (dropped, won't resurface). Never lost.
FailureNative can't find a viable shape for the idea — surfaces that plainly ("I don't see how this fits today — I'll park it with a note and check back in two weeks") rather than pretending to commit.
