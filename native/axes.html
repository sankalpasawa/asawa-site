Work is ordered by the moment each family fires in the loop, by the pick test on every axis (keep, merge, rename, reject, escalate; only escalate touches the families), and by the five-step path P1 to P5 that makes a kept axis part of the product. The three moves of the one primitive mint the axes the families sort. Realization moves down, cutting a value into buildable parts, and stops at atomicity. Reflection moves up, lifting a record line to the rule it is an instance of, and stops at the rung that describes itself (M6, reflexive). Reframe moves across, the same value on another axis. Reflexive is the stop of the up move, not a third move. Produced by the A→B bootstrap path as bounded Work-Atoms (write → critique → fix), rendered deterministically. Spine: D62 P1 (directional/bounded/structured) + P2 (placement).

At the front of every run, SHAPE reads the fresh input and decides the run's form — what kind of ask it is, how certain the ground is, and where to cut the work into children — so RUN executes a deliberately-shaped plan instead of a default one.

1. Abstract

SHAPE is the family of axes that read the incoming work fresh, every single run, and decide the form that run will take before any of it executes. The one thing every SHAPE axis shares — its answer to the sorting test — is that it reads the INPUT, fresh, on each pass: nothing is carried over as a standing decision, the shaping is re-derived from this ask, this goal, and the patterns available now. SHAPE fires at the front of the loop, between INTENT and RUN, and GOVERN wraps the shaping transition like every other. What the operator gets is a run that is deliberately formed to its own situation — a one-line ask gets one atom, a multi-part build gets a partitioned plan — instead of every piece of work being forced through the same default mold. Read SHAPE as the front door: where an intent stops being a wish and becomes a plan with a shape.

2. What it does

When a new intent arrives, SHAPE looks at it and forms the run around what it actually is, so the operator never has to hand-build the plan or watch a trivial ask get over-processed. It reads the ask and names its kind, it reads how certain the ground is and chooses a posture to match, and it reads where the natural seams are and cuts the work into children along them — and only then does the work begin. The operator feels this as a system that meets each piece of work on its own terms: a summarize-this-doc request runs as a single shot, a ship-the-redesign request fans into a coordinated set of pieces, and a why-is-retention-falling request is treated as an exploration rather than a march to a wrong answer. The plan is shaped to the work, freshly, every time.

3. Why this is its own family

SHAPE exists because the very first decision about a piece of work — what form it should take — is otherwise an unexamined constant, and a wrong default here taxes every later stage. It solves the front-of-loop framing problem for whoever sets work in motion: the same partition, the same posture, the same assumed kind of ask applied to everything regardless of fit. It is its own closed family, and not folded into a neighbor, because its members are the only ones defined by reading the input afresh on each run rather than by accumulating on the unit, gating a transition, or spending a stock — that single read-the-input-fresh property is the boundary. The six-family count is principled on the system's own native rule, not on any external numeric precedent: the families are a closed skeleton while the axes inside each are open, minted flesh (faceted classification in the Ranganathan sense, where a fixed set of facet families holds an open set of values). SHAPE is the front-reading facet of that closed skeleton, with the axis set inside it deliberately left open to mint.

4. Place in the loop

On the shared loop — INTENT, SHAPE, RUN, RECORD, EVIDENCE, GROW, with GOVERN wrapping every transition — the highlight sits on SHAPE, the stage right after INTENT, and the map is otherwise unchanged. SHAPE reads the input fresh and fires at the front, before each run, exactly as its row in the master family table states; it consumes the just-arrived intent and emits the shaped plan that RUN will execute. It is also the stage that reads back from the loop's learning: the form it picks this run can be informed by what GROW has codified from prior runs — the record becomes evidence the moment it is read across runs, which is the EVIDENCE seam — so the front of the loop is where past improvement re-enters the present. GOVERN sits over the shaping transition the same as over every other, deciding whether the chosen shape proceeds, asks, or is denied.

5. The axes

The catalog of SHAPE is small and each member is a categorical dimension you sort the work into — these are read-and-decide axes, not numbers you aggregate. TYPE reads the ask and decides its kind (a task versus a question versus a direction), and it runs first because the kind colors everything after it. CERTAINTY reads how known the ground is and decides the posture — do, analyze, probe, or stabilize — and it sits upstream of the cut because the posture decides which cut even fits. LENS reads where the natural seams are and decides where to cut the work into children, and how those children are wired relative to one another. IMPACT (ruled 2026-09-25, designed, not yet built) is the output side of the same reading: before the work runs it states what the work must move and on which dimension of the goal, as a measure a check can read, and when the work closes the measure is read back against the done line. It is set fresh per piece of work, which is why it belongs in SHAPE; what it moved accumulates in GROW, and Priority ranks work by its impact. Alongside these the family also carries the finer shaping dimensions — the control-flow pattern (parallel versus sequence), the depth of effort, and the run's pace — each likewise read fresh from this input. Every row answers the same sorting question with YES: it reads the input, fresh, every run, and fires at the front before RUN.

6. One axis, walked

Take LENS, the most load-bearing SHAPE axis, and watch its value change across two runs. The takeaway first: the same system produces a completely different plan for two different asks because LENS re-reads the input each time and the seams it finds differ. For a ship-the-onboarding-redesign intent, LENS reads a multi-deliverable build, finds the seams between deliverables, and cuts by deliverable into roughly three children wired to coordinate — its value resolves to a parallel, multi-actor shape. For a fix-this-one-bug intent arriving moments later, LENS reads a single-thread change, finds no seam worth cutting, and resolves to a sequential, single-actor shape — effectively one piece. Nothing about the first run's cut is carried into the second; the value is derived fresh from the input each time, which is precisely what makes it a SHAPE axis rather than a standing setting. The cut LENS chooses is then handed to RUN as the plan to execute.

7. Boundaries

SHAPE owns the fresh, front-of-run framing and nothing downstream of it. It looks like SHAPE should own learning which shape worked best, but that reads the accumulated record across runs, not this input fresh — flip it to GROW, whose Codify axis writes a proven practice into the FOLLOW catalog that SHAPE then reads. It looks like SHAPE should own whether the chosen shape is allowed to proceed, but that gates a transition with an auto-ask-deny verdict — flip it to GOVERN. It looks like SHAPE should own how the children it cut talk to each other, but that reads the relationship between two atoms — flip it to EDGE (handoff, shared-resource, must-cohere). It looks like SHAPE should own the budget a parallel cut will burn, but that is a finite stock the work spends — flip it to RESOURCE. And it looks like SHAPE should own when the run must happen, but that is about over-time scheduling and dynamics — flip it to TIME. In each case the sorting test is the referee: only read-the-input-fresh stays in SHAPE.

8. Why this grouping

These axes group under one family because they all answer the same question — what should this run look like, read fresh from this input — and splitting them would scatter a single front-of-loop decision across several places while merging them into a neighbor would hide the framing step inside learning or gating where it does not belong. The grouping rule is the closed-skeleton, open-flesh principle plus the sorting test: the family slot is fixed, the axes inside it are minted and open, and membership is decided solely by the read-the-input-fresh answer. The rejected alternative was a single mega-shaping axis, which collapses genuinely distinct reads (kind, posture, cut) into one undifferentiated decision and loses the stagger between them.

9. Path to productization

A new SHAPE axis grows along the same reusable path every axis follows — name and define it against the sorting test, show its need-advantage-how-example, thread it onto its owning page, cross-link it into the loop and its neighbors, then ratify it — specialized here so that SHAPE axes thread onto the workflow/flow page and attach at the front of the loop, and are ratified as front-reading members of the closed family. The honest math note belongs here too: SHAPE's natural fit is partial-order and topological ordering over the children it cuts, with acyclicity as the soundness check — detection-grade ordering ships early, while optimizer-grade scheduling is the at-scale horizon and properly belongs to TIME, not SHAPE. For the generic method see axis-productization; for where SHAPE axes live and run, see the platform workflow/flow page. This section points at those; it does not re-explain them.

1. Abstract

GROW is the family of axes that read the accumulated record and write an improvement back, so the next pass of the work starts smarter than the last. The one thing every GROW axis shares — its answer to the sorting test — is that it accumulates on the unit across runs (not a fresh read of one input, not a gate on a single transition): proof builds up, and at an operator-set threshold the system reshapes itself. GROW fires over time, after runs, as the loop's correction leg — INTENT sets the aim, EVIDENCE measures the gap, GROW closes it by changing the next SHAPE. The reader gets the part of Native that makes it a learning loop rather than a re-run loop: a worked practice becomes doctrine, a proven step gets cheaper, a pile of work earns more autonomy. Where SHAPE decides this run, GROW decides how the next run is even allowed to be shaped.

2. What it does

For the operator, GROW means the system stops asking the team to re-decide things it has already watched succeed many times over. A practice that ran the same way enough times and never failed is noticed, surfaced, and — once approved — written into the catalog the next run reads from, so the team follows it instead of rebuilding the decision from scratch; a step the system has watched prove itself enough times can be hardened so it runs cheaper and more reliably; a body of work that has grown enough coordination earns a larger operating shape and more standing autonomy. Crucially, none of this touches the run in flight — GROW reshapes the NEXT run. The operator feels a system that compounds: every completed loop leaves the next loop a little more capable, and the improvements are explicit, approvable, and reversible rather than silent drift.

3. Why this is its own family

GROW solves a problem no other family owns: the work keeps relearning what it already knows, because nothing reads the long record and acts on it. SHAPE reads one input fresh and forgets; GOVERN judges one transition and moves on; only GROW treats the accumulated history as the thing to read and the next run as the thing to change. That cross-run, write-back character is the load-bearing reason it is a closed family of its own and not folded into SHAPE: SHAPE consumes improvements, GROW produces them, and collapsing the two would erase the direction of learning. GROW takes one of six closed family slots — a closed skeleton the sorting test fills (every axis sorts into exactly one family) — so the skeleton stays small and closed while the axes inside it stay open and minted.

7. Boundaries — what this family is NOT

GROW owns improvement that accrues across runs and writes back; it does not own the five near-misses that look like it. A dimension that reads this run's input fresh and shapes only this run is not GROW — it is SHAPE; the flip is the sorting test's first question (fresh input versus accumulated record), and SHAPE is the sibling that consumes the improvements GROW produces. A dimension that approves or blocks a single transition (auto / ask / deny) is not GROW even though GROW proposes write-backs — it is GOVERN; the flip is gate-a-transition versus accumulate-then-reshape, and GOVERN is the sibling whose authority gate must admit every GROW improvement. A dimension that is the typed link between two units is not GROW — it is EDGE; the flip is that GROW grows a cross-unit edge over time but the typed link itself lives in EDGE (the two compose: an edge is wired at SHAPE and grown at GROW, and the cross-unit handoff GROW grows is one of EDGE's three typed links). A dimension about a finite stock the work spends is not GROW — it is RESOURCE; GROW may read spend trends, but allocation and reconciliation belong to RESOURCE. A dimension about when work runs or how it behaves over time is not GROW — it is TIME, the one family that owns the schedule-and-dynamics reading. Each near-miss is handed to its named sibling so GROW's outer edge is closed, not hand-waved.

1. Abstract

GOVERN is the family that answers a single question at every transition in the loop: may this proceed, and on whose authority? Every axis in GOVERN shares one thing — it gates a transition with a three-rung verdict whose canonical form is auto / ask / deny. That is its answer to the sorting test: a SHAPE axis reads the fresh input, a GROW axis accumulates on the unit, a RESOURCE axis is a finite stock — a GOVERN axis decides whether a change is allowed to happen at all. GOVERN does not do the work and does not improve the work; it wraps the work, sitting over INTENT, SHAPE, RUN, RECORD, EVIDENCE, and GROW alike, and biting hardest where an action leaves the system or a learned change writes back. What the operator gets is a system that can act on its own where it is safe to, stops and asks a real person where the stakes warrant it, refuses cleanly where a binding rule forbids it, and can always answer the question why was this allowed, or why was this blocked.

2. What it does

GOVERN gives the operator a system that is trusted to act without becoming a system that acts blindly. As work flows through the loop, every transition that could spend something irreversible, touch the outside world, or rewrite how the system behaves is held up to an authority dimension before it commits, and the operator sees the action proceed automatically when it is routine and reversible, get paused for their decision when it is consequential, or get refused when it crosses a binding line. The operator never has to watch everything to stay in control — they set where the line sits, and the family enforces that line on every transition while it runs, surfacing only the calls that genuinely need a human. And because every verdict is recorded with its reason, the operator can replay any decision after the fact and get a straight answer to who decided this and why, turning trust from a leap of faith into something inspectable.

3. Why this is its own family

GOVERN solves the control problem an autonomous work-loop creates for the operator who is accountable for it: a system that shapes, runs, records, and improves on its own will, without a gate, eventually take an action the operator would never have sanctioned. It is its own closed family — and not folded into SHAPE or GROW — because deciding whether a change may happen is a categorically different act from deciding how to shape the work or learning to do it better; the sorting test isolates it cleanly with one question, gates a transition with an auto / ask / deny verdict. The six-family count stays principled rather than arbitrary: GOVERN is one of six closed slots and it earns a slot because authority is orthogonal to every other family — any axis in any family can be gated, so the gate cannot live inside any one of them.

2. WHAT IT DOES

EDGE makes the connections between pieces of work first-class, so an operator can see and govern them instead of discovering them as breakage. When work fans out into atoms that must touch, EDGE is what orders the handoff so a consumer never reads a half-finished output, arbitrates the moment two atoms reach for the same finite pool so one proceeds and one waits with a reason, and holds a shared standard so independently built pieces still cohere into one whole. The operator names who may hand to whom and what they share — and the system enforces those links, watches how they are actually used, and surfaces the ones gone stale for tightening. When a handoff crosses an isolation boundary — one unit handing to a sibling unit — the same link is treated as explicit and logged rather than ambient: the cross-boundary form is still a handoff, governed by GOVERN at the crossing and grown by the GROW Cross-unit axis over time. The default is isolation: nothing crosses a boundary until an EDGE is deliberately wired, so the blast radius of any one atom stays bounded and every connection has a named owner and an audit trail.

3. WHY THIS IS ITS OWN FAMILY

Decomposition creates a blind spot: the moment you cut one job into many atoms, the connections between them become load-bearing — and no single-atom axis can read a connection, because a relationship is not a property of either endpoint. EDGE solves this for the operator who has fanned work out and now needs the seams to hold: ordering, contention, and coherence. It is a closed family of its own, not folded into GOVERN, because GOVERN gates every transition of one unit while EDGE reads the standing link between two — a different reader, a different lifecycle (wired at SHAPE, grown at GROW, not evaluated at every gate). It is not folded into RESOURCE either: a shared-resource edge is about the relationship of contention, while RESOURCE is the finite stock itself. The six-family count stays principled and inside the proven 4-6 structuring range; EDGE earns its slot because the relationship is the one thing the other five structurally cannot see.

4. PLACE IN THE LOOP

On the shared loop diagram — the same INTENT to SHAPE to RUN to RECORD to EVIDENCE to GROW map used on every page, with GOVERN wrapping every transition — EDGE lights up at SHAPE and at GROW, the two ends of a link's life. It reads the link between atoms; it is wired at SHAPE (the connection is planned and authority-checked before the work runs) and grown at GROW (accumulated usage of the link is read and the link kept, tightened, or dropped for the next run). In between, an EDGE acts as the work runs — a handoff fires when its producer completes, a shared-resource edge arbitrates at the moment of contention — and every such crossing is logged at RECORD so EVIDENCE can audit it and GROW can act on the trend. GOVERN still wraps each crossing: an EDGE says a link may exist, never that a given transition across it bypasses authority.

5. THE AXES

EDGE holds exactly three relationship axes, each carrying its own coordinates — what it reads, when it fires, and the states it moves through. Handoff reads one atom's output as another's input; it fires at RUN when the producer completes and needs an ordering plus a usable output, moving an atom from waiting to fed to consumed. Shared-resource reads two atoms' competing claim on one finite pool; it fires at the moment of contention and needs an allocation rule (first-come, priority, or budget-order), moving claimants through available to allocated to one-waits — this axis is the categorical seam that the RESOURCE family measures numerically on the other side. Must-cohere reads two atoms that each build a piece of one whole; it fires across the whole span of parallel work and needs a standard agreed up front or an integration step at the end, moving from divergent to checked to coherent. All three are categorical relationships you sort and enforce; shared-resource is additionally the categorical face of a claim whose magnitude RESOURCE aggregates. One important variant lives inside handoff rather than beside it: a cross-unit delegation is a cross-boundary handoff — a handoff that crosses a Tenant boundary, sharing the waiting/fed/consumed ladder but carrying a standing grant whose isolate -> coordinate -> delegate lifecycle is driven by the GROW Cross-unit axis, not by a fourth EDGE axis.

6. ONE AXIS, WALKED

Take handoff, the flagship EDGE axis — the simplest typed link — and walk one instance through the loop in its load-bearing cross-boundary form, so the trace also shows what a cross-unit delegation actually is. The takeaway first: a handoff orders a producer before its consumer, and when it crosses a unit boundary it is wired explicitly, leaves a trail when it fires, and is judged by its usage over time — so reach is never ambient and never permanent. At SHAPE, branch A is wired with a cross-boundary handoff to a specific approval step on sibling branch B; with no link wired, the call would hit the default boundary stop and fail closed (state: isolated). The work runs: A's producer completes, the wired handoff is authority-checked at the crossing, and the output moves across — B's approval step goes from waiting to fed, then to consumed when it reads A's output (state at the seam: coordinated, then delegated). 7. BOUNDARIES — WHAT THIS FAMILY IS NOT

EDGE owns the link between atoms and nothing else; each adjacent concern flips to the sibling the sorting test assigns. A near-miss that looks like EDGE but is not: "may this action proceed, auto/ask/deny?" looks like governing a crossing, but it gates a single transition of one unit, so it belongs to GOVERN — the sorting flag is that it reads a gate, not a relationship. "How much of the pool is left and did it reconcile?" looks like the shared-resource edge, but it reads a finite stock's magnitude, so it belongs to RESOURCE — EDGE owns the categorical fact of contention between two atoms, RESOURCE owns the quantity; this is one coupling seen from both sides, the S2/S3 rungs of the maturation ladder, and both docs name it. "When must this run and does it clash on the schedule?" looks like coordinating two atoms in time, but scheduling contention is RESOURCE seen over time, owned jointly by RESOURCE and TIME, not by EDGE. "Should a cross-unit grant be kept, tightened, or revoked as it scales?" reads the link's usage over time, so the grant lifecycle itself belongs to the GROW Cross-unit axis — EDGE supplies the cross-boundary handoff that GROW then grows. For the gating of crossings see the GOVERN family; for the finite pool behind a shared-resource edge see the RESOURCE family; for clash-over-time see the TIME family; for the cross-unit grant lifecycle see the GROW family.

8. WHY THIS GROUPING

These three axes group as one family because they share a single reader — the relationship between two atoms — and that shared reader is exactly the sorting test's EDGE question; the grouping rule is the sorting test, not surface similarity. The rejected alternative was to scatter them: fold shared-resource into RESOURCE and let cross-unit handoffs live in GOVERN. That was rejected because it would split one reader (the link) across two families, leaving handoff and must-cohere homeless and forcing GOVERN to carry standing links it does not gate per-transition. A second tempting move — promoting cross-unit delegation to a co-equal fourth EDGE axis — is also rejected: delegation is the cross-boundary form of the handoff axis, grown by the GROW Cross-unit axis, so minting it as a fourth axis would double-count one link and break the catalog's three-axis count. The closed-skeleton / open-flesh principle settles both: the family slot is closed at "reads the relationship" and the catalog at three axes, while new relationship variants (a coherence-contract variant, a new grant scope) mint into an existing axis as flesh rather than spawning a fourth axis or a new family — and a genuinely new closed-skeleton axis escalates to the core author rather than silently bending EDGE's boundary.

9. PATH TO PRODUCTIZATION

A new EDGE variant has a known path, which is what makes the family's open-flesh-on-closed-skeleton claim real: name and define it against the sorting test (does it read the relationship between two atoms?), confirm it slots into one of the three existing axes rather than claiming a fourth, show its need / advantage / how / example as an operator feature, thread it onto the owning page beside its sibling EDGE axes, cross-link it into the loop at SHAPE and GROW and to its named neighbors, then ratify it. What ratifies an EDGE variant is the invariant that a link never bypasses the stringency it crosses — a cross-boundary handoff is a ceiling, not a floor — together with a defined grown-over-time rule (for cross-unit handoffs, the GROW Cross-unit keep-if-used, tighten-if-idle rule) and the boundary-stop fallback when no link exists. 1. ABSTRACT

RESOURCE is the family of axes that answer one question about every piece of work: what finite stock does this work spend, and is there enough left? Its single shared trait — the answer to the sorting test — is that each axis names a bounded pool that the work draws down and that must reconcile, not merely accumulate: tokens, money, attention, compute slots, rate-limit headroom, a human's time, an account's standing. RESOURCE reads the running spend against the available pool and fires hardest at RUN (when an atom reserves and consumes) and at RECORD (when the pool balance is reconciled). The reader gets the family that turns 'we ran out mid-run, opaquely' into an explicit, auditable wallet: every atom debits a named stock, every parallel claim is allocated or queued by a stated rule, and every run closes with a balance that adds up. Where SHAPE decides how to cut the work and TIME decides when it runs, RESOURCE decides whether the work can afford to run at all.

2. WHAT IT DOES

For the operator, RESOURCE makes the cost of work visible and governable while it happens, not after it has overspent. When several atoms run in parallel and reach for the same pool, the family allocates the stock by a stated rule and queues the losers rather than letting them all drain the wallet until it silently empties mid-run; an operator watching a long parallel job sees one atom reserve its share, another wait, and the pool draw down to a number they can read, not a surprise. When the run ends, the family reconciles — it shows that what started, plus what came in, equals what was spent plus what remains plus what is still reserved — so the operator can trust the ledger instead of guessing why credits vanished. And when a pool is exhausted before a new intent arrives, RESOURCE refuses the work cleanly at the front with a stated reason, so the failure is a legible 'allocation denied, pool empty' rather than a half-finished run and an opaque out-of-credits error.

3. WHY THIS IS ITS OWN FAMILY

RESOURCE exists because scarcity is a distinct concern from shaping, timing, or gating: a pool can be empty even when the plan is perfect, the schedule is met, and authority has said yes. The problem it solves — for any operator running parallel or repeated work against a metered stock — is that without an explicit finite pool the system has no way to say 'stop, there isn't enough', and overspend shows up only as a downstream failure with no ledger to read. It is its own closed family, not folded into a neighbor, because the sorting test isolates exactly one yes: it is the only family whose axes name a finite stock the work spends and must balance. That single-yes test is what keeps the family count principled rather than borrowed from an external tally — each family slot is the closed skeleton that holds exactly one sorting answer, and the answer here ('a finite stock the work spends and reconciles') is held by no other family. So 'cost' does not leak into TIME (which is about when, not how much is left) or into GOVERN (which decides whether an action is allowed, not whether the stock can fund it); it stays its own slot because its sorting answer is its own.

It earns a closed slot because its sorting question — is this about when, or about dynamics over time — catches a class of concern no sibling's question catches, and because temporal reasoning has a distinct character: it is plan-forward and graph-shaped, not a fresh per-input read and not an accumulated tally. Six families is a principled count — the closed skeleton the sorting test fills — and TIME is the load-bearing sixth: drop it and scheduling collapses into hand-waving and dynamics into surprise. It is its own family because the question 'when, and how over time' is orthogonal to all five others and cannot be folded into any of them without losing the answer. That it reads as 'one axis with two faces' on the canon time page is the same claim from the inside — a single shared signature — and 'family' is that signature seen from the master table; the two readings name the same thing, not a disagreement about how many axes live here.

4. Place in the loop

On the shared loop — INTENT, SHAPE, RUN, RECORD, EVIDENCE, GROW, with GOVERN wrapping every transition — TIME lights up almost the whole arc, with the highlight on its two firing moments. It reads the work graph and the loop's stocks-and-delays, then acts as a plan at SHAPE (the schedule face: when must this run, by when is it due) and as observed motion from RUN through GROW (the dynamics face: how is the rhythm actually behaving). RECORD captures whether each beat landed on time; EVIDENCE flags the misses past grace; GROW aggregates beats into a health signal. GOVERN, wrapping all of it, consults that health at the next gate — a healthy rhythm passes on audit-only, a faltering one can require a human decision. The map never changes; only this family's highlight moves to show TIME plans at the front and watches across the whole loop.

6. One axis, walked

Take Cadence, the most load-bearing TIME axis, and watch one value move across the loop. Takeaway first: a cadence does not catch itself up — it surfaces lateness as a number and hands the decision to authority. A recurring payroll job is given a fortnightly rhythm at SHAPE, expressed as a plain recurrence the operator can read; the operator also sets this rhythm's degraded threshold to k = 3 consecutive misses (k is policy-defined per rhythm, not a fixed family constant — see the open-k note below). The loop holds it; for several cycles the beat lands on time and RECORD marks each on-time. Then one cycle the beat is late — RECORD captures the lateness, EVIDENCE checks it against the grace margin and finds it past, so it is flagged rather than swallowed: that is miss 1 of the operator-set 3. A second and third miss follow (misses 2 and 3); GROW aggregates the run of misses into a health state that flips from healthy to degraded exactly when the count reaches this rhythm's k of 3 — the third consecutive miss. Now the highlight reaches GOVERN: at the next gate, authority reads the degraded health and, because this rhythm is load-bearing, requires a human decision before the next run proceeds. At no point did the system silently fire the missed beats — it counted, flagged, and escalated. The static Cadence row from the catalog has become a running one: a rhythm set, a lateness measured, a health degraded at the operator's chosen k, a gate raised. Open-k note: the threshold is operator-set and inherits canon's still-open pattern-emergence-k status (PROPOSED, not ratified); k = 3 here is this rhythm's policy choice, illustrative of the dial, not a fixed value the family asserts.

7. Boundaries — what this family is NOT

TIME owns when and over-time behavior, and nothing else; each near-miss below is converted, flipped to the sibling whose sorting question truly claims it, and flagged with the reason. The mandatory handoffs: scheduling contention is RESOURCE seen over time — when two jobs collide for one finite pool at the same moment, the collision is a stock problem, owned by RESOURCE, even though it shows up on a calendar; the coupling is real and named on both sides (a TIME deadline can be missed because a RESOURCE pool was dry). A deadline that triggers an ask-or-act decision is not TIME's to gate — TIME measures the lateness, GOVERN renders auto/ask/deny, so cadence-health feeds the gate but does not own it. A rhythm hardening into team doctrine ('we always run this weekly') has left the when-question and entered GROW, which owns accumulation-into-practice. TIME states the schedule shape and the dynamics warning; it does not guarantee on-time delivery or stability — a fully-verified atom set can still miss its deadline or oscillate, and that honesty is a boundary, not a gap.

8. Why this grouping

These axes group as one family because they share a single sorting answer — when, or dynamics over time — and splitting them would scatter that answer across slots that ask different questions. The rejected alternative was to fold scheduling into RESOURCE (since contention looks like a stock fight) and dynamics into GROW (since both watch many runs); both were rejected because the unifying question is temporal, not stock-based or accumulation-based — contention is a stock problem only incidentally clocked, and dynamics is about the shape of motion, not the hardening of practice. Merging TIME away would lose the one place that distinguishes fast from on-time and steady-looking from oscillating. The grouping rule is the same closed-skeleton, open-flesh principle the whole system uses, the faceted-scheme discipline of Ranganathan's PMEST applied here: the family is fixed (the two canon faces plus the worked Cadence), the when-axes minted within it are open (Lateness, Cadence-health, and any future rhythm or stability signal).

9. Path to productization

A new TIME axis grows along the same reusable path every axis follows — name and define it, show its need-advantage-how-example, thread it onto the owning time page, cross-link it into the loop and its neighbors, and ratify it — specialized here by where it threads and what ratifies it. A minted when-axis (the section-5 illustrative rows are this path mid-stride) threads onto the family's owning time material and is cross-linked into its two firing moments (plan at the front, dynamics across the loop) and to its named neighbors in RESOURCE and GOVERN; it is ratified as a directional decision that fixes which face it belongs to and states its honest ceiling (diagnostics now, early-warning later). The open-set claim is concrete: a new rhythm, a new lateness measure, or a new stability signal has a known route in, and the family closes at its two faces only until real usage forces the core author to reshape the skeleton. Resource (the finite stock) folded from resource.html on 2026-09-29
WORKING DRAFT (2026-06-15). The second primitive beside the Work-Atom. An atom is the unit of doing; a resource is the finite, singular thing it spends. Naming spend a first-class primitive lets the record reconcile (balance), not merely append.

What it is · where they come from

A resource is born wherever the world is finite (limited capacity) and singular (one of it) and more than one atom wants it at once. With one atom running serially, nothing is shared; the moment you parallelize, resources appear.

ResourceWhy finite/singularThe competition
compute / rate-limit / concurrency capone machine; capped calls/min; daemon runs N at onceatoms queue / starve for a slot
money / token budgetone finite $ poolatoms drain the same wallet
the human (attention / approval)one operator, finite timeatoms pile up at the ask-gate
the record (shared state)one System of Record; one row/statetwo atoms write the same row → clash
an external account / connectorone Slack token, one API, one inboxsends serialize through one door
context windowfinite per runsub-tasks compete for what's loaded

What it needs — allocation + reconcile

  • Allocation — when atoms compete, a rule decides order: first-come, priority, or by-budget. Without one: starvation (an atom never gets the slot) or thrashing (atoms collide on the record).
  • Reconcile — every atom debits a resource; the record should balance (resources-in = resources-out + delta-stock), not just append. That makes runs auditable, not merely narrated.
Resource contention is the S2 (coordination) / S3 (resource) rungs of the maturation ladder, and the shared-resource edge seen between two atoms. Scheduling's finite-resource contention (Time) is the same thing on the clock.

Minting on the fly — and when the families change

Five of the six worked examples above were minted — they were never in a built-in list. That is the point: users mint axes freely; the family skeleton stays closed. The retention gate decides each minted axis’s fate:

OutcomeWhenWhat happens
keeppasses the pick test, no overlapproductize via P1–P5 (on the fly)

Only escalate changes the families, and only the core author does it — deliberately, off-the-fly. This is the single guard that keeps the skeleton closed while the axis set stays open.
